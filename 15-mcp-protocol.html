MCP协议深度 必考

🎯 学习目标：掌握MCP（Model Context Protocol）协议原理、Client-Server架构、Transport层（SSE/stdio）、Tools/Resources/Prompts三大核心概念、Java实现MCP客户端（SSE+JSON-RPC）、mall-agent中的MCP实战集成，能在面试中清晰阐述MCP的设计理念和工程价值。

MCP是AI领域的"USB-C接口"——定义了一套统一的工具调用协议，让任何AI应用都能用同样的方式调用任何工具，不用为每个工具写定制适配代码。

1. MCP是什么 ★★★★★ 必考

MCP（Model Context Protocol）是Anthropic于2024年底提出的标准化AI工具调用协议。它解决的问题非常具体：每个AI框架都自己定义工具接口格式，导致工具无法跨框架复用——你在langchain4j里写好的工具，Spring AI用不了，Python LangChain也用不了。

MCP解决的核心问题

在没有MCP之前，集成一个外部工具需要：1）理解那个工具的API文档（每个工具格式不同）；2）写适配代码（把工具API包装成框架要求的格式）；3）处理认证、重试、错误。如果要用10个工具，就要写10份适配代码。

有了MCP之后：1）MCP Server按统一协议暴露工具；2）MCP Client按统一协议发现和调用工具；3）任何框架只要实现MCP Client，就能调用所有MCP Server的工具。工具提供方和AI应用解耦——就像USB-C让所有设备用同一个接口充电一样。

MCP = AI工具调用的"USB-C标准"：统一接口，解耦工具提供方和AI应用

2. MCP架构：Client-Server模型 ★★★★☆

MCP采用经典的Client-Server架构，通过JSON-RPC 2.0进行通信。一个MCP Server可以同时被多个MCP Client连接，一个Client也可以连接多个Server。

MCP架构三要素

  • MCP Host：发起连接的AI应用（如Claude Desktop、Cursor、你的Agent）。它管理多个MCP Client实例，每个Client连接一个Server。
  • MCP Client：协议客户端，负责与一个Server建立连接、发送请求、接收响应。一个Host可以有多个Client。
  • MCP Server：协议服务端，暴露Tools/Resources/Prompts。一个Server可以同时服务多个Client。

Transport层：SSE vs stdio

Transport通信方式适用场景mall-agent使用
SSE（Server-Sent Events）HTTP长连接：GET /sse建立连接，POST /mcp/message发送JSON-RPC请求远程Server，跨网络通信✅ mall-agent连接远程mall-mcp-server
stdio标准输入输出：启动子进程，通过stdin/stdout通信本地Server，同机进程通信—

3. MCP三大核心概念：Tools/Resources/Prompts ★★★★☆

概念用途谁控制模型可见性
Tools模型可调用的操作（查订单、发邮件、调API）Server暴露，模型决定是否调用模型可见——LLM根据Tool Description决定调用
Resources模型可读取的数据（文档、数据库记录、文件）Server暴露，模型/Client读取模型可见——类似RAG的检索结果
Prompts预定义的Prompt模板（欢迎语、错误提示、FAQ）Server提供，Client选择使用用户/Client可见——帮助用户快速开始

Tools vs Resources的核心区别

Tools是动作：LLM决定"我要调用这个工具"→执行操作→返回结果。如"查订单"、"发邮件"、"创建工单"。

Resources是数据：LLM可以读取这些数据作为上下文，但不能修改。如"知识库文档"、"用户手册"、"API文档"。Resources更像RAG中的"检索结果"——给LLM提供背景信息，但LLM不能对它们执行操作。

mall-agent主要用Tools（32个本地工具+MCP远程工具），Resources目前通过RAG的向量检索实现，没有走MCP的Resources机制。

5. Java实现MCP客户端（SSE+JSON-RPC） ★★★★★ 必考

这是mall-agent的技术亮点——Java实现MCP客户端。大部分MCP客户端是Python/TS写的，Java实现展示了你的底层协议理解能力。

Java (MCP客户端核心实现) 
public class McpSseClient {
    private final WebClient webClient;  // WebFlux HTTP客户端
    private final String baseUrl;

    // 1. 建立SSE连接，持续接收Server推送的事件
    public Flux<String> connect() {
        return webClient.get()
            .uri(baseUrl + "/sse")
            .accept(MediaType.TEXT_EVENT_STREAM)
            .retrieve()
            .bodyToFlux(String.class);
    }

    // 2. 发送JSON-RPC请求
    public Mono<JsonNode> sendRequest(String method, JsonNode params) {
        JsonNode request = objectMapper.createObjectNode()
            .put("jsonrpc", "2.0")
            .put("id", UUID.randomUUID().toString())
            .put("method", method)
            .set("params", params);

        return webClient.post()
            .uri(baseUrl + "/mcp/message")
            .contentType(MediaType.APPLICATION_JSON)
            .bodyValue(request)
            .retrieve()
            .bodyToMono(JsonNode.class);
    }

    // 3. 发现工具列表
    public Mono<List<ToolDefinition>> listTools() {
        return sendRequest("tools/list", null)
            .map(resp -> parseToolList(resp.get("result")));
    }

    // 4. 调用工具
    public Mono<String> callTool(String toolName, Map<String, Object> args) {
        JsonNode params = objectMapper.createObjectNode()
            .put("name", toolName)
            .set("arguments", objectMapper.valueToTree(args));

        return sendRequest("tools/call", params)
            .map(resp -> resp.get("result").toString());
    }
}

工具适配器：McpToolAdapter

MCP返回的工具是JSON Schema格式，需要适配为langchain4j的Tool接口。McpToolAdapter做这个转换：

  • inputSchema → 转换为Tool的参数定义（name + type + description）
  • 工具调用 → 通过McpSseClient.callTool()发送JSON-RPC请求
  • 返回值 → 包装为HardWorkflowTool的标准返回格式

这样本地工具和MCP远程工具在ReAct循环中统一调度——LLM不需要知道工具是本地的还是远程的，它只需要知道"有一个工具叫query_order，参数是orderId"。

MCP不可用时的降级策略：启动时连接MCP Server失败→返回McpTool.disabled()占位实例（调用时返回"工具不可用"）→本地工具不受影响。运行中断开→工具调用返回错误JSON→ReAct循环感知失败→尝试其他工具或返回"服务暂时不可用"。

当前欠缺：没有自动重连。生产环境应加指数退避重试（1s→2s→4s→8s→max 30s）。

6. mall-agent中的MCP实战 ★★★★★

架构设计：本地工具 + MCP远程工具统一注册

mall-agent的HardWorkflowToolRegistry管理两类工具：

  1. 本地工具（32个）：直接实现HardWorkflowTool接口，注册在Spring容器中。如query_order、track_logistics、check_balance。
  2. MCP远程工具：启动时通过MCP Client连接mall-mcp-server → tools/list获取工具列表 → McpToolAdapter包装为HardWorkflowTool → 注册到Registry。

LLM看到的是一个统一的工具列表，不区分本地/远程。工具分类选择性注入对两者同样生效。

本地工具和MCP远程工具统一注册到HardWorkflowToolRegistry，LLM看到统一列表

7. MCP vs 传统API调用 ★★★☆☆

对比维度传统API调用MCP
工具发现手动看文档→写适配代码tools/list自动发现
接口格式每个工具不同（REST/GraphQL/gRPC）统一JSON-RPC 2.0
参数Schema手动定义/文档里找inputSchema自动获取
跨框架复用每个框架写一次适配一次实现，所有框架可用
认证每个工具不同（API Key/OAuth/Basic）MCP层统一管理
版本兼容API改了就断协议版本协商
mall-agent选择本地工具用传统方式（Spring Bean）远程工具用MCP
MCP ≈ JDBC之于数据库。JDBC之前：每个数据库有自己的一套API（Oracle OCI、MySQL C API）→ 换数据库要重写所有数据访问代码。JDBC之后：统一的Connection/Statement/ResultSet接口 → 换数据库只改驱动。MCP同理：统一Tools/Resources/Prompts接口 → 换工具只改Server，Client代码不变。

8. 面试Q&A ★★★★★

MCP协议是什么？解决了什么问题？

MCP（Model Context Protocol）是Anthropic提出的标准化AI工具调用协议，解决"每个AI框架自己定义工具接口，工具无法跨框架复用"的问题。核心思想：定义统一的Client-Server协议（JSON-RPC 2.0 + SSE/stdio），Server暴露Tools/Resources/Prompts，Client自动发现和调用。

类比：MCP就是AI领域的"USB-C"——统一接口，解耦工具提供方和AI应用。之前每个框架需要为每个工具写定制适配代码（N×M），现在一次实现MCP即可（N+M）。

"USB-C"类比简单有力。说"N×M变N+M"展示你理解协议的核心价值。
你的项目怎么集成MCP的？Java怎么实现的？

Java实现MCP客户端：用Spring WebFlux的WebClient连接mall-mcp-server。SSE长连接接收事件（GET /sse），JSON-RPC发送请求（POST /mcp/message）。启动时调用tools/list自动发现远程工具，McpToolAdapter包装为HardWorkflowTool接口，与本地32个工具统一注册到HardWorkflowToolRegistry。

关键设计：1）MCP不可用时返回disabled()占位，本地工具不受影响；2）LLM看到统一工具列表，不区分本地/远程；3）工具分类选择性注入对两者同样生效。

说"Java实现MCP客户端"是加分项。提"disabled()降级"和"统一注册"展示工程设计。
MCP的Tools和Resources有什么区别？

Tools是动作：模型可调用的操作（查订单、发邮件、调API）。LLM决定是否调用、传什么参数。Resources是数据：模型可读取的数据（文档、数据库记录、文件）。LLM只能读取不能修改。

类比：Tools ≈ Service方法（有副作用），Resources ≈ 配置文件/数据库查询（只读）。mall-agent主要用Tools，Resources通过RAG向量检索实现。

"动作vs数据"的区分要清楚。说"mall-agent主要用Tools"展示实际经验。
MCP的SSE Transport和stdio Transport怎么选？

SSE（HTTP长连接）：适合远程Server，跨网络通信。GET /sse建立事件通道，POST /mcp/message发送请求。需要处理断线重连。mall-agent用这个连接远程mall-mcp-server。

stdio（标准输入输出）：适合本地Server，启动子进程通过stdin/stdout通信。更简单、延迟更低，但只限同机。适合本地工具（如文件系统操作、本地数据库查询）。

选择原则：远程服务用SSE，本地工具用stdio。如果工具需要跨机器共享，用SSE。

说清楚两种Transport的适用场景。提"远程用SSE，本地用stdio"是标准答案。
MCP协议有什么局限？

1）协议尚在演进：MCP还在快速迭代，API可能变化。2）性能开销：JSON-RPC序列化+HTTP往返比本地方法调用慢。高频调用场景需要批量优化。3）工具描述质量依赖：LLM根据Tool Description决定调用，描述写不好工具就废了。4）安全：MCP Server暴露什么工具需要谨慎——不应该把"删除数据库"这种工具暴露给LLM。5）生态仍在早期：MCP Server的数量和成熟度远不如REST API生态。

能说出局限说明你不是盲目吹捧。提"协议演进中"和"安全"展示批判性思维。
  • MCP是什么：标准化AI工具调用协议，Client-Server架构，JSON-RPC 2.0 + SSE/stdio
  • 核心概念：Tools（动作/模型可调用）+ Resources（数据/模型可读取）+ Prompts（模板/用户可见）
  • Transport：SSE（远程/HTTP长连接）vs stdio（本地/标准输入输出）。mall-agent用SSE
  • Java实现：WebClient + SSE + JSON-RPC，McpToolAdapter适配，HardWorkflowToolRegistry统一注册
  • 降级策略：MCP不可用→disabled()占位，本地工具不受影响。欠缺：自动重连
  • 类比JDBC：MCP统一工具调用接口，就像JDBC统一数据库访问接口
  • 面试要点："USB-C"类比 + N×M→N+M + Java实现MCP客户端 + 统一注册 + 降级策略
