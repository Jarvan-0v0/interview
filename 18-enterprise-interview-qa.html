第一类：架构设计类 ⭐⭐⭐

1. Agent编排器是怎么设计的？为什么这样设计？ 高频

我们项目没有用复杂的Agent编排器，而是手写ReAct循环作为编排核心。ReActAgentService是整个Agent的调度中枢，负责 Thought → Action → Observation → Final Answer 的循环驱动。

设计原因是：矿池客服场景的工具调用链路通常不超过3轮（查算力→查订单→查退款），用手写ReAct + maxRounds=3就够了，不需要LangGraph那种多DAG编排。手写的好处是完全可控——每轮的日志、超时、降级都能精确控制，出问题排查链路清晰。

具体实现：ReActAgentService.executeReAct()接收用户问题，构建ReAct Prompt（硬编码text block），调用LlmModelFactory.streaming(routeSpec)获取流式模型，解析返回的Action行提取工具名和参数，通过HardWorkflowToolRegistry找到对应工具执行，将Observation追加到chatHistory进入下一轮。round > maxRounds时走兜底逻辑直接生成Final Answer。

// ReActAgentService 核心循环（简化）
int maxRounds = aiProperties.getHardWorkflowMaxRounds(); // 3
if (round > maxRounds || done.get()) {
    // 兜底：超出轮数，直接生成Final Answer
    return generateFallbackAnswer(chatHistory, route);
}
log.info("ReAct round {}/{} starting", round, maxRounds);
// 解析Action → 执行工具 → 追加Observation → 下一轮
💡 回答策略：面试官问编排器，先说"我们用的手写ReAct循环"，再解释为什么不用LangGraph/多Agent——因为场景简单+可控性强。最后补一句"如果业务复杂到需要多DAG编排，会考虑迁移到LangGraph4j"。
2. 系统的可扩展性是怎么设计的？

可扩展性体现在三个维度：工具层、模型层、知识层。

工具层扩展：HardWorkflowToolRegistry + ToolCategory枚举（8大分类），新增工具只需实现AbstractWorkflowTool接口并注册到对应分类。29个工具覆盖矿池查询、订单、退款、算力、Skill SOP等场景。MCP工具通过McpToolAdapter动态接入，不需要改Java代码。

模型层扩展：LlmModelFactory通过routeSpec前缀（qwen:/deepseek:/ds:）路由到不同供应商，新增供应商只需加一个前缀判断。ConcurrentHashMap缓存模型实例，相同规格不重复创建。application.yml配置路由列表，热更新即可切换模型。

知识层扩展：Milvus向量库支持动态Collection切换，KB分块300字 + Rerank 16→4。Skill热插拔通过mall-admin REST API上传Markdown文件，10秒TTL自动生效，不需要重启服务。

💡 扩展性回答要分层次：工具/模型/知识三层各自怎么扩。面试官追问"加一个新工具多久"——回答：写一个AbstractWorkflowTool实现类 + 注册到Registry，半天能上线。
3. 如果让你重新设计这个系统，你会怎么改进？ 高频

三个改进方向：

1. 流式体验改进：当前是全缓冲模式（Reactor buffer + SSE一次性推送），用户要等完整答案才看到内容。改成增量流式——ReAct循环中每生成一个token就推给前端，用户体验更好。难点是质检纠错和流式的冲突（correct-on-fail模式下答案已经发出去了），需要改成先发占位+后发纠错的双段模式。

2. 多模型并行优化：当前ReAct循环是串行的（Thought→Action→Observation→下一轮），可以并行化——比如同时检索多个知识库、同时调用多个工具。但需要处理结果聚合和冲突仲裁。

3. 会话记忆增强：当前max-messages=12直接截断，长对话会丢失上下文。改成摘要+向量检索混合记忆——超过12轮时自动摘要前N轮，摘要存入向量库按需检索。这是V2规划。

💡 这题展示成长性。别说"我系统没问题"，要说"如果重来我会改X"——面试官想看你的反思能力。重点说"流式体验"和"记忆增强"，因为这是真实的痛点。
4. 为什么要做模型路由？直接用一个模型不行吗？ 高频

直接用一个模型的问题：成本和能力不匹配。矿池客服的问题分易/中/难三档，简单问题（如"怎么改密码"）用72B模型是浪费，难问题（如"退款流程异常排查"）用7B模型答不好。

我们的路由设计：application.yml配置了general路由列表 [qwen:qwen2.5-vl-72b-instruct, deepseek:deepseek-v3.2, qwen:qwen2.5-32b-instruct]。问题分类器（qwen2.5-7b-instruct）先判断难度，简单问题走缓存或小模型，难问题走大模型。LlmModelFactory根据routeSpec前缀创建对应供应商的OpenAI兼容实例。

路由还有一个关键作用：故障降级。主模型（72B）超时时自动降级到备用模型（32B/DeepSeek），保证服务可用。这是比"用一个模型"最大的优势——单模型挂了就全挂，多模型路由可以容灾。

# application.yml 模型路由配置
ai:
  routing:
    general:
      - qwen:qwen2.5-vl-72b-instruct    # 主模型（视觉+文本）
      - deepseek:deepseek-v3.2           # 备用1（推理强）
      - qwen:qwen2.5-32b-instruct        # 备用2（性价比）
  classifier-model: qwen2.5-7b-instruct  # 难度分类器
  normalize-question-model: qwen:qwen2.5-14b-instruct  # 问题归一化
💡 模型路由回答要点：成本优化 + 故障容灾 + 能力匹配。面试官追问路由策略——回答"按难度分类+故障自动降级"，不要说"轮询"或"随机"。
5. 你的系统支持哪些模型？怎么做模型适配的？

当前支持两类供应商：通义千问（DashScope）和DeepSeek。两者都提供OpenAI兼容接口，所以模型适配层很薄——LlmModelFactory内部用langchain4j的OpenAiChatModel/OpenAiStreamingChatModel，只改baseUrl和apiKey。

适配机制：routeSpec格式是供应商:模型名，如qwen:qwen2.5-vl-72b-instruct。LlmModelFactory解析前缀：qwen:走DashScope OpenAI兼容接口，deepseek:/ds:走DeepSeek API。每种路由规格创建两个实例——流式（temp=0.2, maxTokens=2000）用于实时对话，阻塞（temp=0.3, maxTokens=4096）用于问题归一化、质检评分等非实时任务。

新增供应商很简单：加一个前缀判断 + 对应的Properties配置类。因为都是OpenAI兼容协议，代码改动量极小。ConcurrentHashMap缓存保证相同规格不会重复创建模型实例。

// LlmModelFactory 路由解析
private static final String PREFIX_QWEN = "qwen:";
private static final String PREFIX_DEEPSEEK = "deepseek:";
private static final String PREFIX_DS = "ds:";
// 流式：temperature=0.2, maxTokens=2000
// 阻塞：temperature=0.3, maxTokens=4096, timeout=60s
💡 这题展示你对OpenAI兼容协议的理解。核心说"都是OpenAI兼容接口，适配层很薄"。追问"如果要接非OpenAI兼容的模型怎么办"——回答"包一层适配器，实现langchain4j的ChatLanguageModel接口"。
6. 如何设计Agent的错误恢复和重试机制？

错误恢复分三层：

1. 工具调用层：每个工具执行有try-catch，失败时返回错误信息作为Observation注入ReAct循环，让模型自己决定是否重试或换工具。不是简单的重试N次——而是让Agent感知到错误并自主决策。

2. 模型调用层：LlmModelFactory.streaming/blocking调用失败时，通过路由列表降级到下一个模型。比如72B超时就降级到DeepSeek V3.2，再失败降级到32B。blocking模型有60秒超时。当前是手写降级逻辑，没有用Resilience4j（V2规划）。

3. 整体兜底层：ReAct循环超过maxRounds=3仍未产出Final Answer时，走generateFallbackAnswer()——用当前chatHistory直接让模型生成一个答案，保证用户不会收到空响应。质检fail + correct-on-fail=true时还会基于KB重答一次。

💡 错误恢复的亮点是"让Agent自己感知错误"——不是机械重试，而是把错误信息喂给模型让它决策。这比"失败重试3次"高一个层次。
7. 你的系统支持多租户吗？怎么实现的？

当前版本未实现多租户。mall-ai是矿池客服的单一租户场景，所有用户共享同一套知识库和工具集。

面试回答策略：如果面试官追问，可以说"这是V2规划"，然后给出设计思路：

多租户的核心是数据隔离——KB向量库按tenantId分Collection，Redis会话key加tenantId前缀，工具注册表按tenantId隔离。LlmModelFactory的routeSpec可以按租户配置不同模型（大客户用72B，小客户用32B）。RateLimitFilter的限流维度天然支持按租户隔离（当前已按userId隔离，加一层tenantId即可）。

实现难点在于知识库隔离——Milvus的Collection有数量上限，租户多了需要做分库。以及计费——按租户统计Token消耗和工具调用次数。

💡 未实现的功能不要装作实现了。诚实说"当前未实现，V2规划"，然后展示你知道怎么做——数据隔离+模型路由+限流维度。面试官更看重你知道怎么做，而不是已经做了什么。
8. 你怎么看Agent架构的未来发展？

三个判断：

1. 单Agent → 多Agent协作：当前ReAct单Agent在简单场景够用，但复杂任务（如"帮我分析这个月矿池收益并给出优化建议"）需要检索Agent+分析Agent+报告Agent协作。MCP协议已经在标准化Agent间通信，类似HTTP标准化了服务间通信。

2. 确定性工作流 + 自主决策混合：纯ReAct太发散，纯工作流太死板。未来趋势是关键路径（退款、支付）用确定性工作流，非关键路径（闲聊、推荐）让Agent自主决策。我们的Skill SOP热插拔已经在往这个方向走——SOP注入给ReAct加了一层流程约束。

3. 长期记忆突破：当前max-messages=12截断太粗暴。未来会演进到结构化长期记忆——对话摘要 + 向量检索 + 实体图谱。让Agent"记住"用户的偏好和历史交互，不是每次从零开始。

💡 这题考视野。别说"AI要取代程序员"这种空话，要落到Agent架构的具体趋势：多Agent协作、混合工作流、长期记忆。每个都联系到你项目的现状和规划。

9. 熔断器是怎么实现的？三个状态是什么？ 高频

当前版本未实现正式熔断器（未引入Resilience4j），而是用手写的多模型降级机制替代。

面试回答策略：先说通用原理——熔断器三状态：Closed（正常，请求通过）、Open（熔断中，快速失败不调用下游）、Half-Open（半开，放少量请求探测恢复）。状态转换：连续失败N次 → Closed到Open；等待冷却时间 → Open到Half-Open；探测成功 → Half-Open到Closed；探测失败 → Half-Open到Open。

然后说项目现状：我们当前用LlmModelFactory的路由列表实现降级——主模型(72B)调用失败时降级到备用模型(DeepSeek V3.2/32B)。这相当于熔断器的"快速失败+切换"能力，但缺少自动恢复探测（Half-Open状态）。V2规划引入Resilience4j的CircuitBreaker，实现完整的三状态熔断。

// 通用熔断器三状态
Closed   --连续失败N次-->  Open    (快速失败，不调下游)
Open     --冷却时间到-->    Half-Open (放少量请求探测)
Half-Open --探测成功-->    Closed  (恢复正常)
Half-Open --探测失败-->    Open    (继续熔断)

// 项目当前替代方案：多模型降级
route: [72B → DeepSeek V3.2 → 32B]  // 主模型失败自动切下一个
💡 熔断器是高频题。先说三状态原理（展示知识面），再说项目用多模型降级替代（展示实战），最后说V2引入Resilience4j（展示规划）。不要装作用了Resilience4j。
10. 文档解析支持哪些格式？怎么处理表格和图片？

知识库文档当前以纯文本和Markdown为主。KB分块策略是300字/overlap=50，由KnowledgeBaseService处理。文档内容通过管理端上传后存入Milvus向量库（dimension=1024, text-embedding-v3）。

表格处理：当前对Markdown表格直接保留，分块时尽量不切断表格行。复杂的Excel/CSV表格需要预处理成Markdown或纯文本再入库。

图片处理：纯文本文档不含图片。但我们的主模型qwen2.5-vl-72b-instruct是视觉语言模型（VL），支持图片理解——如果用户在对话中发图片，模型可以识别。知识库中暂不支持图片向量化（这是V2规划，需要接入CLIP等多模态embedding）。

面试回答策略：诚实说"当前KB以文本为主"，然后展开"如果要支持复杂格式，会接入Apache Tika做文档解析 + CLIP做多模态embedding"。

💡 文档解析这题展示你对RAG数据管道的理解。核心说"当前以文本为主"，然后展开怎么做复杂格式。面试官想看你知道完整管道怎么设计，而不是你已经全做了。
11. 会话摘要压缩的阈值是多少？怎么确定的？

当前版本未实现会话摘要压缩。记忆策略是Redis存储 + max-messages=12，超过12条直接截断（保留最近12条用户+助手消息），不做摘要。

面试回答策略：先说现状"当前用简单截断，max-messages=12"，然后解释原因"矿池客服单次会话通常不超过8轮，12条够覆盖大多数场景，摘要压缩会增加一次LLM调用延迟和成本"。再说改进方向"如果会话变长，V2规划做摘要+向量检索混合记忆——超过12轮时自动摘要前N轮，摘要存入向量库按需检索，参考MemGPT的思路"。

通用原理：摘要压缩的阈值通常基于Token预算计算。假设总context window 8K tokens，System Prompt占800，RAG上下文占2000，工具结果占1000，留给对话历史约4200 tokens。按每轮对话~300 tokens算，约14轮就要触发摘要。我们设12条是留了安全余量。

💡 未实现不要装。说"当前截断，V2规划做摘要压缩"，然后展示你知道阈值怎么算——Token预算分配。这比"我们做了摘要"更有说服力。
12. 嵌入模型用的什么？维度多少？怎么选的？ 高频

用的是通义千问 text-embedding-v3，维度1024。配置在application.yml: qwen.embedding-model: text-embedding-v3，MilvusProperties默认dimension=1024。

选型考虑：①中文效果好——DashScope的embedding模型对中文FAQ类文档优化好，矿池客服场景中文为主；②维度适中——1024维在检索精度和存储/计算成本间平衡，768维可能丢信息，1536维成本高；③和主模型同一供应商——DashScope统一API管理，不用多一个供应商依赖。

Milvus向量库配置：MilvusEmbeddingStoreConfig创建collection时指定.dimension(1024)，索引用HNSW（Milvus默认）。检索时min-similarity=0.65，低于0.65的片段不召回。

# application.yml 嵌入模型配置
qwen:
  embedding-model: text-embedding-v3
  rerank-model: gte-rerank
# MilvusProperties.java
private int dimension = 1024;  // text-embedding-v3 默认 1024
💡 embedding选型是RAG基础题。回答要点：模型名+维度+选型理由（中文效果/维度权衡/供应商统一）。追问"为什么不用OpenAI的embedding"——回答"中文场景DashScope更好+不用翻墙+成本更低"。
13. 怎么做的日志和链路追踪？ 高频

链路追踪用TraceWebFilter——WebFlux过滤器，order=-100（最先执行）。从请求头X-Trace-Id提取traceId，没有则自动生成UUID。traceId注入MDC（SLF4J的Mapped Diagnostic Context），所有日志自动携带traceId。同步调用链（.block()）可复用MDC。

日志设计：关键节点都有info级别日志——ReAct每轮开始/结束、工具调用Action、质检评分结果、模型路由切换。日志格式：[traceId=xxx] ReAct round 1/3, Action: queryHashrate。质检评分日志带question摘要+分数+耗时ms。

当前未接入OpenTelemetry/SkyWalking（V2规划），但TraceWebFilter + MDC已经能覆盖单服务内的链路追踪需求。如果微服务化，需要把traceId通过HTTP头传递到下游服务。

// TraceWebFilter 核心逻辑
String traceId = request.getHeaders().getFirst("X-Trace-Id");
if (traceId == null || traceId.isBlank()) {
    traceId = UUID.randomUUID().toString();
}
MDC.put("traceId", traceId);  // 注入MDC，日志自动携带
// ... 业务逻辑 ...
MDC.clear();  // 出口清理
💡 日志追踪是工程化基本功。亮点是WebFlux + MDC + traceId，以及order=-100保证最先执行。追问"跨服务怎么办"——回答"traceId通过HTTP头传递 + 接入SkyWalking"。
14. 怎么做的异步并行处理？

异步并行体现在两个层面：

1. WebFlux + Reactor：全链路响应式，AiController用publishOn(Schedulers.parallel())把请求切到并行线程池，不阻塞Netty IO线程。SSE推送通过Flux<ServerSentEvent>异步发送。

2. 质检并行：QualityGate用CompletableFuture.supplyAsync()异步调用质检模型，不阻塞主对话流。质检模型（Qwen 72B）和主对话模型并行跑——用户收到答案的同时，质检在后台评分。如果质检fail且correct-on-fail=true，才触发重答流程。

// QualityGate 异步质检
QualityJudge.JudgeResult score = CompletableFuture
    .supplyAsync(() -> qualityJudge.judge(question, answer, kbContext))
    .get(timeoutSeconds, TimeUnit.SECONDS);  // 60秒超时

// AiController 响应式
.publishOn(Schedulers.parallel())  // 切到并行线程
.flatMap(response -> sendSse(response))
💡 异步处理的亮点是"质检不阻塞对话"——用户不用等质检完才收到答案。展示你理解Reactor的线程调度和CompletableFuture的异步编排。

26. Agent死循环怎么检测和防止的？ 高频

核心防线：maxRounds=3硬上限。ReActAgentService的递归调用executeReActRound()在round > maxRounds时直接走兜底——用当前chatHistory让模型生成Final Answer，不再进入Action循环。这是代码级硬限，不管模型怎么"想"调工具，3轮就是上限。

检测机制：每轮日志记录ReAct round {round}/{maxRounds} starting，可以监控到有没有频繁触发3轮兜底的session——这通常是知识库覆盖不够或工具能力不足导致模型反复尝试。

防止策略：①maxRounds=3硬限；②工具执行有try-catch，失败时返回错误Observation让模型换路径，不会无限重试同一个失败工具；③done标志位——模型输出Final Answer时done.set(true)，立即终止循环。

// 防死循环核心逻辑
if (round > maxRounds || done.get()) {
    return generateFallbackAnswer(chatHistory, route);
}
// done标志位在检测到Final Answer时设置
if (response.contains("Final Answer:")) {
    done.set(true);
}

ReAct循环中对模型输出格式有解析容错：

1. Action行解析：模型输出不一定严格按"Action: toolName Args: json"格式。解析器做了容错——用正则匹配Action行，提取工具名和参数。解析失败时返回错误Observation："无法解析Action，请按格式输出"，让模型下一轮修正。

2. Final Answer检测：检测"Final Answer:"关键字判断循环是否结束。如果模型3轮都没输出Final Answer，走兜底generateFallbackAnswer()——直接让模型基于chatHistory生成答案，不再要求ReAct格式。

3. 质检JSON解析：QualityJudge解析模型返回的JSON评分，用tolerant JSON parsing（jsonParse helper）处理模型常见的格式错误（多余逗号、引号缺失等）。解析失败时重试一次，仍失败给默认分数。

💡 格式异常处理的核心是"容错解析 + 错误反馈 + 兜底"。不要说"我们要求模型严格按格式输出"——LLM不会100%遵守格式。展示你理解模型输出的不确定性。

问题：用户收到SSE流式推送的答案后，质检才发现答案不合格（score<0.6）。答案已经发给用户了，怎么纠错？

解决过程：第一版方案是"质检不阻塞流式推送，纠错通过SSE correction事件下发"——用户先看到第一次答案（可能不准），然后看到纠错后的答案。体验不够好——等于承认"第一次答错了"。

最终方案：全缓冲模式。ReAct循环完整跑完后先做质检，质检pass直接SSE推送；质检fail且correct-on-fail=true时，先推送纠错后的版本。用户只看到一个答案。代价是首字延迟变高（要等完整ReAct+质检），但答案质量有保障。这是质量优先于速度的设计选择。V2计划改成增量流式+双段纠错来兼顾延迟和质量。

💡 最大挑战回答要点：具体的问题(流式和质检冲突) + 尝试的方案(SSE correction) + 最终方案(全缓冲+质检前置) + 设计权衡(质量vs速度)。
50. 这个项目的ROI是怎么计算的？

ROI计算分成本侧和价值侧：

成本侧：①开发成本——1人x3个月；②API成本——DashScope/DeepSeek按Token计费，日均调用量x单价；③基础设施成本——K8s+Redis+Milvus+MySQL月租。

价值侧：①人工客服工时节省——日均AI处理对话数 x 单次人工成本 x 365天；②夜间覆盖——从0到100%，避免夜间用户流失；③质检一致性——减少人工质检工时。

51. Embedding模型是怎么训练的？对比学习怎么做的？

Embedding模型训练的核心是对比学习（Contrastive Learning）：

1. 训练目标：让语义相似的文本对在向量空间中距离近，不相似的对距离远。损失函数用InfoNCE：让正样本对相似度尽可能高，负样本对相似度尽可能低。

2. 正样本构造：①同一文档不同段落；②问答对（问题和答案互为正样本）；③数据增强——同义词替换/回译。text-embedding-v3用了大量中文问答对训练，所以中文FAQ检索效果好。

3. 负样本构造：①Batch内负采样——同batch其他样本作为负样本；②困难负样本——和正样本主题相关但答案不同的样本（如"怎么改密码" vs "密码忘了怎么办"），让模型学细微差异。困难负样本比随机负样本效果显著提升。

我们的项目不自己训练embedding——直接用DashScope text-embedding-v3（1024维），已在海量中文语料上预训练好。

💡 回答要点：对比学习 + InfoNCE损失 + 正负样本构造（困难负采样是亮点）。追问"为什么不自己训练"——"预训练模型效果够用+需要大量标注数据+算力成本"。
52. Prompt Engineering有哪些关键技巧？

结合项目实践的Prompt技巧：

1. 结构化Prompt：ReAct Prompt用硬编码text block，包含角色定义、工具列表、输出格式、Few-shot示例。结构清晰——System Prompt + ReAct格式说明 + 工具描述 + 历史 + 当前问题。

2. 输出格式约束：明确要求"Thought: ... Action: toolName Args: {...}"格式。LLM不100%遵守，所以解析器要容错。但格式约束越明确，模型遵守率越高。

3. Few-shot示例：在Prompt中给1-2个ReAct对话示例，模型更容易理解"思考->行动->观察->答案"循环。比纯文字描述有效。

4. Skill SOP注入：命中Skill后把SOP流程注入Prompt——"处理退款时按以下步骤：1.验证订单->2.检查退款条件->3.执行退款->4.通知用户"。这是流程约束Prompt——让Agent按SOP走，不自由发挥。

5. 温度控制：流式temp=0.2（低发散，适合客服回答），阻塞temp=0.3（稍高，适合问题归一化和质检评分）。温度是Prompt Engineering的"调节旋钮"。

💡 回答要点：结构化 + 格式约束 + Few-shot + SOP注入 + 温度控制。亮点是"SOP注入"——项目特有的Prompt技巧，不是通用八股。
