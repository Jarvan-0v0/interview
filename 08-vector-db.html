CHAPTER 07

向量数据库与 Embedding

🎯 学习目标：理解Embedding的本质（文本→高维向量的语义映射）与向量相似度计算（余弦/欧氏/点积），掌握ANN近似最近邻搜索（HNSW/IVF/PQ）解决暴力搜索性能问题，能对比Milvus/Pinecone/Chroma/Qdrant/Weaviate/pgvector做技术选型，并结合langchain4j的EmbeddingStore接口说清向量库的工程用法。

向量数据库 = 专门存高维向量并按"语义距离"做检索的存储引擎——不是替代MySQL，而是为"语义相似查询"这种传统数据库做不了的场景而生。

1. Embedding的本质 ★★★★★ 必考

Embedding（嵌入）是把文本映射成高维浮点向量（如768维、1536维）的过程，核心思想是：语义相近的文本，向量距离也近。这样"语义相似度"就变成了可计算的"向量距离"。

Embedding做了什么

  • 输入：一段文本（如"如何申请退货"）
  • 输出：一个固定长度的浮点数组，如 [0.023, -0.187, 0.541, ..., 0.082]（768个数）
  • 性质：语义相近的文本 → 向量在空间中离得近；语义无关 → 离得远
图7-1 Embedding语义空间示意：语义相近的文本聚成一簇，查询点落在哪个簇就能召回该簇的文档（注：真实向量是768+维，这里降维到2维仅作示意）
Embedding ≈ 带语义距离的HashMap。普通HashMap的hash只用来定位bucket，两个hash值接近毫无语义含义；而Embedding把文本映射到向量空间后，向量距离是有语义含义的——距离近=语义近。可以说Embedding是"保留了语义结构的hash映射"。
关键认知：真实向量是几百上千维的浮点数组，无法直接画出来。上图把768维降维到2维只是为了直观展示"语义相近=距离近"这个性质，不代表真实分布。

2. 向量相似度计算 ★★★★☆

有了向量，怎么算"相近"？有三种主流度量，面试要能写出公式并讲清差异。

度量公式关注点适用场景
余弦相似度
Cosine Similarity		 cos(A,B) = (A·B) / (|A|×|B|) 方向（夹角），不看大小 文本检索最常用，只关心语义方向
欧氏距离
Euclidean		 d = √Σ(Aᵢ-Bᵢ)² 绝对位置（直线距离） 图像特征、点云等
点积
Dot Product		 A·B = Σ Aᵢ×Bᵢ 方向+大小（向量未归一化时） 向量已归一化时等价于余弦，速度快
图7-2 三种相似度度量的几何含义：余弦看夹角、欧氏看直线距离、点积看投影累加

为什么文本检索多用余弦相似度

文本Embedding后，向量的模长（长度）往往受文本长度、措辞等影响，而方向才代表语义。余弦相似度只看夹角不看模长，能屏蔽"长短不一"的干扰，更纯粹地反映语义相似度。很多Embedding模型在输出前就做了L2归一化（把向量长度统一为1），此时点积=余弦，算得更快。

余弦相似度的公式与计算示例

数学公式：两个向量 A、B 的余弦相似度 = 它们的点积除以各自模长的乘积：
cos(A, B) = (A · B) / (||A|| × ||B||) = Σ(Aᵢ × Bᵢ) / (√ΣAᵢ² × √ΣBᵢ²)
其中 A·B 是点积（对应位相乘再求和），||A|| 是A的L2范数（各维度平方和开根号）。取值范围 [-1, 1]：1 表示方向完全相同（语义最相近），0 表示正交（语义无关），-1 表示方向相反（语义对立，实际文本中罕见）。

计算示例：假设3维向量 A = [3, 4, 0]（如"如何申请退货"的embedding简化），B = [4, 5, 0]（如"退款流程是什么"）。
① 点积 A·B = 3×4 + 4×5 + 0×0 = 12 + 20 + 0 = 32
② ||A|| = √(3²+4²+0²) = √25 = 5；||B|| = √(4²+5²+0²) = √41 ≈ 6.40
③ cos(A,B) = 32 / (5 × 6.40) = 32 / 32.0 = 1.0
两个向量方向几乎一致（夹角≈0°），说明"如何申请退货"和"退款流程是什么"语义高度相似，会被向量检索召回为Top结果。

对比无关文本：若 C = [0, 0, 5]（如"今天天气真好"）。A·C = 3×0+4×0+0×5 = 0，cos(A,C) = 0 / (5×5) = 0。两向量正交，语义无关，不会召回——这正是余弦相似度"只看方向不看大小"的价值：即使C的模长和A一样大，方向不同就判为不相关。

图7-5 余弦相似度几何图解：左图两向量夹角≈0°(方向一致,cos≈1,语义相似召回) / 右图两向量正交θ=90°(cos=0,语义无关不召回)
相似度计算 ≈ Comparator的compare实现。向量库本质是给每个查询向量找出"排序后Top-K"的元素，和SQL的ORDER BY+LIMIT思想一致——只不过排序键从标量变成了"向量距离"这个特殊比较函数。

3. ANN 近似最近邻搜索 ★★★★☆

有了一堆向量，怎么找出和查询向量最相近的Top-K？最朴素的做法是暴力搜索：和库里每个向量都算一遍相似度，排序取Top-K。问题是——库里有上亿条向量时，每次查询都算上亿次，O(N)复杂度根本扛不住。

暴力搜索的痛点：1000万条向量、每次查询算1000万次相似度，单次查询几百毫秒到秒级，高并发下数据库直接被打爆。必须用索引加速——这就是ANN算法要解决的问题。

ANN（Approximate Nearest Neighbor，近似最近邻）的核心思路：牺牲一点精度换取巨大速度提升。不要求100%精确，只要recall（召回率）够高（如95%），但速度能快几个数量级。三种主流算法：

HNSW 算法的分层图原理详解

HNSW（Hierarchical Navigable Small World，分层可导航小世界图）的核心思想是"空间换时间+分层导航"。它把所有向量组织成一张多层图结构，每层都是一个"小世界图"——节点之间用边连接，相邻向量之间有边。关键是层级越往上，节点越稀疏、边越长（连接距离远的节点）；层级越往下，节点越密集、边越短（只连接近邻）。插入节点时，先用指数衰减概率决定它最高出现在哪一层（大部分节点只在最底层），顶层节点是"长距离高速公路"。

查询流程：从最高层的入口节点出发，先在稀疏层利用长距离边大步跳到查询向量附近的区域（粗定位），然后下沉到下一层，在更密的图里做更精细的局部搜索（逼近），逐层下沉直到最底层（密集层），在邻域内做最终的精确排序返回Top-K。整个过程像地图导航：先上高速走大方向→下省道缩小区间→最后县道精确定位。由于每层只访问少量节点（图搜索的局部性），总访问数远小于暴力搜索的N，复杂度接近 O(logN)。

为什么快、代价是什么：快的原因有二：①分层结构让搜索"先粗后细"，避免在最密的底层从头遍历；②小世界图的特性是任意两节点间只需少量跳数即可到达（六度分隔理论），即使上亿节点，平均跳数也是对数级。代价是内存占用大——要存所有层的图结构（节点+邻接表），且建图是增量的、插入慢。所以 HNSW 适合内存充足、追求查询速度的中小到中大规模场景；超大规模（十亿级）常和 IVF/PQ 组合，用 IVF 分桶缩小搜索范围、桶内再用 HNSW 加速。

图7-4 HNSW分层图结构：顶层稀疏长距离(粗定位) → 中层过渡 → 底层密集全量数据(精排Top-K)，逐层下沉收敛

工程实战：组合使用 IVF + PQ

Milvus等向量库常用IVF+PQ组合：先用IVF聚类缩小搜索范围（粗筛），再用PQ压缩向量减少内存和计算（精算）。还可以在IVF内部套HNSW加速簇内搜索。面试提到"组合索引"会显得懂工程优化。

ANN ≈ 数据库索引（B+Tree）的思想。B+Tree用空间换时间——建索引慢、占空间，但查询从O(N)降到O(logN)。ANN索引同理：建库时要先构建HNSW图/IVF聚类（慢、占内存），但查询从O(N)降到O(logN)级别。都是"预计算结构+牺牲空间+近似换取速度"。

3.5 为什么不用 MySQL 直接做向量检索 ★★★★☆

这是Java后端转AI Agent的同学最容易问的问题——"我已经有MySQL了，为什么还要引入Milvus/pgvector这种新组件？把向量塞进MySQL的一列不就行了？"答案是：MySQL在架构上就不是为高维向量距离检索设计的，硬做会在三个层面撞墙。

第一堵墙：没有原生的向量索引。MySQL的B+Tree索引、Hash索引、全文索引，都是为标量精确匹配或范围查询设计的——WHERE id=123、WHERE age BETWEEN 20 AND 30。但向量检索是"给一个768维的查询向量，找出和它余弦相似度最高的Top-K"——这是一个高维空间的距离排序问题，B+Tree根本无法索引（高维距离没有单调性，无法用区间剪枝）。MySQL最多能用全文索引做关键词匹配，但关键词匹配不懂语义：用户问"怎么退款"，文档里写的是"退货政策"，LIKE和MATCH都召回不了，而向量检索能识别它们语义相近。

第二堵墙：暴力全表扫描的O(N)性能灾难。如果硬把768维向量存进MySQL的BLOB/JSON列，查询时只能"SELECT出所有行 → 在应用层逐行算余弦相似度 → 排序取Top-K"。这是O(N)复杂度，N=百万级时单次查询就要扫百万行+算百万次768维点积，耗时秒级；N=千万级直接不可用。专业向量库靠ANN索引（HNSW/IVF）把复杂度压到O(logN)，同样千万级数据查询只要毫秒——差距是几个数量级。这就像用MySQL的COUNT全表扫来做计数 vs 用Redis的INCR，技术上能做，但工程上不可接受。

第三堵墙：缺乏向量计算的原语和优化。专业向量库在底层做了大量向量计算优化——SIMD指令集并行计算、批量矩阵乘法、GPU加速、量化压缩（PQ）减少内存带宽瓶颈。MySQL完全没有这些，每个维度的乘加都要逐条记录逐字段处理，效率天差地别。打个比方：这就像用通用HashMap做图算法——能存数据但没图的遍历原语，每一步都要自己手写循环，既慢又易错。

折中方案与选型建议：如果公司已有PostgreSQL且数据量不大（百万级），pgvector是最佳折中——它是PG的扩展插件，带HNSW/IVFFlat索引、SQL原生查询（ORDER BY embedding <-> '[0.1,...]' LIMIT 5），复用现有DBA和运维，无需引入新组件。MySQL 8.x虽然也开始加向量类型，但索引能力、生态成熟度远不及pgvector。规模再大（千万到亿级）就必须上Milvus这类专业分布式向量库了——就像全文检索量大了要上ES一样，是"专用工具做专用的事"的工程常识。

为什么不用MySQL做向量检索 ≈ 为什么不用MySQL做全文检索而要上ES。MySQL的LIKE能做简单搜索，但量一大、相关性排序要求一高，就得用专门的Elasticsearch（倒排索引+TF-IDF/BM25）。同理，向量语义检索量大、要ANN加速，就得用专业向量库或pgvector。都是"通用DB不够用→上专用引擎"的经典演进。
面试加分点：能补一句"pgvector和Milvus不是对立的——pgvector适合已有PG、数据量百万级、想低成本接入；Milvus适合从0搭建、千万到亿级、要分布式"，体现你懂按场景选型而非一概而论。

4. 向量数据库对比选型 ★★★★★ 必考

向量数据库不止一家，面试常问"你怎么选"。要能从部署方式、性能、生态、Java友好度等维度对比。

数据库部署方式语言/实现Java生态特点适用场景
Milvus 自托管/云托管 Go/C++ SDK好 分布式、高性能、索引类型全、支持十亿级 企业级生产首选，Java后端友好
Pinecone 全托管SaaS 闭源 HTTP API 零运维、自动扩缩、稳定 不想运维、海外业务、快速验证
Chroma 嵌入式/本地 Python 弱 轻量、开发友好、Python原生 原型开发、Demo、小数据量
Qdrant 自托管/云 Rust HTTP API Rust写的高性能、内存效率高、过滤强 追求性能、过滤条件复杂
Weaviate 自托管/云 Go HTTP API GraphQL接口、内置模块化向量化 喜欢GraphQL、一站式
pgvector PostgreSQL扩展 C/SQL JDBC原生 复用PG生态、SQL查询、IVFFlat/HNSW索引 已有PG、不想引入新组件

选型决策树

  • 已有PostgreSQL且数据量不大（百万级） → pgvector，复用现有DBA和运维，SQL原生
  • 企业级生产、千万到亿级、需分布式 → Milvus，Java SDK成熟
  • 不想运维、海外业务 → Pinecone，全托管省心
  • 追求极致性能、过滤条件多 → Qdrant，Rust内存效率高
  • 快速原型/Demo → Chroma，几行代码跑起来
向量库选型 ≈ 选消息队列。Kafka（Milvus，重量级但能扛大规模）、RabbitMQ（Chroma，轻量友好）、Redis Stream（pgvector，复用现有组件）——根据规模、运维能力、生态需求选，没有银弹。
国内Java后端转Agent，Milvus和pgvector是重点。Milvus适合从0搭建的大规模场景；pgvector适合公司已有PG、想低成本接入向量检索的场景。两者面试都要能讲清。

5. langchain4j 中的向量存储

langchain4j抽象了统一的 EmbeddingStore 接口，屏蔽底层是Milvus/PgVector/Chroma的差异，切换成本极低。

Java · langchain4j EmbeddingStore 用法 
// 1. 创建Embedding模型（离线建库和在线检索必须用同一个）
EmbeddingModel embeddingModel = new BgeSmallZhEmbeddingModel();  // 768维，中文友好

// 2. 创建向量存储——以Milvus为例
EmbeddingStore<TextSegment> store = MilvusEmbeddingStore.builder()
    .host("localhost")
    .port(19530)
    .collectionName("kb_docs")
    .dimension(768)                  // 必须和Embedding模型维度一致
    .indexType(IndexType.IVFFLAT)   // ANN索引类型
    .metricType(MetricType.COSINE)  // 相似度度量
    .build();

// 3. 离线：把文档分块后向量化并入库
TextSegment segment1 = TextSegment.from("退货政策：7天内可无理由退货...");
Embedding emb1 = embeddingModel.embed(segment1).content();  // 文本→向量
store.add(emb1, segment1);   // 向量+原文一起存

// 4. 在线：用户提问→向量化→检索Top-K
Embedding queryEmb = embeddingModel.embed("怎么退货").content();
List<EmbeddingMatch<TextSegment>> matches = store.findRelevant(
    queryEmb,
    5,          // maxResults: Top-5
    0.7         // minScore: 相似度阈值
);

// 5. 拼成context给LLM
String context = matches.stream()
    .map(m -> m.embedded().text())
    .collect(Collectors.joining("\n---\n"));
// 再把context塞进Prompt调LLM——见第6章RAG
踩坑点：① 维度必须一致——换Embedding模型导致维度变了，旧库数据全部作废要重建。② minScore阈值要调——太高召回少、太低混入噪声，需结合语料A/B测。③ 索引类型在建表时定，建好后再改要重建索引。
EmbeddingStore接口 ≈ JDBC的DataSource。上层代码只面向接口编程，底下接MySQL/PG/Oracle都行。langchain4j同理——业务代码面向EmbeddingStore，底下Milvus/PgVector/Chroma无缝切换，这就是抽象的力量。

面试场景演练

Q1：向量检索的原理是什么？

分三步：①离线用Embedding模型把文档映射成高维向量存入向量库；②在线用同一个Embedding模型把用户问题也映射成向量；③在向量库里按相似度度量（一般用余弦相似度）算查询向量和所有文档向量的距离，取Top-K最相近的返回。

底层靠的是"语义相近的文本向量距离也近"这个性质，本质是把"语义匹配"问题转化成了"向量距离计算"问题。

关键词："同一个Embedding模型""语义相近=距离近""余弦相似度Top-K"。能补一句"这和HashMap不同——hash值相近没语义，向量距离近是有语义的"会显得理解到位。
Q2：HNSW算法是什么？

HNSW（Hierarchical Navigable Small World，分层可导航小世界图）是一种ANN近似最近邻索引算法。它把向量组织成多层图结构：上层节点稀疏、连接长距离，下层节点密集、连接短距离。查询时从顶层入口节点开始，利用长距离边快速跳到目标区域附近，再逐层下沉到密集层做精细搜索，像走高速公路→省道→县道逐级收敛。

优点是召回率高、查询快（接近O(logN)）；缺点是建图慢、内存占用大（要存图结构）。适合中小规模、追求速度的场景，Milvus/Qdrant默认推荐的就是HNSW。

类比"地图导航：高速→省道→县道逐级下沉"特别好记。能再补一句"内存大是它的代价，超大规模时会和IVF+PQ组合"就是高手答法。
Q3：Milvus和Pinecone怎么选？

Milvus是开源、可自托管的分布式向量库，Java SDK成熟、索引类型全、支持十亿级规模，适合企业级生产、对数据主权敏感、有运维团队的场景，国内Java后端首选。Pinecone是全托管SaaS，零运维、自动扩缩容、稳定，适合不想碰运维、海外业务、快速验证的场景，缺点是闭源、数据要出本地、按用量付费成本可能高。

决策点：数据量小且要快上线→Pinecone；企业级大规模、数据不出本地、Java生态→Milvus。我项目里选Milvus，因为公司数据合规要求私有化部署，且Java SDK好对接现有Spring Boot技术栈。

关键差异是"自托管 vs 全托管"。结合"数据合规、Java生态、运维能力"三点讲选型理由，体现你懂工程权衡而非盲选。
Q4：为什么不用MySQL直接做向量检索？

核心原因是MySQL没有原生的向量索引和距离计算能力。用MySQL做向量检索只能用LIKE或全文索引做关键词匹配，做不了语义相似——"退款"和"退货"LIKE匹配不到，但向量检索能召回。即使把向量存进MySQL，也只能全表扫描算距离，O(N)复杂度，上百万条就慢得不可用。

两个折中方案：①用pgvector——给PostgreSQL加向量扩展，带HNSW/IVFFlat索引，SQL原生查询，适合已有PG、数据量不大的场景；②MySQL自己也在8.x加向量类型，但生态和索引能力远不如专业向量库。大规模语义检索还是得上Milvus这类专业组件。

答到"MySQL做不了语义相似，只能关键词匹配"是核心。再补"pgvector是折中、大规模上专业向量库"就完整了。类比"用MySQL做全文检索要上ES"——Java工程师秒懂。
  • Embedding本质：文本→高维向量，语义相近=距离近，是"保留语义结构的hash映射"
  • 相似度三度量：余弦(看方向，文本最常用) / 欧氏(看直线距离) / 点积(归一化后等价余弦，最快)
  • 暴力搜索O(N)扛不住，ANN牺牲精度换速度：HNSW(图分层导航) / IVF(聚类倒排) / PQ(分段量化压缩)
  • 工程常用IVF+PQ组合：IVF粗筛+PQ压缩精算，兼顾速度和内存
  • 向量库选型：Milvus(企业级、Java友好) / Pinecone(全托管) / Chroma(原型) / Qdrant(高性能) / Weaviate(GraphQL) / pgvector(复用PG)
  • Java后端重点：Milvus(大规模新建) 和 pgvector(已有PG、低成本接入)
  • langchain4j的EmbeddingStore≈JDBC的DataSource，面向接口编程，底层库无缝切换
  • 关键约束：离线建库和在线检索必须用同一个Embedding模型，换模型=全部重新入库
