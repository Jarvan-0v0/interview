第02章

常用中间件

学习目标：掌握4年后端开发常用的中间件核心原理和面试高频考点——Redis、消息队列(Kafka/RabbitMQ)、搜索引擎(Elasticsearch)、注册中心/配置中心(Nacos)、分布式协调(Zookeeper)。这些是Java后端的基本盘，面试官会用来验证你的工程深度。

一、Redis ⭐⭐⭐ 必考

Redis是面试中出场率最高的中间件，没有之一。几乎每个Java后端面试都会深入问Redis。

Redis = 内存数据库 + 单线程 + IO多路复用，快不是因为单线程，而是因为纯内存操作+避免锁竞争+epoll。

1.4 分布式锁

Java (Redisson实现分布式锁) 
// SET key value NX PX 30000 — 原子性加锁+设置过期
RLock lock = redissonClient.getLock("order:lock:" + orderId);
try {
    // 尝试加锁，等待5秒，锁30秒自动释放
    boolean locked = lock.tryLock(5, 30, TimeUnit.SECONDS);
    if (!locked) {
        throw new RuntimeException("获取锁失败");
    }
    // 业务逻辑
    doBusiness();
} finally {
    // Redisson会检查是否是自己加的锁再释放(防误删)
    lock.unlock();
}

Redisson分布式锁的几个关键设计：

  • 加锁原子性：SET key value NX PX 30000，一步完成加锁+设过期
  • 防误删：value存唯一UUID，释放锁时先检查是不是自己的锁
  • 锁续期(看门狗)：如果业务执行超过30秒，看门狗线程每10秒续期
  • 可重入：用Hash结构记录重入次数，同一线程可多次获取
SETNX + EXPIRE 两步操作不是原子的！如果SETNX成功后EXPIRE前宕机，锁就永远不释放了。必须用SET key value NX PX 30000一步到位，或用Lua脚本。

二、消息队列 (Kafka / RabbitMQ) ⭐⭐⭐ 必考

消息队列是后端系统解耦、异步、削峰的核心中间件。Kafka和RabbitMQ的选型是面试高频题。

Kafka = 日志系统(高吞吐、顺序、流式)，RabbitMQ = 消息代理(灵活路由、可靠投递)。

2.1 Kafka vs RabbitMQ 选型

对比维度KafkaRabbitMQ
定位分布式流处理平台(日志/事件)传统消息代理(AMQP协议)
吞吐量⭐ 百万级TPS，顺序写磁盘+零拷贝万级TPS
延迟毫秒级微秒级(更低)
路由弱(Topic/Partition)⭐ 强(Exchange+Routing Key多种模式)
消息可靠ack+副本，可能重复⭐ 更强(ACK机制+事务消息)
消息顺序⭐ Partition内有序单队列有序
消费模式拉取(Pull)推(Push)/拉(Pull)
适用场景日志收集、大数据流、事件溯源业务消息、任务分发、RPC

2.2 Kafka核心架构

Kafka架构：Producer → Topic(多Partition) → Consumer Group并行消费，ZK/KRaft协调

2.3 Kafka关键机制

  • Partition(分区)：Topic分成多个Partition，实现水平扩展。Partition内消息有序，跨Partition无序
  • Offset(偏移量)：Consumer记录自己消费到哪个位置，支持断点续消费
  • Consumer Group：同组内每个Consumer消费不同Partition（实现并行），不同组各自独立消费全量
  • 副本机制：每个Partition有Leader+Follower副本。Leader处理读写，Follower同步。Leader挂了选新Leader
  • ISR (In-Sync Replicas)：和Leader保持同步的副本集合。只有ISR中的副本才有资格被选为新Leader
  • acks参数：acks=0不等确认 / acks=1 Leader确认(默认) / acks=all 所有ISR确认(最安全)

2.4 消息可靠性三保证

环节可能丢失保证措施
生产端网络中断、Leader切换acks=all + 重试 + 幂等生产
Broker端磁盘损坏、Broker宕机副本机制(多副本) + ISR + min.insync.replicas≥2
消费端提交了offset但没处理完手动提交offset(处理完再提交)
Kafka消息可靠性 ≈ Java事务的ACID：acks=all ≈ WAL日志持久化，副本机制 ≈ 主从同步，手动提交offset ≈ 手动提交事务(而非自动提交)。

三、Elasticsearch ⭐⭐ 中高频

Elasticsearch(ES)是分布式搜索引擎，在日志分析、全文检索场景面试常问。和RAG的向量检索有对比价值。

ES = 倒排索引 + 分布式 + 近实时，核心是把"找包含某个词的文档"从O(N)降到O(1)。

3.1 倒排索引

传统正排索引：文档 → 包含哪些词。倒排索引反过来：词 → 出现在哪些文档。

词项(Term)文档列表(Posting List)词频(TF)
AI[doc1, doc3, doc5]doc1:3次, doc3:1次, doc5:2次
Agent[doc1, doc2]doc1:2次, doc2:1次
Java[doc2, doc3, doc5]doc2:3次, doc3:1次, doc5:5次

搜索"AI Agent"时：先从倒排索引找到"AI"和"Agent"各自的文档列表，求交集[doc1]，按相关度打分排序返回。

3.2 ES核心概念

  • Index(索引) ≈ MySQL的数据库，存储相关文档的集合
  • Document(文档) ≈ MySQL的一行记录，JSON格式
  • Mapping(映射) ≈ MySQL的表结构，定义字段类型和分析器
  • Shard(分片)：索引分成多个分片分布在不同节点，实现水平扩展
  • Replica(副本)：每个分片有副本，保证高可用

3.3 ES vs MySQL vs 向量检索

对比MySQLElasticsearch向量检索(Milvus)
索引结构B+树倒排索引HNSW/IVF
检索方式精确匹配/范围全文检索(关键词)语义相似(向量近邻)
擅长结构化查询"包含某个词的文档""语义相近的文档"
搜索"苹果手机"LIKE '%苹果手机%'(差)分词匹配"苹果"+"手机"(好)理解语义(最好)
实时性强实时近实时(1秒刷新)近实时
ES做的是"关键词匹配"，向量检索做的是"语义匹配"。RAG场景用向量检索更好，但ES的BM25可以和向量检索混合使用，效果更佳——这就是混合检索。

四、Nacos (注册中心+配置中心) ⭐⭐ 中频

Nacos = Naming and Configuration Service，阿里开源，微服务架构标配。

4.1 注册中心

  • 服务提供者启动时注册到Nacos，消费者从Nacos获取服务列表
  • 心跳检测：5秒上报，15秒标记不健康，30秒摘除
  • 两种模式：AP(默认，临时实例) vs CP(持久实例，需Raft共识)
注册中心 ≈ Java的ServiceLoader SPI机制，但加了网络通信、心跳健康检查、服务发现动态更新。

4.2 配置中心

  • 集中管理所有微服务的配置，支持热更新(@RefreshScope)
  • 配置变更后推送通知，服务自动拉取新配置
  • 命名空间(Namespace) + Group + DataId 三级隔离
Nacos的AP和CP模式有什么区别？什么时候用哪个？

AP模式(默认)：服务挂了立即从列表摘除，保证可用性但可能短暂不一致。适合临时实例(如SpringCloud服务)，因为服务本来就需要心跳维持。

CP模式：服务挂了不立即摘除，需Raft共识。适合持久实例(如Kafka Broker、数据库)，这些服务挂了不应该自动删除注册信息。

选择原则：需要高可用选AP(大部分微服务)，需要强一致选CP(有状态服务)。

提到CAP理论，说明你知道分布式系统的本质权衡。再提一句"大部分微服务用AP就够了"展示工程判断。

五、ZooKeeper ⭐⭐ 中频

ZooKeeper是分布式协调服务，Kafka(旧版)、Dubbo注册中心、分布式锁都用它。

5.1 核心概念

  • ZNode：树状结构的数据节点，类似文件系统路径
  • 持久节点 vs 临时节点：临时节点在会话断开后自动删除(用于服务注册)
  • 顺序节点：节点名自动加序号(用于分布式锁公平排队)
  • Watcher监听：节点变化时通知客户端(服务上下线感知)

5.2 典型应用

  • 分布式锁：创建临时顺序节点，序号最小的获取锁，后面的监听前一个节点
  • 服务注册发现：服务启动创建临时节点，消费者监听节点变化
  • Leader选举：多个节点创建同一节点，创建成功的为Leader
  • 配置管理：配置存在ZNode上，监听变化通知更新
ZooKeeper的ZAB协议不是Raft！虽然都是共识算法，但ZAB是原子广播(Primary-Backup)，Raft是日志复制。面试别说混。

🎤 面试实战

Redis为什么快？单线程为什么也快？

Redis快的原因：1）纯内存操作，数据在内存中读写，没有磁盘IO；2）单线程+IO多路复用，epoll实现一个线程处理大量连接，避免多线程的锁竞争和上下文切换；3）数据结构高度优化，如SDS预分配、ziplist压缩、跳表等。

单线程也快是因为：瓶颈不在CPU计算，而在IO。单线程+epoll = 没有锁开销 + 高效IO，反而比多线程更快。而且Redis 6.0引入多线程处理IO，命令执行仍单线程。

提到Redis 6.0多线程IO是加分项。能说"瓶颈不在CPU"说明理解了本质。
缓存穿透怎么解决？布隆过滤器原理是什么？

缓存穿透就是查询一个数据库里根本不存在的key，Redis查不到就去查DB，DB也没有，大量这样的请求会压垮DB。

解决方案：1）缓存空值——查不到也缓存null并设短TTL；2）布隆过滤器——在Redis前面加一层过滤，判断key"可能存在"还是"一定不存在"。

布隆过滤器原理：用多个哈希函数把存在的key映射到bit数组的多个位置(置1)。查询时，如果所有哈希位置都是1，则"可能存在"；如果有任何一个位置是0，则"一定不存在"。它有误判率(假阳性)，但不能漏判。

能说出"可能存在"和"一定不存在"这个特性，就说明理解了布隆过滤器的核心。提到误判率可调(数组大小+哈希函数数量)更佳。
Redisson分布式锁是怎么实现的？有什么问题？

Redisson分布式锁用Lua脚本实现原子操作：SET key value NX PX 30000，value存唯一UUID防误删。核心机制：1）看门狗定时续期防止业务没执行完锁就过期；2）用Hash结构记录线程ID和重入次数实现可重入；3）释放锁用Lua脚本判断UUID+删除。

问题：1）时钟漂移——如果某台Redis服务器时间跳变，锁可能提前或延后过期；2）主从切换丢锁——master加锁后还没同步到slave就宕机，新master没有锁信息。

要彻底解决用RedLock算法(Redlock)，或者用ZooKeeper实现(CP保证一致性)。

提到"主从切换丢锁"和"RedLock"说明你对Redis分布式锁的局限有深入理解。但要补一句"实际生产中Redisson够用了，不用过度设计"。
Kafka为什么吞吐量这么高？

Kafka高吞吐的原因：1）顺序写磁盘——消息追加到Partition末尾，磁盘顺序写速度接近内存写；2）零拷贝(Zero Copy)——用sendfile直接从页缓存到网卡，不经过用户态；3）批量处理——生产者批量发送+压缩，消费者批量拉取；4）Partition分区并行——多Partition分散到多个Broker，水平扩展。

核心就是：把磁盘当顺序日志用 + 绕过用户态拷贝 + 批量+分区并行。

"顺序写磁盘接近内存速度"这个知识点是Kafka面试的金牌答案。再提零拷贝(sendfile)说明你理解OS层面优化。
如何保证Kafka消息不丢？

三个环节都要保证：1）生产端——acks=all + retries重试 + 幂等生产，确保消息到Broker；2）Broker端——副本机制(min.insync.replicas≥2) + ISR机制，确保即使Leader宕机消息也不丢；3）消费端——关闭自动提交offset，业务处理完再手动提交。

注意acks=all会降低吞吐量，需要根据业务权衡可靠性和性能。

分三端回答是最清晰的框架。提到"手动提交offset而非自动"说明你踩过坑。
ES的倒排索引和MySQL的B+树有什么区别？和向量检索呢？

B+树是正排索引——从主键找记录，擅长精确匹配和范围查询。倒排索引反过来——从词找文档列表，擅长全文检索。搜索"AI Agent"，ES分词后找"AI"和"Agent"各自的倒排表求交集，O(1)级别。MySQL只能LIKE '%AI Agent%'做全表扫描O(N)。

但ES做的是关键词匹配，不理解语义。向量检索(如Milvus)把文本变成向量，找语义最相近的。搜"人工智能代理"也能匹配到"AI Agent"的内容，因为语义相近。RAG场景用向量检索更好，但BM25(ES)和向量混合检索效果最佳。

能对比三种索引(B+树/倒排/HNSW)是高级表现。提到"混合检索"直接联系到RAG场景，展示你能把中间件知识和Agent开发关联起来。
Kafka和RabbitMQ怎么选？

看场景：要高吞吐、大数据流处理、日志收集、事件溯源——选Kafka，百万级TPS不是RabbitMQ能比的。要灵活路由、消息可靠投递、任务分发、小规模系统——选RabbitMQ，它的Exchange(4种路由模式)更灵活，延迟更低。

简单记忆：大数据场景Kafka，业务消息场景RabbitMQ。如果不确定，Kafka更通用但运维更复杂，RabbitMQ更简单但吞吐有上限。

不要只说一个好。能说出"看场景"和具体对比维度(吞吐/路由/延迟/可靠)展示工程思维。
Nacos的AP和CP模式什么时候用哪个？

AP模式(默认)：服务实例下线后立即从列表摘除，保证可用性，适合临时实例(如SpringCloud服务)——这些服务本来就需要心跳维持，挂了就该摘除。

CP模式：不立即摘除，需Raft共识，适合持久实例(如Kafka Broker、MySQL)——这些服务挂了不应该删除注册信息，因为它们是有状态的，重启后还在。

选择原则：大部分微服务用AP，有状态服务用CP。

用CAP理论框架回答，展示你对分布式系统的理解。提到"有状态vs无状态"是判断依据，说明你不是死记答案。

六、MySQL ⭐⭐⭐ 必考

MySQL是Java后端最常用的关系型数据库，面试出场率仅次于Redis。虽然第01章已有数据库核心复习，这里从中间件视角补充索引优化、主从架构、分库分表等工程化考点。

MySQL面试三板斧：索引怎么建怎么走、事务怎么隔离怎么用、大表怎么分怎么拆。

6.1 B+树索引深度

MySQL索引底层是B+树，理解B+树是回答所有索引问题的基础。

B+树结构：非叶子节点只存索引(节省空间)，叶子节点存数据+双向链表(范围查询高效)
对比B树B+树
非叶子节点存索引+数据只存索引(更紧凑，一次IO读更多)
叶子节点无链表双向链表相连(范围查询O(logN+K))
查询稳定性不稳定(可能非叶子就命中)稳定(都要到叶子节点)
单次IO信息量少(非叶子含数据)多(非节点只含索引)

6.2 聚簇索引 vs 非聚簇索引

对比聚簇索引(InnoDB主键)非聚簇索引(二级索引)
叶子存什么完整数据行索引列值 + 主键值
查询方式直接拿到数据先查到主键，再回表查数据
每表几个1个多个
类比字典的拼音目录(直接定位页)字典的部首目录(先查拼音再翻页)
覆盖索引：如果查询的列全在二级索引里，就不需要回表。如SELECT id,name FROM users WHERE name='张三'，如果(name)是索引，id在叶子节点直接有，不用回表。这就是"覆盖索引优化"。

6.3 索引失效场景

  • 最左前缀违反：联合索引(a,b,c)，查询条件没有a则不走索引
  • 索引列做运算/函数：WHERE YEAR(create_time)=2026 → 改 WHERE create_time >= '2026-01-01'
  • 隐式类型转换：WHERE phone=13800138000(phone是varchar) → 字符串比较变全表扫描
  • LIKE左模糊：LIKE '%abc'不走索引，LIKE 'abc%'可以
  • OR条件：WHERE a=1 OR b=2 如果b没有索引则全表扫描
  • NOT IN / NOT EXISTS：通常不走索引，改用LEFT JOIN

6.4 主从复制与读写分离

MySQL主从复制原理：Master写binlog，Slave拉取并回放

三种复制方式：

  • 异步复制(默认)：Master不等待Slave确认，性能高但可能丢数据
  • 半同步复制(semi-sync)：Master等至少1个Slave确认才返回，兼顾性能和安全
  • 组复制(MGR)：基于Paxos，多主一致性，但性能损耗大

6.5 分库分表

方式说明适用场景
垂直分库按业务拆库(订单库/用户库/商品库)业务耦合低
垂直分表按列拆表(热列+冷列分离)大字段、冷热数据
水平分库同表数据分到不同库(取模/范围/哈希)单库数据量大
水平分表同库内按规则拆成多表单表千万级以上
分库分表后的问题：①跨库JOIN困难(需应用层组装) ②分布式事务(Seata) ③全局唯一ID(Snowflake雪花算法) ④跨库分页排序复杂。不要一上来就分，先加索引→缓存→读写分离→最后才分库分表。
MySQL为什么用B+树而不是B树或Hash索引？

B+树相比B树：1）非叶子节点只存索引不存数据，单次磁盘IO能读更多索引节点，树更矮，IO次数更少；2）叶子节点双向链表相连，范围查询( BETWEEN / > / < )只需要找到起点然后顺着链表走，B树需要中序遍历回溯，效率低。

相比Hash索引：Hash等值查询O(1)确实快，但不支持范围查询、排序、最左前缀匹配。数据库大量场景是范围查询和排序，B+树更通用。

InnoDB选B+树是因为它兼顾了等值查询和范围查询，且查询稳定(每次都到叶子)。

能说出"范围查询"和"非叶子节点不存数据省空间"是B+树的两大优势就够了。提一句"Hash索引Memory引擎支持"说明知识面广。
什么情况下索引会失效？你怎么排查的？

常见失效场景：1）违反最左前缀(联合索引(a,b,c)查询没a)；2）索引列做运算/函数(WHERE YEAR(time)=2026)；3）隐式类型转换(varchar列用int查)；4）LIKE左模糊('%abc')；5）OR条件有一侧无索引；6）NOT IN。

排查方法：用EXPLAIN分析执行计划，看type列(ALL=全表扫描, ref/range=走索引)、key列(实际使用的索引)、rows列(预估扫描行数)。如果type=ALL但应该走索引，就是索引失效了。

说EXPLAIN是必答。能说出看type/key/rows三列说明你有实际调优经验。
分库分表怎么选分片键？分完后跨库查询怎么办？

选分片键原则：1）查询频率最高的字段(如user_id)；2）数据分布均匀(避免热点)；3）尽量让查询落在单分片内。

跨库查询的解决方案：1）冗余字段——在分片表里冗余一些常用查询字段，避免跨库JOIN；2）数据同步——用Canal监听binlog同步到ES，复杂查询走ES；3）应用层组装——分别查各分片再在内存合并(性能差，尽量少用)；4）绑定表/广播表——小表(如配置表)每个库都放一份。

提Canal+ES方案是加分项，展示你把前面ES的知识串起来了。说"先加索引→缓存→读写分离→最后分库分表"展示工程判断力。

七、Nginx ⭐⭐ 中高频

Nginx是后端最常用的反向代理和Web服务器，面试常问负载均衡、正向vs反向代理、性能优化。

Nginx = 反向代理 + 负载均衡 + 静态资源服务，单机可扛数万并发，靠的是epoll事件驱动+非阻塞IO+多进程。

7.1 正向代理 vs 反向代理

对比正向代理反向代理
代理谁代理客户端代理服务端
客户端知道知道目标服务器(如VPN)不知道真实服务器(如nginx)
典型场景翻墙、隐藏客户端IP负载均衡、隐藏服务器IP
类比代购(你找代购买，代购去买)客服总机(你打总机号，总机转分机)

7.2 负载均衡策略

Nginx配置 
# 1. 轮询(默认) - 按顺序逐一分配
upstream backend {
    server 192.168.1.1:8080;
    server 192.168.1.2:8080;
}

# 2. 加权轮询 - 按weight比例分配，配置高的机器多分
upstream backend {
    server 192.168.1.1:8080 weight=3;
    server 192.168.1.2:8080 weight=1;
}

# 3. IP Hash - 同一IP总是打到同一台(会话粘性)
upstream backend {
    ip_hash;
    server 192.168.1.1:8080;
    server 192.168.1.2:8080;
}

# 4. least_conn - 分给当前连接数最少的
upstream backend {
    least_conn;
    server 192.168.1.1:8080;
    server 192.168.1.2:8080;
}

# 5. 一致性Hash - 解决IP Hash增减节点时大面积缓存失效
upstream backend {
    hash $request_uri consistent;
    server 192.168.1.1:8080;
    server 192.168.1.2:8080;
}

7.3 Nginx为什么高并发

Nginx多进程+epoll架构：Master管理，Worker用epoll处理数万并发连接
  • 多进程模型：1个Master + N个Worker(通常N=CPU核心数)，Master管理Worker，Worker独立处理请求
  • epoll事件驱动：1个Worker用epoll管理数万个连接，非阻塞IO + 事件回调，不阻塞等待
  • 零拷贝(sendfile)：静态文件传输用sendfile直接从磁盘到网卡，不经过用户态
  • 内存池：自己管理内存分配，减少内存碎片和系统调用
Nginx的epoll模型 ≈ Java Netty的EventLoop：单线程+Selector多路复用+非阻塞IO。Nginx的Worker ≈ Netty的WorkerGroup，Master ≈ BossGroup。思路一模一样。

7.4 常用场景配置

Nginx典型反向代理配置 
# 前端静态资源 + API反向代理 + 负载均衡
server {
    listen 80;
    server_name api.example.com;

    # 前端静态文件
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;  # SPA路由
    }

    # API反向代理到后端集群
    location /api/ {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # WebSocket支持(Agent流式输出需要)
    location /ws/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
做Agent开发时，LLM流式输出(SSE/WebSocket)通常需要Nginx做反向代理。注意配置proxy_buffering off关闭缓冲，否则流式输出会被Nginx缓存导致体验差。
Nginx为什么能扛高并发？

三个核心原因：1）多进程+epoll——Master管理N个Worker(CPU核心数)，每个Worker用epoll事件驱动管理数万连接，单线程不阻塞；2）非阻塞IO——IO操作不等待，立即返回，事件就绪再回调处理；3）零拷贝——静态资源用sendfile直接从磁盘到网卡，不经过用户态。

本质和Redis一样：瓶颈不在CPU计算而在IO，用epoll把IO等待变成事件通知，单线程也能处理海量连接。

和Redis对比"都是epoll事件驱动"是高级答法。提Netty类比说明你Java体系的知识是通的。
Nginx负载均衡有哪些策略？一致性Hash解决什么问题？

五种策略：轮询(默认)、加权轮询(按机器配置)、IP Hash(会话粘性)、least_conn(最少连接)、一致性Hash。

IP Hash的问题：当增减后端节点时，Hash环重新映射，大量请求会落到新节点导致缓存大面积失效。一致性Hash把节点和请求都映射到Hash环上，增减节点只影响相邻区间的请求，缓存失效面小。

场景：缓存代理(如Nginx代理Redis/Memcached)用一致性Hash，增减节点时缓存命中率不暴跌。

提"缓存失效"是关键——一致性Hash的初衷就是减少增减节点时的缓存失效。能说出Hash环原理更佳。
正向代理和反向代理什么区别？Nginx是哪个？

正向代理代理客户端——客户端知道要访问谁，代理帮你去访问(如VPN、翻墙工具)。反向代理代理服务端——客户端只知道代理地址，不知道真实服务器(如Nginx)。

Nginx做的是反向代理：客户端请求Nginx，Nginx根据配置转发到后端真实服务器，客户端不知道也不关心后端有谁。

一句话：正向代理代理客户端(隐藏客户端)，反向代理代理服务端(隐藏服务端)。

用"代购 vs 客服总机"类比最直观。如果面试官追问正向代理场景，说VPN/翻墙即可。
  • Redis快的原因：纯内存 + 单线程避免锁竞争 + IO多路复用epoll + 优化的数据结构(SDS/跳表/ziplist)
  • 缓存三大问题：穿透(查不存在→布隆过滤器/空值缓存)、击穿(热点过期→互斥锁/永不过期)、雪崩(批量过期→随机TTL/多级缓存)
  • 分布式锁三要素：原子加锁(SET NX PX) + UUID防误删 + 看门狗续期。注意主从切换丢锁问题
  • RDB vs AOF：RDB全量快照恢复快但可能丢数据，AOF命令日志更安全但恢复慢，生产混用
  • Kafka高吞吐：顺序写磁盘 + 零拷贝sendfile + 批量处理 + Partition分区并行
  • Kafka消息不丢：生产端acks=all + Broker副本ISR + 消费端手动提交offset
  • Kafka vs RabbitMQ：Kafka高吞吐大数据流，RabbitMQ灵活路由低延迟业务消息
  • ES倒排索引：词→文档列表，全文检索O(1)；vs B+树精确匹配，vs向量检索语义匹配
  • MySQL B+树：非叶子只存索引(省空间)，叶子存数据+双向链表(范围查询快)，3-4层存千万数据
  • 聚簇vs非聚簇：聚簇索引叶子存完整数据行(主键)，二级索引叶子存主键值需回表，覆盖索引免回表
  • 索引失效：违反最左前缀、索引列做运算/函数、隐式类型转换、LIKE左模糊、OR一侧无索引
  • 分库分表顺序：先加索引→缓存→读写分离→最后才分库分表。分片键选查询最频繁+分布均匀的字段
  • Nginx高并发：多进程(Master+Worker) + epoll事件驱动 + 非阻塞IO + 零拷贝sendfile
  • 负载均衡策略：轮询/加权/IP Hash/least_conn/一致性Hash，后者解决增减节点缓存大面积失效
  • 正vs反向代理：正向代理客户端(翻墙VPN)，反向代理服务端(Nginx负载均衡)
  • Nacos AP vs CP：AP临时实例立即摘除(微服务)，CP持久实例共识保留(有状态服务)
  • ZooKeeper：临时节点(服务注册)+顺序节点(分布式锁)+Watcher(通知)。ZAB不是Raft
