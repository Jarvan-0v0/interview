CHAPTER 06

RAG 检索增强生成

🎯 学习目标：理解RAG解决的核心问题（知识截止/私有数据/幻觉），掌握离线+在线两阶段完整流程，能讲清楚Chunking策略、Embedding模型、检索策略（向量/关键词/混合/Reranking）和Advanced RAG技术，并结合客服助手项目说清自己的RAG实战与优化经验。

RAG = 让LLM"先查资料再回答"，而不是凭记忆硬答——本质是给模型一个可检索的外部记忆库，把"知识"从模型权重里搬到向量数据库里。

1. 为什么需要RAG ★★★★★ 必考

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是LLM"知识不够用"的三大痛点。面试官问"为什么用RAG"，必须能逐条说清：

LLM的三大知识痛点

  1. 知识截止日期：模型训练有截止点，之后的新知识它不知道。问"2024年新出的API"它会答不上来或编一个旧的。
  2. 私有数据未训练：公司的订单系统、客服话术、内部文档，模型从来没见过，不可能"记"得住。
  3. 幻觉问题：不知道也硬答，编造看起来合理但错误的内容——客服场景里这是灾难。
RAG ≈ 在Service层先查数据库再调外部API。传统Service调外部API前会先查本地库补全上下文，RAG就是让LLM"调API生成答案"前先查向量库补全资料——让模型"看着资料回答"而不是"凭记忆回答"。把检索结果塞进Prompt，等于给Service方法传了一个额外的上下文参数。
RAG vs 微调：私有知识更新频繁、量大、需要可追溯来源——用RAG；知识相对稳定、风格/格式定制——用微调。企业客服场景几乎都是RAG胜出，因为话术和商品库天天在变。

2. RAG完整流程 ★★★★★ 必考

RAG分离线（建库）和在线（检索+生成）两大阶段，这是面试必画的图。

图6-1 RAG完整流程：离线建库（加载→分块→向量化→入库） + 在线检索生成（提问→向量化→检索→拼Prompt→LLM生成）
面试要点：离线阶段只跑一次（或定期增量更新），在线阶段每次查询都跑。向量化用的是同一个Embedding模型——离线把文档转向量，在线把问题转向量，才能在同一向量空间算相似度。

3. 文档分块（Chunking）策略 ★★★★☆

分块是RAG效果好坏的第一道关卡。文档太大塞不进Prompt，太小又丢失上下文。怎么切直接决定检索质量。

策略做法优点缺点
固定大小分块按字符数（如500字）硬切实现最简单可能切断语义，句子截断
语义分块按段落/句子边界切语义完整块大小不一，需后处理
滑动窗口固定大小+overlap重叠跨块信息不丢存储冗余、检索重复
递归分块先按大结构切，再递归细分保留文档层级依赖分隔符，对无结构文档失效

分块策略的底层原理

固定大小分块是"无脑切"策略：按固定字符数（如每500字一个块）依次截断文档，通常会在末尾补齐到完整字符数。优点是实现极简、块大小可控、向量空间分布均匀，便于批量处理和内存预算；缺点是完全不考虑语义边界，可能把一句话切成两半，或把不相关的两段拼进同一个块。适合结构均匀、主题单一的语料（如产品规格说明、统一格式的日志），不适合段落主题切换频繁的文档。

语义分块按文本的自然边界（段落、句子、甚至句号/换行符）切分，保证每个块内部语义完整。它的原理是：先用句子分割器（如spaCy、正则）把文档切成句子单元，再按语义连贯性合并相邻句子——常用的做法是计算相邻句子的Embedding相似度，相似度低于阈值时切一刀。优点是每块语义自洽、检索命中后LLM能读懂；缺点是块大小不均匀（可能几十字也可能上千字），对后续存储和Prompt token预算不友好，需要设置上下限做截断。适合FAQ、政策文档、知识库文章等结构化较强的语料。

滑动窗口在固定大小基础上引入overlap重叠区：相邻块之间共享一部分内容（如每块500字、重叠100字）。原理是：很多关键信息恰好在块边界附近，硬切会丢失"前文铺垫"或"后文结论"，overlap让边界信息同时出现在两个块里，检索时至少有一个块能保留完整上下文。缺点是存储冗余（overlap部分被存多次）、检索时同一信息可能被多次召回需去重。适合长文叙事、上下文强依赖的内容（如操作手册、故事类文档）。经验值：overlap一般取块大小的10%-20%。

递归分块按文档的层级结构递归切分：先按最大分隔符（如章节标题）切，如果某块仍超过阈值，再按次级分隔符（如段落）切，还不行再按句子切……层层递归直到每块都小于阈值。原理是：尊重文档原有的结构层次，让同一小节的内容尽量在同一个块里。LangChain的RecursiveCharacterTextSplitter就是典型实现，分隔符优先级可配置（如 ["\n\n", "\n", "。", " "]）。优点是保留文档逻辑结构、语义完整度高；缺点是依赖分隔符、对无结构的纯流水文本失效。适合Markdown/HTML/技术手册等有明确层级的文档。

图6-3 四种分块策略对比：固定大小(硬切风险) / 语义(完整但大小不一) / 滑动窗口(overlap防丢) / 递归(按层级细分)
Chunking ≈ 数据库的分页查询，但这里是对文档内容"分页"。区别在于：分页是运行时按limit/offset切，Chunking是离线预处理时切好存库。选块大小就像选pageSize——太大返回冗余、太小丢失上下文，需要按业务语料调试。

分块大小对效果的影响

  • 块太大（如2000字）：一个块里混杂多个主题，向量被"平均"，检索精度下降；也浪费Prompt token。
  • 块太小（如100字）：语义不完整，检索到但LLM看不懂上下文。
  • 经验值：中文300-500字、英文200-500 token是常见起点，需结合语料A/B测试。
分块是RAG最容易踩坑、也最容易被忽视的环节。面试时如果说"我就随便切了下"，基本凉。要讲清"我试了几种大小，对比检索准确率选的"。

4. Embedding模型 ★★★★☆

什么是向量化

Embedding就是把文本映射成高维向量（如768维/1536维的浮点数组），语义相近的文本在向量空间里距离也近。这样"相似度检索"就变成了"向量距离计算"（余弦相似度等）。

常用Embedding模型

模型来源维度特点
text-embedding-ada-002OpenAI1536闭源、效果好、英文强、要付费调API
BGE（bge-large-zh）智源1024开源、中文效果好、可本地部署
M3E社区768开源、中英均衡、轻量
bge-m3智源1024多语言/多粒度，支持稀疏+稠密

维度与效果：并非维度越高越好。高维度信息更丰富但计算更慢、存储更占；关键看模型训练质量和与语料的匹配。中文场景BGE/M3E往往比OpenAI的更懂中文语义。

工程要点：离线建库和在线检索必须用同一个Embedding模型，否则向量空间不一致，相似度无意义。换模型=全部重新向量化入库。

5. 检索策略 ★★★★★ 必考

检索质量直接决定RAG上限——检索不到，再强的LLM也答不对。四种主流策略要能对比讲清。

图6-2 四种检索策略对比：向量(语义) / 关键词(精确) / 混合(兼顾) / Reranking(精排)

为什么需要Reranking

向量检索用Bi-Encoder（问题和文档各自编码再算距离），快但粗；Reranking用Cross-Encoder（问题和文档拼一起送入模型），慢但准。生产套路：向量/混合检索粗召回Top-100 → Cross-Encoder精排Top-10。

6. Advanced RAG技术 ★★★☆☆

基础RAG"问什么就检索什么"效果有限。Advanced RAG在查询前和检索后做文章，进一步提升效果。

① Query Transformation 查询改写

用户问题往往口语化、模糊、指代不清。先让LLM把问题改写得更"检索友好"再检索。例："那个能退吗" → 改写为"商品退换货政策是什么"。

HyDE 与 Query Transformation 的原理深挖

为什么要改写查询：向量检索的本质是"问题向量和文档向量算相似度"，但问题和文档在语言形式上往往不对等。问题是疑问句（"怎么退款"），文档是陈述句（"退款政策为7天内可申请…"）——同义但句式不同，Embedding后的向量可能并不那么接近。Query Transformation 让LLM先把口语化、指代模糊的问题规范化成检索友好的表述：补全指代（"那个"→"商品"）、消除歧义、加上关键词。本质是在检索前加一道"问题翻译层"，把用户语言翻译成文档语言，缩小 query 与 doc 的语义分布差距。

HyDE（Hypothetical Document Embeddings）更激进：它让LLM直接对问题生成一个假设性答案文档（可能完全编错），然后用这个"假答案"的向量去检索真实文档。为什么这招有效？因为答案和文档在语言形式上更接近——都是陈述句、都在描述事实，Embedding后的向量分布更对齐。问题"怎么退款"的向量可能和退款政策文档距离较远，但LLM编的假设答案"用户可以在7天内通过订单页申请退款，审核通过后…"的向量，和真实退款政策文档的向量会非常接近，召回率显著提升。

HyDE的适用场景与风险：它特别适合问题短、文档长、问题与文档表述差异大的场景（如客服、技术问答）。但有两个代价：①多一次LLM调用，延迟和成本翻倍；②假设答案如果方向完全跑偏（LLM对问题领域一无所知），可能把检索带偏。工程上常加兜底策略：HyDE检索结果和原始问题检索结果都召回，融合后取并集，避免HyDE翻车时全军覆没。

图6-4 Advanced RAG四种技术对比：基础RAG(直查) / 查询改写(问题翻译) / HyDE(假答案检索) / Multi-Query(多角度召回)

② HyDE 假设性答案检索

先让LLM对问题生成一个假设答案（可能错），用这个假设答案的向量去检索——因为"答案"和"文档"语义分布更近，比用"问题"检索更准。适合问题短、文档长的场景。

③ Parent-Child 父子分块

小块检索、大块返回。把文档切成大块（父），大块内再切小块（子）向量化入库。检索时用小块命中（精度高），但返回给LLM的是小块所在的父块（上下文全）。兼顾检索精度和上下文完整性。

④ Multi-Query 多查询

让LLM把一个问题拆成多个角度的子问题，分别检索后合并结果。例："这个产品怎么样" → 拆成"价格""质量""售后"三个子问题分别检索，召回更全。

7. RAG效果评估 ★★★☆☆

RAG不是"跑通了就行"，要能量化评估才能优化。分三层：

评估层指标含义
检索质量Recall@KTop-K结果里是否包含正确文档，含了算召回
检索质量MRR正确结果的排名倒数均值，越靠前分越高
生成质量Faithfulness 忠实度回答是否忠于检索资料，有没有"编"
生成质量Answer Relevance回答是否切题、是否解决了用户问题
端到端整体准确率从用户视角看最终回答对不对
Ragas、TruLens是常用的RAG评估框架，能自动算上述指标。面试提到这些工具会显得有实战经验。

Recall@K 的计算方法

定义：对于一个查询，如果在检索返回的Top-K个结果中包含至少一个相关文档，则算"命中"，得分为1；否则为0。对所有查询的命中率取平均，就是Recall@K。

公式：Recall@K = (命中查询数) / (总查询数) = (1/N) × Σ 1[相关文档 ∈ TopK(qᵢ)]，其中 1[...] 是指示函数，条件成立取1否则取0，N是查询总数。

计算示例：假设有5个测试查询，K=5。查询1的Top-5含相关文档→命中；查询2不含→未命中；查询3、4、5都命中。则 Recall@5 = 4/5 = 0.8（80%）。注意：Recall@K只关心"是否召回到"，不关心排在第几位——排在第1和第5都算命中。如果想体现排名质量，用 MRR = (1/N) × Σ 1/rank(qᵢ)，rank是第一个相关文档的排名位置，越靠前MRR越接近1。

工程意义：Recall@K是RAG的检索层天花板——如果正确文档没进Top-K，后面LLM再强也答不对。一般要求 Recall@5 ≥ 0.9 才算检索合格。调试时分桶看：哪些类型的问题召回低？往往是分块不合理或Embedding对该类语义不敏感，针对性优化。

Faithfulness 忠实度的计算方法

定义：衡量LLM生成的回答中，有多少陈述（statements）能被检索到的context支撑。忠实度=被支撑的陈述数 / 总陈述数。本质是检测"幻觉"——回答里有没有context没提到但LLM自己编的内容。

计算步骤（Ragas框架的做法）：①用LLM把生成的回答拆成一个个原子陈述（如"退货需在7天内申请"是一个陈述）；②对每个陈述，用LLM判断它是否能被context中的内容推导出来（verdict: yes/no）；③统计 yes 的数量除以总陈述数，得 Faithfulness 分数。

计算示例：LLM回答="商品支持7天无理由退货，需保留原包装。审核通过后退款将在3个工作日内原路返回。" 拆成3个陈述：S1"7天无理由退货" / S2"需保留原包装" / S3"3个工作日原路返回"。假设context只支撑了S1和S2，S3是LLM编的。则 Faithfulness = 2/3 ≈ 0.67。说明回答里有1/3的内容缺乏依据，存在幻觉风险。

工程意义：Faithfulness低 → 优化方向是加强Prompt约束（"严格基于资料回答，资料没有的就说不知道"）、提高minScore过滤掉低质context、或换更强的LLM。Faithfulness高但 Answer Relevance 低 → LLM没编，但答非所问，优化Prompt让它更聚焦问题。两个指标要一起看才能定位问题。

langchain4j RAG 代码示例

Java · langchain4j RAG实现 
// 1. RAG增强的AiService——把检索到的资料通过{{info}}注入SystemMessage
interface RagAssistant {
    @SystemMessage("你是一个客服助手。请严格根据以下检索到的资料回答用户问题，"
            + "资料中没有的内容请说明'暂无相关信息'，不要编造。资料：{{info}}")
    String chat(@UserMessage String question, @V("info") String info);
}

// 2. 检索器——从向量库取Top-K相关文档
ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()
    .embeddingStore(store)            // 向量库（如Milvus/PgVector）
    .embeddingModel(embeddingModel)    // 同一个Embedding模型
    .maxResults(5)                  // Top-5
    .minScore(0.7)                // 相似度阈值，过滤不相关
    .build();

// 3. 组装RAG链：检索 → 拼接 → 生成
RagAssistant assistant = AiServices.builder(RagAssistant.class)
    .chatLanguageModel(model)
    .contentRetriever(retriever)       // langchain4j自动检索并注入info
    .build();

// 用户提问，框架自动：向量化问题→检索→拼Prompt→调LLM
String answer = assistant.chat("你们的退货政策是什么？");
上面是基础用法。生产级还需加：查询改写、混合检索、Reranking、minScore过滤、来源引用追溯。能讲清"我从最简版逐步加了哪些优化"，就是真做过项目的人。

面试场景演练

Q1：RAG的完整流程是什么？

RAG分离线和在线两阶段。离线：文档加载 → 分块Chunking → Embedding向量化 → 存入向量库。在线：用户提问 → 同一Embedding模型向量化 → 在向量库做相似度检索取Top-K → 把检索结果拼进Prompt作为context → LLM基于context+问题生成回答。

核心是让LLM"看着资料答"而不是凭记忆答，解决知识截止、私有数据、幻觉三大问题。

能顺手画出离线+在线流程图、强调"离线和在线必须用同一个Embedding模型"，是高分答法。
Q2：文档分块有什么策略，怎么选？

主要有四种：固定大小（按字符数硬切）、语义分块（按段落/句子）、滑动窗口（固定大小+overlap重叠避免割裂）、递归分块（先按大结构再细分）。选择要看语料：结构化文档（手册/FAQ）用语义或递归；无结构长文用滑动窗口。

块大小是关键调参点——太大语义混杂检索不准、太小上下文丢失，中文一般300-500字起步，靠A/B测检索准确率定。我项目里对比过200/400/800字三档，400字召回率最好。

类比Java分页查询；强调"我试过几档对比了召回率"——立刻显得有实战，不是背书的。
Q3：向量检索和关键词检索有什么区别？

向量检索基于语义相似，问题和文档各自编码成向量算余弦距离，能识别同义词（"退款"召回"退货"）但精确词召回弱。关键词检索（BM25）基于词频权重，精确匹配强（查订单号20230801精准）但不懂语义。

生产上通常用混合检索——两路并行召回再用RRF融合，兼顾语义和精确。客服场景里订单号查询靠关键词、政策类问题靠向量，混合最稳。

举一个"订单号用关键词、退货政策用向量"的具体例子，立刻把抽象概念落地。
Q4：什么是Reranking，为什么需要？

Reranking是对初步检索结果做精排。向量检索用Bi-Encoder（问题和文档各自编码再算距离），快但粗；Reranking用Cross-Encoder（问题和文档拼一起送入模型做深度交互），慢但准。

生产套路：向量/混合检索粗召回Top-100 → Cross-Encoder精排取Top-10给LLM。因为Reranking慢，只对少量候选精排，既保速度又提精度。

类比数据库：粗排像LIMIT 100扫一遍索引、精排像ORDER BY精确排序取10。Java工程师一听就懂。
Q5：你的客服助手RAG是怎么做的？（结合项目）

我的客服助手用langchain4j做的RAG。离线把公司的商品FAQ、退换货政策、物流说明等文档加载后按语义分块（约400字/块，带overlap），用BGE中文模型向量化存入Milvus。

在线用户提问后，用混合检索（向量+BM25）粗召回Top-20，再用Cross-Encoder精排Top-5，拼进SystemMessage作为context，让LLM严格基于资料回答、资料没有的就说"暂无相关信息"。还加了查询改写，把口语化问题改成检索友好的表述。最终回答会附带来源文档链接，方便人工核查。

这是你的招牌题。要讲清技术选型理由（为什么BGE不选OpenAI——中文+本地部署+免费）、踩过的坑（分块大小调参）、最终效果（准确率提升多少），形成完整故事线。

Q6：RAG效果不好怎么排查和优化？

按链路分层排查：①检索环节——先看Recall@K，正确文档有没有进Top-K？没进就是检索的问题，可能分块不合理、Embedding模型不匹配、或查询太口语化，对应优化分块策略、换模型、加查询改写。②生成环节——检索到了但答不对，看Faithfulness和Answer Relevance，可能是context没拼好或Prompt没约束好"基于资料答"，调SystemMessage约束、加minScore过滤低质结果。③端到端——整体准确率，看是检索还是生成拖后腿。

优化顺序：先保检索（分块+模型+混合检索+Reranking），再调生成（Prompt约束+来源追溯），最后上Advanced RAG（HyDE/Multi-Query）。

能说出"按链路分层排查"这个方法论比直接背优化点高级——体现你懂系统性Debug，不是瞎试。
  • RAG解决三大痛点：知识截止、私有数据未训练、幻觉——让LLM"看着资料回答"
  • 完整流程：离线加载→分块→向量化→入库；在线提问→向量化→检索→拼Prompt→生成
  • 离线和在线必须用同一个Embedding模型，换模型=全部重新入库
  • Chunking四种策略：固定/语义/滑动窗口/递归，块大小需A/B测，中文300-500字起步
  • Embedding模型：OpenAI(1536维)/BGE(中文强、开源)/M3E——维度非越高越好，看训练质量与语料匹配
  • 检索策略：向量(语义) vs BM25(精确) vs 混合(兼顾) vs Reranking(Cross-Encoder精排)——生产首选混合+Reranking
  • Advanced RAG：查询改写/HyDE/Parent-Child(小块检大块返)/Multi-Query
  • 评估三层：检索(Recall@K/MRR) + 生成(Faithfulness/Relevance) + 端到端准确率，工具用Ragas/TruLens
