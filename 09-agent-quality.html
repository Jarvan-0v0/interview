第09章

Agent测试与质量保障

学习目标：掌握Agent系统怎么测、怎么评价好坏、线上怎么监控质量。这是实际工作中最核心的问题——Agent不像传统软件有确定性输出，测试和评价方法论完全不同。本章覆盖测试方法论、质量评价体系、Prompt版本管理、线上监控与退化检测、AB测试灰度、Bad Case排查。

一、Agent测试方法论 ⭐⭐⭐

传统Java测试有JUnit + Mockito + SpringBoot Test一套成熟体系。Agent测试的核心挑战是LLM输出不确定性——同样的输入跑两次可能输出不同。但测试方法论可以复用，只是断言方式要变。

Agent测试 = 传统测试金字塔(单元→集成→端到端) + 非确定性断言(语义匹配而非精确匹配) + LLM-as-Judge(用AI当裁判)
Agent测试金字塔：底层多（单元测试快且多），顶层少（端到端慢且贵）

1.1 单元测试：测Tool和Prompt

Agent单元测试 ≈ JUnit的@Test，但断言从assertEquals变成语义匹配。Tool的单元测试和普通Java方法测试几乎一样——因为Tool就是普通Java方法。
Java (Tool单元测试) 
@Test
void testWeatherTool() {
    // Tool就是普通Java方法，正常测
    WeatherTool tool = new WeatherTool(mockWeatherApi);
    String result = tool.getWeather("北京");
    
    // Tool输出是结构化的，可以精确断言
    assertNotNull(result);
    assertTrue(result.contains("温度"));
}

@Test
void testPromptFormatting() {
    // 测Prompt模板格式化（不调LLM）
    String prompt = promptTemplate.format(Map.of(
        "question", "怎么退款",
        "context", "退款政策..."
    ));
    
    // 确认变量正确插值
    assertTrue(prompt.contains("怎么退款"));
    assertTrue(prompt.contains("退款政策"));
}

1.2 集成测试：Golden Set回归

Golden Set（黄金测试集）是Agent测试的核心武器：维护一批经典问题+期望答案，每次改Prompt/换模型后跑一遍，确保不退化。

Java (Golden Set集成测试) 
@Test
void testGoldenSet() {
    // 1. 准备黄金测试集（50-100条经典case）
    List goldenSet = loadGoldenSet("golden-set.json");
    
    // 2. 对每条case跑Agent
    int passCount = 0;
    for (TestCase tc : goldenSet) {
        String actual = agent.chat(tc.getInput());
        
        // 3. 语义断言：不是精确匹配，而是语义包含关键词
        boolean pass = semanticCheck(actual, tc.getExpectedKeywords());
        if (pass) passCount++;
    }
    
    // 4. 通过率要求 ≥90%
    double passRate = (double) passCount / goldenSet.size();
    assertTrue(passRate >= 0.9, "Golden set通过率" + passRate);
}

1.3 非确定性测试的断言策略

策略做法适用场景缺点
关键词包含assertContains(output, "退款")简单问答关键词不全则漏判
正则匹配assertMatches(output, regex)格式验证不验证语义
语义相似度cosineSim(output, expected) > 0.8开放式问答需要Embedding模型
LLM-as-Judge用GPT-4评判输出质量打分复杂Agent评测贵+裁判本身可能不准
多次运行取多数跑5次取多数结果需要稳定性的场景成本×5
LLM-as-Judge的陷阱：用同一个模型当裁判评自己的输出会有偏见。最好用更强的模型评弱模型的输出（如GPT-4评判GLM-4的输出）。

1.3.1 为什么LLM输出不确定？——非确定性的根因

LLM本质是一个概率模型，不是确定性函数。每次生成时，模型在词表上计算下一个token的概率分布，然后从中采样——采样的随机性由temperature参数控制：temperature=0时几乎确定（贪心解码，取概率最高的token），temperature>0时引入随机性。即便temperature=0，由于浮点数精度、批处理padding差异、GPU非确定性运算等原因，同一输入也可能输出不同结果，只是差异很小。这和Java方法截然不同——Java方法给定输入必有确定输出，LLM给定输入只给出一个"高概率输出"。

更深一层，LLM的不确定性来自三个叠加来源：①模型权重本身是高维概率分布的参数化表达，同一句话在不同context下激活不同神经元；②采样策略（top-p/top-k/temperature）在概率分布上做随机采样；③上下文长度——超长对话会因为窗口截断丢信息，截断位置不同结果不同。理解这三层后，测试策略就清晰了：能固定的地方固定（temperature=0、固定seed、固定context），不能固定的地方用语义断言而非精确断言。

1.3.2 语义断言怎么实现？

语义断言的核心思想是"意思对就行，字面不必一样"。实现方式分三档：①轻量级——关键词/正则匹配，适用于结构化输出（如要求必须包含"退款"二字、必须符合JSON格式）；②中量级——Embedding语义相似度，把实际输出和期望输出都Embedding成向量算cosine similarity > 阈值（如0.8），适用于开放式问答，能识别"退款流程"和"怎么办理退货"语义相近；③重量级——LLM-as-Judge，用一个LLM当裁判，输入"问题+期望+实际输出"让它按评分标准打1-5分，适用于复杂Agent评测（如"回答是否准确、完整、礼貌"这种多维度判断）。

Java类比：语义断言 ≈ 用Hamcrest的Matchers做模糊匹配，而不是JUnit的assertEquals做精确匹配。assertThat(output, containsString("退款"))是轻量级；自己写个SemanticMatcher用Embedding算相似度是中量级；调一个LLM当Matcher是重量级。生产中通常分层使用：CI快速回归用关键词+正则（秒级出结果），每周深度评测用LLM-as-Judge（慢但准），人工抽样做最终校准。

1.3.3 LLM-as-Judge的原理与局限

LLM-as-Judge的原理是"用AI评AI"：给裁判模型一个评分标准（rubric），让它对被评输出逐项打分。例如评客服回答质量，rubric包含：①准确性（是否答对问题）②完整性（是否覆盖要点）③语气（是否礼貌）④安全性（是否泄露敏感信息）。裁判模型按rubric逐项打1-5分并给出理由。优势是规模化——1000条case人工评要一周，LLM-as-Judge几分钟跑完，且评分一致性比人工高（人评会疲劳、有主观偏差）。

但有四个局限必须知道：①自评偏见——同模型评自己会偏高，必须用更强模型评弱模型；②位置偏见——并列两个答案让裁判选更好的，它会倾向选第一个出现的，解决方法是交换位置评两次取平均；③冗长偏见——裁判倾向给更长的答案打高分，即使内容质量一样，需要在rubric里明确"长度不作为评分依据"；④裁判本身有幻觉——裁判可能误判，所以必须人工抽样校准：定期抽50条让真人复核LLM-Judge的评分，计算一致率（Cohen's Kappa），一致率<0.7说明裁判不可靠需要换。这些坑不踩不知道，踩了才知道LLM-as-Judge不是万能的。

非确定性测试断言策略决策树：按输出类型选断言层级，结构化用精确、开放问答用语义、复杂评测用LLM-Judge

1.4 Mock策略

Mock LLM ≈ Mockito.when(mockLLM.chat("你好")).thenReturn("你好，有什么可以帮你")。测试Agent逻辑时不调真LLM，用mock返回固定结果，快且免费。
Java (Mock ChatLanguageModel) 
// 测试Agent编排逻辑，不调真LLM
ChatLanguageModel mockModel = mock(ChatLanguageModel.class);
when(mockModel.generate("你好")).thenReturn("你好，有什么可以帮你");

CustomerService agent = AiServices.builder(CustomerService.class)
    .chatLanguageModel(mockModel)
    .build();

// 测试Agent是否正确返回mock结果
String result = agent.chat("你好");
assertEquals("你好，有什么可以帮你", result);

三、Prompt版本管理 ⭐⭐

Prompt是Agent的"代码"，需要像代码一样管理版本、对比、回滚。

Prompt即代码：集中管理 → 版本编号 → AB对比 → 不行就回滚，和Git管代码一模一样。

3.1 Prompt即代码理念

Prompt散在代码里 ≈ SQL语句散在Java代码里(应该用MyBatis集中管理)。Prompt应该用文件/数据库/配置中心集中管理，不硬编码。
Java (从数据库加载Prompt) 
// 不推荐：硬编码在注解里
@SystemMessage("你是客服助手，回答用户问题")
interface CustomerService { ... }

// 推荐：从配置中心/数据库动态加载
String promptVersion = promptService.getActivePrompt("customer_service_v");
CustomerService agent = AiServices.builder(CustomerService.class)
    .chatLanguageModel(model)
    .systemMessageProvider(chatId -> promptVersion)
    .build();

// 切换prompt版本不重启服务（类似Nacos @RefreshScope）
public String getActivePrompt(String key) {
    return promptRepository.findActiveVersion(key).getContent();
}

3.2 版本对比与回滚

  • 每个Prompt版本有编号(v1/v2/v3)，存数据库
  • 新版本上线前跑Golden Set对比：v2通过率90% vs v1通过率92% → 不上线
  • 线上出问题立即回滚到上一版本（改一个配置，不重启）
  • Java类比：≈ Git的branch+merge+revert

四、线上监控与退化检测 ⭐⭐⭐

Agent上线后不是万事大吉，质量退化是最大隐患。

Agent线上监控架构：数据采集→指标计算→看板→告警→人工介入

4.1 监控指标分层

层级指标告警阈值
质量指标幻觉率、用户满意度、工具调用成功率幻觉>5% / 满意度<80%
性能指标P50/P99延迟、token消耗、成本P99>5s / 成本日增>20%
业务指标任务完成率、转人工率、复用率完成率<85% / 转人工>15%

4.2 模型漂移(Model Drift)

Agent线上最常见的质量退化原因：
  • 上游模型升级：GPT-4/Claude偷偷更新，你的Prompt可能不再适配
  • 用户输入分布变化：新类型问题增多，原来没覆盖的case出现了
  • 知识库过期：RAG检索到的信息过时了
  • 上下文污染：多轮对话中早期错误信息影响后续生成

4.2.1 上游模型更新：为什么"没动代码效果就变差了"

这是Agent线上最隐蔽的退化原因。OpenAI/Anthropic等模型供应商会不定期静默更新模型权重（如gpt-4-0613到gpt-4-1106），版本号变了但API名字不变，你的代码一行没改效果可能就退化了。原因有三个：①Tokenization变化——新版分词器可能把同一句话切成不同token，导致Prompt的实际输入变了；②对齐偏移——模型RLHF对齐调整后，对同一Prompt的"偏好回答风格"变了，如更保守/更冗长/更倾向拒答；③指令遵循敏感度——你精心调的Prompt（如"用一句话回答"）在新版模型上可能不再被严格遵守。

应对策略：①版本钉死——API调用时指定具体版本号（如gpt-4-0613而非gpt-4），不跟随latest，升级时主动测试再切；②版本追踪——日志记录每次请求的实际模型版本，效果退化时能定位是哪次更新引起的；③自动回归触发——订阅模型供应商的更新公告，或在每次请求response里检查model字段是否变化，发现变化立即自动跑Golden Set回归；④多模型备选——langchain4j的ChatLanguageModel接口可切换底层实现，主模型退化时临时切到备选模型（如GPT-4退化就临时切Claude）。这和Java里"依赖版本锁定+升级跑回归测试"是同一套思路。

4.2.2 用户输入分布变化：怎么检测"新类型问题"

用户输入分布漂移（Data Drift）是另一种常见退化——你的Agent没变、模型没变，但用户问的问题变了。比如客服Agent上线时80%是退款咨询，三个月后变成60%是物流查询，原来没重点优化的物流场景暴露出问题。这种退化不会在Golden Set里体现（Golden Set是历史case），只在线上指标里露端倪——某类问题满意度突然下降、转人工率上升。

检测方法：①意图聚类监控——定期用Embedding把线上用户问题聚类，对比聚类中心和历史分布，新簇出现或某簇占比突变就告警；②低置信度样本采集——监控Agent输出的置信度（如logprob或LLM自评的不确定度），低置信度样本增多说明遇到了不熟悉的输入；③未覆盖问题检测——把线上问题和Golden Set做语义相似度，相似度都低的说明是"没见过的类型"，自动加入待标注队列扩充Golden Set；④按意图分桶看指标——不要只看整体满意度，按意图分类（退款/物流/产品咨询）分别看趋势，某类突降才能定位。Java类比：这就像微服务监控里"按接口维度看RT"而不是只看整体RT——整体正常但某个接口退化会被平均掉。

模型漂移检测流程图：两类信号(模型更新+输入分布)汇入检测引擎，按阈值分流为继续/告警/扩充，告警触发回归→定位→修复

4.3 退化检测方案

  • Golden Set定期回归：每天/每周自动跑golden set，对比通过率趋势
  • 质量看板：Grafana展示核心指标趋势，设置告警阈值
  • 异常检测：某类问题满意度突然下降 → 自动告警
  • 模型版本追踪：记录每次请求的模型版本，模型变了立即跑回归
线上Agent监控 ≈ Spring Boot Actuator + Prometheus + Grafana，但监控的是"AI质量"而非"系统指标"。系统监控看CPU/内存/QPS，Agent监控看幻觉率/满意度/完成率。

五、AB测试与灰度发布 ⭐⭐

Java (Agent AB测试逻辑) 
// 按用户ID hash分流
public CustomerService getAgent(String userId) {
    int bucket = Math.abs(userId.hashCode()) % 100;
    
    if (bucket < 10) {
        // 10%流量用新版本prompt
        return agentV2;
    } else {
        // 90%流量用老版本
        return agentV1;
    }
}

// 灰度发布流程：10% → 50% → 100%
// 每个阶段观察2-3天，指标不退化才放量
发布策略做法风险适用
灰度发布10%→50%→100%逐步放量低Prompt/模型升级
影子流量新版本只跑副本结果，不服务用户零大改动验证
AB测试两组并行对比指标中方案选型
影子流量(Shadow Traffic) ≈ 金丝雀发布(Canary Release)的极致版：新版本不接触真实用户，只跑流量副本对比结果差异。

六、Bad Case排查方法论 ⭐⭐⭐

Bad Case排查五步法：收集→分类→定位→修复→验证

6.1 常见Bad Case类型及修复方案

Bad Case类型表现根因修复方案
检索失败有相关文档但没检索到分块太碎/Embedding不好/查询词不匹配问题改写(Query Transformation)/调分块大小
幻觉回答和知识库不符温度过高/没引用来源/知识库无相关内容降温度/Prompt加"只基于参考资料"/加引用追溯
工具选错该查订单却调了退款ToolTool description不清晰优化description/加few-shot示例
多轮遗忘第3轮忘了第1轮说的Memory窗口太小调大TokenWindow/加摘要
格式错误要求JSON但输出纯文本Prompt约束不够/模型能力不足用@AiService结构化输出/换更强模型
拒答该回答的说"无法回答"安全过滤过度/知识库有但检索差调安全策略/改善检索
Bad Case排查 ≈ Java线上故障排查：先看日志定位(第3步) → 本地复现 → 改代码修复 → 跑回归测试确认。思路完全一致，只是"日志"变成了"Agent决策链路日志"。

开发阶段

🎤 面试实战

Agent系统怎么测试？和传统Java测试有什么区别？

方法论可以复用传统测试金字塔：单元测试(测Tool/Prompt格式)→集成测试(Golden Set跑完整流程)→端到端测试(人工/LLM-Judge)。主要区别是断言方式——传统测试assertEquals精确匹配，Agent测试用语义断言(关键词包含/语义相似度/LLM-as-Judge)。

另一个区别是Mock策略：测试Agent编排逻辑时Mock掉LLM返回固定结果，和Mockito mock Service层一样。我的客服助手项目里维护了80条Golden Set，每次改Prompt必跑回归，通过率要求≥90%。

说"Golden Set"和"通过率≥90%"这两个具体数字，展示你有实际经验。提到Mock LLM ≈ Mockito说明你能把新知识和旧经验关联。
怎么评价一个Agent开发的好不好？

四个维度评价：1）RAG指标——检索质量(Recall@K/MRR)和生成质量(Faithfulness/Answer Relevance)；2）Agent指标——任务完成率(≥85%)、工具调用准确率(≥95%)、平均对话轮数(≤3轮)、幻觉率(≤5%)；3）用户指标——满意度(thumb up率≥80%)、转人工率(≤15%)；4）成本指标——平均token消耗和每次对话成本。

评测方法用LLM-as-Judge(GPT-4当裁判)做规模化评测+人工抽样标注做校准+线上用户反馈做真实验证。评测框架推荐RAGAS(RAG专项)+LangFuse(全链路追踪)。

给出具体目标值(85%/95%/5%)说明你有工程标准。提RAGAS和LangFuse说明你知道行业工具。四维度框架(质量/Agent/用户/成本)展示系统性思维。
LLM输出不确定，怎么写断言？

五种策略按场景选：1）关键词包含——assertTrue(output.contains("退款"))，简单case够用；2）正则匹配——验证格式；3）语义相似度——用Embedding算cosine similarity > 0.8，适合开放式问答；4）LLM-as-Judge——用GPT-4评判输出质量打分，适合复杂Agent评测；5）多次运行取多数——跑5次取majority vote，验证稳定性。

注意LLM-as-Judge别用同一个模型评自己，用更强模型评弱模型输出。生产中我一般用关键词+语义相似度做快速回归，LLM-as-Judge做深度评测。

提"别用同一个模型评自己"说明你踩过坑。给出"快速回归用关键词，深度评测用LLM-Judge"的分层策略展示工程化思维。
线上用户反馈变差了，怎么排查？

用Bad Case排查五步法：1）收集——汇总thumb down的case+人工巡检+自动告警；2）分类——是幻觉？检索失败？工具选错？Prompt不好？模型能力不足？；3）定位——看完整链路日志(用户输入→检索内容→Prompt→LLM输出)，找到具体哪一环出了问题；4）修复——改Prompt/加分块/加Tool/换模型；5）验证——修复后跑Golden Set确认修复且不引入新问题。

如果是突然变差，首先排查：模型是不是偷偷更新了？用户输入分布是不是变了？知识库是不是过期了？

五步法(收集→分类→定位→修复→验证)是最清晰的回答框架。提到"突然变差先查模型更新"说明你有线上运维经验。
Prompt改了之后怎么确保不退化？

三步保障：1）Golden Set回归——改前先跑一遍80条golden set记录基线通过率，改后再跑对比，通过率不能下降；2）AB测试——新Prompt先用10%流量跑3天，对比满意度/完成率等指标不退化才全量；3）灰度+回滚——灰度期间密切监控，有问题立即回滚到上一版本(Prompt集中管理，改配置即可回滚不重启)。

关键原则：Prompt即代码——集中管理、版本编号、可对比、可回滚，和Git管代码一样。

"Prompt即代码"这个理念是高级答法。提"改配置回滚不重启"联系到Nacos配置中心的思路。
Agent上线后怎么监控质量？

三层监控：1）质量指标——幻觉率(>5%告警)、用户满意度(<80%告警)、工具调用成功率；2）性能指标——P99延迟(>5s告警)、token消耗、日成本(增>20%告警)；3）业务指标——任务完成率(<85%告警)、转人工率(>15%告警)。

退化检测用Golden Set每天自动回归+质量趋势看板。重点关注模型漂移——上游模型更新/用户输入分布变化/知识库过期都会导致质量退化。Java类比就是Spring Actuator+Prometheus+Grafana，但监控的是AI质量而非系统指标。

给出具体告警阈值(5%/80%/5s)说明你有实操经验。提"模型漂移"概念展示你对AI系统特有问题的理解。
模型偷偷更新了导致效果变差怎么办？

这是模型漂移(Model Drift)最常见的形式。应对方案：1）版本追踪——记录每次请求的模型版本(如gpt-4-0613 vs gpt-4-1106)，发现模型变了立即跑Golden Set回归；2）定期回归——不管模型有没有变，每天/每周自动跑golden set，通过率下降就告警；3）多模型备选——不绑死一个模型，langchain4j支持多模型切换，出问题可以临时切到备选模型；4）自托管模型兜底——关键场景用自部署的开源模型(如Qwen2)做兜底，不受上游更新影响。

"记录模型版本"这个细节说明你真的踩过坑。提"自托管模型兜底"是高级架构思维。
怎么做Agent的AB测试？

流程：1）流量切分——按用户ID hash分10%到新版本；2）对比指标——同时监控满意度/完成率/成本，跑至少3天收集足够样本；3）统计显著性——不能看几条结果就下结论，至少需要100+条样本才有统计意义；4）逐步放量——10%→50%→100%，每阶段指标不退化才放量。

更安全的方案是影子流量(Shadow Traffic)：新版本不服务用户，只跑流量副本对比输出差异，零风险验证。Java类比就是金丝雀发布。

提"统计显著性"和"至少100+条样本"说明你懂数据驱动决策。影子流量是高级方案。
  • 测试金字塔：单元测试(Tool/Prompt格式+Mock LLM)→集成测试(Golden Set)→端到端(人工/LLM-Judge)
  • 非确定性断言：关键词包含/正则/语义相似度/LLM-as-Judge/多次取多数，别用assertEquals
  • Golden Set：50-100条经典case+期望关键词，每次改Prompt必跑，通过率≥90%
  • 质量四维度：RAG指标(Recall@K/Faithfulness)+Agent指标(完成率/幻觉率)+用户指标(满意度)+成本指标
  • 评测框架：RAGAS(RAG专项)/LangSmith(链路追踪)/DeepEval(JUnit式测试)/Promptfoo(Prompt对比)
  • Prompt即代码：集中管理+版本编号+AB对比+可回滚，类比Git/Nacos配置中心
  • 模型漂移：上游模型更新/输入分布变化/知识库过期 → 每天跑Golden Set回归检测
  • 监控告警：幻觉>5%/满意度<80%/P99>5s/成本日增>20% → 告警
  • Bad Case五步法：收集→分类(幻觉/检索/工具/Prompt/模型)→定位(链路日志)→修复→验证(Golden Set)
  • AB测试：10%→50%→100%灰度+统计显著性+影子流量(零风险验证)
  • 最佳实践：先强模型验证→便宜模型降成本；先简单Prompt→复杂；先少Tool→多；人工兜底不能少
