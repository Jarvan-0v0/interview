Java后端核心复习

学习目标：系统复习并发编程、JVM、Spring生态、数据库、消息队列五大核心领域。每个知识点先讲原理再给面试Q&A，以4年Java存量优势为底座，为转AI Agent打好基础。

一、并发编程 ⭐⭐⭐ 必考

并发编程是Java后端面试的第一关，几乎每场面试都会深入考察。核心考点：线程池、锁机制、volatile/CAS、AQS、ThreadLocal、CompletableFuture。

1.1 线程池七大参数与任务提交流程

线程池是Java并发编程的核心工具。它通过复用线程避免频繁创建销毁的开销，同时通过队列+拒绝策略实现流量控制。理解线程池的关键不是背7个参数，而是理解任务提交后的流向逻辑。

七大参数详解：

  • corePoolSize（核心线程数）：线程池的常驻线程数，即使空闲也不会回收（除非设allowCoreThreadTimeout=true）。相当于公司的正式员工，没活也养着。
  • maximumPoolSize（最大线程数）：线程池能创建的最大线程数，相当于正式员工+临时工的上限。只有队列满了之后才会创建超出corePoolSize的"临时工"线程。
  • keepAliveTime（空闲存活时间）：非核心线程空闲超过这个时间会被回收。临时工没活干到点就走。
  • unit（时间单位）：keepAliveTime的单位（秒/毫秒/分钟等）。
  • workQueue（阻塞队列）：核心线程忙不过来时，新任务进入队列等待。相当于候客大厅。常用的有LinkedBlockingQueue（无界，危险）、ArrayBlockingQueue（有界，推荐）、SynchronousQueue（不存储，直接交付）。
  • threadFactory（线程工厂）：创建线程的工厂，主要用于设置线程名（方便排查问题）和守护线程属性。
  • handler（拒绝策略）：队列满+线程达到max时的兜底策略。4种内置策略见下文。
核心线程(正式工) → 队列(候客大厅) → 非核心线程(临时工) → 拒绝策略(限流)。注意：不是先创建到max再入队列，而是先入队列满了才创建非核心线程！
线程池任务提交流程：核心线程→队列→非核心线程→拒绝策略（注意不是先到max再入队，是先入队满了才创建非核心）

四种拒绝策略：

  • AbortPolicy（默认）：直接抛RejectedExecutionException。任务太多了，拒绝并报错，让调用方自己处理。
  • CallerRunsPolicy：让提交任务的线程自己执行。相当于"谁提交谁干"，天然的限流——提交者忙了就不提交了。推荐用这个。
  • DiscardPolicy：默默丢弃新任务，不报错。危险，你可能根本不知道任务被丢了。
  • DiscardOldestPolicy：丢弃队列最老的任务，把新任务入队。适合过期任务没意义的场景（如实时数据）。
Java 
// 手动创建ThreadPoolExecutor（阿里规约要求，禁用Executors工厂方法）
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2,                          // corePoolSize：核心2个线程
    5,                          // maximumPoolSize：最多5个线程
    30, TimeUnit.SECONDS,        // keepAliveTime + unit：非核心空闲30秒回收
    new ArrayBlockingQueue<>(100),  // workQueue：有界队列，容量100
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(), // threadFactory：命名线程
    new ThreadPoolExecutor.CallerRunsPolicy()  // handler：调用者执行
);

// 禁用Executors的原因：
// FixedThreadPool/SingleThreadPool → LinkedBlockingQueue无界 → 队列无限增长 → OOM
// CachedThreadPool → SynchronousQueue不存储 → 线程无限创建 → OOM
// ScheduledThreadPool → DelayedWorkQueue无界 → OOM
线程池 ≈ 公司用人策略：正式工(core)→候客大厅(队列)→临时工(非核心)→拒之门外(拒绝策略)。核心线程不会主动招临时工，而是先让客户排队，大厅满了才招临时工。这个顺序面试经常被问反。
线程池的七大参数分别是什么？任务提交后的执行流程是怎样的？

七大参数：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（非核心线程空闲存活时间）、unit（时间单位）、workQueue（阻塞队列）、threadFactory（线程工厂）、handler（拒绝策略）。

执行流程：提交任务后：① 核心线程未满，创建核心线程执行；② 核心线程满，任务入队列等待；③ 队列满，创建非核心线程（直到maxPoolSize）执行；④ 线程达到maxPoolSize且队列满，触发拒绝策略。

易错点：很多人以为"先创建到max再入队列"，实际是"先入队列满了才创建非核心线程"。这是面试官常设的陷阱。

画纵向流程图加分。提"先入队列再创建非核心线程"这个易错点。再提阿里规约禁用Executors，体现工程规范意识。

1.2 synchronized vs ReentrantLock

两者都是Java实现线程同步的手段，但实现原理和功能差异很大。

synchronized的锁升级过程（JDK 6后优化）：synchronized不是一开始就是重量级锁，而是根据竞争激烈程度逐步升级，这是JDK6的重大优化。

synchronized锁升级过程：从无锁逐步升级到重量级锁，升级不可逆

ReentrantLock基于AQS实现：获取锁时CAS修改volatile state（0→1），成功则持有；失败则封装为Node入CLH队列park阻塞。释放锁时state-1（可重入），然后unpark后继节点。公平锁先检查队列有无前驱，非公平锁直接CAS抢锁。

对比维度synchronizedReentrantLock
实现层面JVM层面（monitorenter/monitorexit字节码）API层面（AQS + CAS + CLH队列）
锁释放自动释放（出代码块/方法自动释放）手动unlock（必须放finally，否则死锁）
可中断不可中断（等待时不能被打断）lockInterruptibly()可响应中断
公平锁非公平（不允许插队）可公平(new ReentrantLock(true))可非公平
条件变量1个wait/notify多个Condition，可精确唤醒
tryLock不支持tryLock(timeout)超时获取
性能JDK6后锁升级优化，差距不大竞争激烈时更稳定可控

选择原则：简单同步用synchronized（代码简洁、不会忘记释放锁、JVM自动优化）；需要公平锁、可中断、tryLock超时、多条件变量(Condition)时用ReentrantLock。

synchronized和ReentrantLock的区别？什么场景用哪个？

核心区别：synchronized是JVM关键字，自动释放锁，经过JDK6偏向锁/轻量级锁/重量级锁升级优化后性能不错；ReentrantLock是API级别的锁，基于AQS实现，需手动释放(必须finally)，但支持公平锁、可中断、tryLock超时、多Condition。

选择：简单同步用synchronized（简洁、不漏释放）；需要公平排队、可中断、超时获取、多条件变量精确唤醒时用ReentrantLock。实际项目中大部分场景synchronized够了，需要高级功能才上ReentrantLock。

提JDK6锁升级（无锁→偏向→轻量→重量级），展示JVM优化理解。说"大部分场景synchronized够了"体现务实。

1.3 volatile与CAS

volatile原理：Java内存模型(JMM)规定每个线程有自己的工作内存（CPU缓存），共享变量存在主内存。线程读写共享变量时先操作工作内存的副本，再同步到主内存，这会导致可见性问题——一个线程改了变量，另一个线程可能看到的还是旧值。

JMM内存模型：volatile通过内存屏障保证修改立即对其他线程可见

volatile通过内存屏障实现：写操作后插入StoreLoad屏障，强制刷回主内存；读操作前插入LoadLoad屏障，强制从主内存重新读。同时禁止指令重排序（如单例的双重检查锁必须用volatile防止"半初始化"问题）。

volatile不保证原子性：i++实际是"读取i→加1→写回i"三步操作，volatile只保证每次读的是最新值，但中间可能被其他线程打断。需要原子性用Atomic类（底层CAS）或synchronized。

CAS(Compare And Swap)原理：CAS(V, expected, new)——如果变量V的当前值等于expected，就更新为new，否则不更新，返回当前值。整个过程是原子的（CPU的cmpxchg指令保证）。CAS是自旋的——失败就重试，不阻塞线程。

Java 
// volatile：保证可见性 + 禁止指令重排，不保证原子性
private volatile boolean running = true;  // 状态标志位，其他线程能立即看到修改

// CAS：AtomicInteger 底层是 Unsafe.compareAndSwapInt
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();  // 底层CAS自旋：while(!CAS(value, old, old+1))

// CAS三大问题：
// 1. ABA问题：值从A→B→A，CAS以为没变过。解决：AtomicStampedReference加版本号
// 2. 自旋开销大：高竞争下不断CAS失败重试。解决：LongAdder分段CAS(分散热点)
// 3. 只能保证单变量原子：多个变量不能一起CAS。解决：AtomicReference包装成对象
volatile能保证原子性吗？CAS有什么问题？

volatile不保证原子性。volatile通过内存屏障保证可见性（修改立即刷回主内存+其他线程强制重读）和有序性（禁止指令重排）。但i++是读-改-写三步操作，volatile只保证每次读的是最新值，中间可能被打断。需要原子性用Atomic类(底层CAS)或synchronized。

CAS三大问题：① ABA问题（值A→B→A，CAS以为没变，用AtomicStampedReference加版本号解决）；② 自旋开销大（高竞争下不断重试，用LongAdder分段CAS分散热点）；③ 只能保证单变量原子（多变量用AtomicReference包装对象）。

提"单例双重检查锁必须用volatile"（防止半初始化）说明你理解指令重排。提"LongAdder分段CAS"展示高并发优化知识。

1.4 AQS (AbstractQueuedSynchronizer)

AQS是Java并发包的核心框架，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock都基于它实现。理解AQS就能理解JUC的大部分锁机制。

AQS核心设计：

  • volatile int state：同步状态变量。不同实现赋予不同含义——ReentrantLock中state表示锁被重入了几次(0=未持有, 1=持有1次, 2=重入2次)；Semaphore中state表示剩余许可数；CountDownLatch中state表示还剩多少个计数。
  • CLH双向队列：一个FIFO双向链表，存放的是获取锁失败后被park阻塞的线程节点。每个Node封装了一个线程引用和一个等待状态。
  • 独占模式 vs 共享模式：独占模式同一时刻只有一个线程能获取到资源(ReentrantLock)；共享模式可以多个线程同时获取(Semaphore/CountDownLatch)。
AQS核心结构：volatile state + CLH双向队列，park阻塞/unpark唤醒
AQS的原理是什么？ReentrantLock是怎么基于AQS实现的？

AQS核心是volatile int state表示同步状态 + CLH双向FIFO队列管理等待线程。获取锁时先CAS修改state，成功则持有锁；失败则封装为Node入CLH队列，调用LockSupport.park()阻塞当前线程。释放锁时修改state，然后unpark队首的后继节点，被唤醒的线程重新尝试CAS获取。

ReentrantLock的NonfairSync/FairSync继承AQS，重写tryAcquire/tryRelease。state表示锁重入次数(0=未持有, ≥1=重入次数)。公平锁tryAcquire先判断队列有无前驱(hasQueuedPredecessors)，有则排队不抢；非公平锁直接CAS抢锁。

提CLH队列、park/unpark(LockSupport)、独占vs共享模式，展示源码级理解。提"公平锁先查队列前驱"说明你知道公平和非公平的具体差异。

1.5 ThreadLocal

ThreadLocal不是解决共享问题的，而是隔离问题的——每个线程有独立的变量副本，互不干扰。

原理：每个Thread对象内部有一个ThreadLocalMap（类似HashMap），ThreadLocal.set(value)实际是把值存到当前线程的ThreadLocalMap里，key是ThreadLocal对象本身(弱引用)，value是用户存的对象(强引用)。

内存泄漏原因：ThreadLocalMap的key是WeakReference，当ThreadLocal对象无外部强引用时被GC回收，key变成null。但value是强引用，只要线程不结束(线程池中线程长期存活)，value就不会被回收，导致内存泄漏。解决：用完必须remove()。

Java 
// 典型场景：用户上下文传递(避免方法参数层层传)
private static final ThreadLocal<UserContext> CONTEXT = new ThreadLocal<>();

// 拦截器中设置用户上下文
public void preHandle(HttpServletRequest req) {
    User user = parseUser(req.getHeader("Authorization"));
    CONTEXT.set(user);  // 存到当前线程的ThreadLocalMap
}

// Service层直接获取，不用通过参数传
public void doBusiness() {
    User user = CONTEXT.get();  // 从当前线程取
    // ...
}

// 拦截器后置处理：必须remove！
public void afterCompletion() {
    CONTEXT.remove();  // 防止内存泄漏 + 线程池复用时数据串
}
线程池场景特别注意：线程被复用，如果上一个用户设了ThreadLocal没remove，下一个用户可能读到上一个用户的数据！这是线程池+ThreadLocal最常见的bug。

1.6 CompletableFuture

CompletableFuture是Java 8引入的异步编程工具，支持链式编排、组合多个异步任务、异常处理，比Future(get阻塞)强大得多。

Java 
// 场景：并行调用用户服务和订单服务，合并结果
CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> {
    return userService.getUser(userId);  // 异步查用户
}, executor);

CompletableFuture<Order> orderFuture = CompletableFuture.supplyAsync(() -> {
    return orderService.getOrder(orderId);  // 异步查订单
}, executor);

// 两个都完成后合并结果(thenCombine)
CompletableFuture<String> result = userFuture.thenCombine(orderFuture, (user, order) -> {
    return user.getName() + "的订单：" + order.getAmount();
});

// allOf等所有完成 / anyOf任一完成
CompletableFuture.allOf(future1, future2, future3).join();

// 异常处理：exceptionally(类比try-catch)
future.exceptionally(ex -> {
    log.error("调用失败", ex);
    return defaultValue;  // 兜底返回默认值
});

常用API：supplyAsync(异步执行有返回值) → thenApply(转换结果) → thenCombine(合并两个) → whenComplete(完成回调) → exceptionally(异常兜底)。注意默认用ForkJoinPool.commonPool()，生产环境建议传自定义线程池。

二、JVM虚拟机 ⭐⭐⭐ 必考

JVM是面试中考察"内功"的核心。重点是内存模型、GC机制、类加载。

2.1 JVM内存模型

JVM运行时数据区分为5个区域，其中堆和方法区是线程共享的，栈/本地方法栈/程序计数器是线程私有的。

  • 堆(Heap)：存放对象实例和数组，GC主战场。分为新生代(Eden+S0+S1)和老年代。OOM: Java heap space。
  • 虚拟机栈(VM Stack)：线程私有，每个方法调用创建一个栈帧(局部变量表+操作数栈+动态链接)。递归过深报StackOverflowError。
  • 方法区/元空间(Method Area/Metaspace)：存类信息、常量池、静态变量。JDK7前叫永久代(PermGen，堆内)，JDK8改为元空间(用本地内存，不易OOM)。OOM: Metaspace(动态生成类太多，如CGLib)。
  • 本地方法栈(Native Method Stack)：服务native方法的栈，和虚拟机栈类似。
  • 程序计数器(PC Register)：记录当前执行的字节码行号。唯一不会OOM的区域。
JVM运行时数据区(JDK8+)：堆/元空间共享，栈/本地方法栈/PC私有

2.2 GC算法与垃圾收集器

判断对象是否存活：JVM用可达性分析算法——从GC Roots出发，顺着引用链遍历，能遍历到的对象存活，遍历不到的是垃圾。

GC Roots包括：①虚拟机栈中引用的对象(局部变量)；②方法区中静态变量引用的对象；③方法区中常量引用的对象；④JNI(native方法)引用的对象。

三种GC算法：

  • 标记-清除(Mark-Sweep)：先标记所有存活对象，然后清除未标记的。缺点：产生内存碎片，大对象找不到连续空间时提前触发Full GC。
  • 复制(Copying)：把存活对象复制到另一半，然后清空原来那半。优点：无碎片。缺点：浪费一半空间。新生代用这个(因为新生代98%对象都是朝生夕死)。
  • 标记-整理(Mark-Compact)：标记后把存活对象向一端移动。优点：无碎片。缺点：移动对象慢(要更新引用)。老年代用这个。

分代收集策略：新生代(Eden:S0:S1=8:1:1)用复制算法——Eden满时Minor GC，存活对象复制到S0，下次Eden+S0的存活对象复制到S1，交替使用。老年代用标记-整理。

G1收集器：JDK9默认。打破物理分代，将堆划分为2048个Region(每个1-32MB)，每个Region可以是Eden/Survivor/Old/Humongous。G1通过记录每个Region的垃圾价值(回收可获得的空间)，在有限停顿时间内优先回收价值最高的Region(Garbage First)。SATB标记存活对象，可预测停顿(-XX:MaxGCPauseMillis)。

ZGC：JDK11+。染色指针技术(在64位指针的几位标记对象状态)，读屏障(在读引用时更新指针)，实现<10ms停顿，支持TB级堆。

G1和CMS有什么区别？为什么JDK9默认用G1？

CMS：老年代收集器，标记-清除算法，低停顿但有三个问题——①内存碎片(标记-清除不整理)；②浮动垃圾(并发标记期间产生的新垃圾本次回收不了)；③Concurrent Mode Failure退化为Serial Old(Full GC，STW很长)。

G1：把堆分成2048个Region(逻辑分代物理不分代)，整体标记-整理+局部复制，无内存碎片。核心优势是可预测停顿：-XX:MaxGCPauseMillis设定期望停顿时间，G1优先回收垃圾最多的Region(Garbage First)。

JDK9默认G1因为CMS有碎片和并发失败风险，G1在停顿可控性和吞吐量上更均衡。JDK14直接移除了CMS。

提Region分区、SATB标记、Garbage First(优先回收价值最高Region)这三个关键词。提"JDK14移除CMS"展示版本跟进。

2.3 类加载机制与双亲委派

类加载过程：加载(读取class文件到内存)→验证(格式/元数据/字节码/符号引用验证)→准备(为静态变量分配内存赋默认值0)→解析(符号引用→直接引用)→初始化(执行<clinit>静态代码块和静态变量赋值)。使用→卸载。

双亲委派模型：收到类加载请求时先委派给父加载器，父加载不到才自己加载。层级：Bootstrap(C++加载rt.jar)→Extension(ext目录)→Application(classpath)→Custom(自定义)。作用：①安全性(防止核心类被篡改，java.lang.String只能Bootstrap加载)；②唯一性(同一类只加载一次)。

打破双亲委派的场景：

  • Tomcat：每个WebApp有独立的WebappClassLoader，先自己加载(实现应用隔离)，加载不到再委派父。这样同一个Tomcat部署的应用可以用不同版本的Spring。
  • SPI机制：如JDBC的DriverManager由Bootstrap加载，但要加载第三方Driver(不在rt.jar)，用Thread.currentThread().getContextClassLoader()打破委派。
  • 热部署：OSGi/热部署通过自定义ClassLoader每次重新加载新的class实现。
双亲委派：先向上委派，父加载不了才自己加载；Tomcat反其道而行

三、Spring生态 ⭐⭐⭐ 必考

3.1 IoC与AOP原理

IoC(Inversion of Control)：控制反转——对象的创建和依赖关系不再由程序员手动new，而是交给Spring容器管理。"反转"体现在：对象创建的控制权从应用代码转移到了容器。DI(依赖注入)是IoC的实现方式，有构造器注入(推荐)、setter注入、字段注入(@Autowired)。

Bean生命周期(完整6步)：

  1. 实例化：反射调用构造器创建对象(此时属性还是null)
  2. 属性注入：populateBean()填充依赖(此时@Resource/@Autowired注入的依赖被设置)
  3. Aware接口回调：如果Bean实现了BeanNameAware→setBeanName()，BeanFactoryAware→setBeanFactory()，ApplicationContextAware→setApplicationContext()
  4. BeanPostProcessor前置：postProcessBeforeInitialization()。@PostConstruct在此执行
  5. 初始化：InitializingBean.afterPropertiesSet() → init-method
  6. BeanPostProcessor后置：postProcessAfterInitialization()。AOP代理就在这里创建——AbstractAutoProxyCreator在此把原始Bean包装成代理对象

使用→销毁：DisposableBean.destroy() → destroy-method / @PreDestroy

AOP原理：Spring AOP基于动态代理，有两种方式：

  • JDK动态代理：目标类必须实现接口，Proxy.newProxyInstance()生成代理类(基于InvocationHandler)。Spring默认有接口时用这个。
  • CGLIB代理：通过生成目标类的子类实现(无需接口，基于MethodInterceptor)。目标类没接口时用这个。spring.aop.proxy-target-class=true强制CGLIB。
Java 
// JDK动态代理：接口必须存在
Proxy.newProxyInstance(classLoader, new Class[]{UserService.class}, (proxy, method, args) -> {
    // @Before
    Object result = method.invoke(target, args);  // 执行目标方法
    // @After
    return result;
});

// CGLIB：生成子类，无需接口
// 不能代理final类和final方法
AOP ≈ Java的Filter/Interceptor链：在不修改业务代码的情况下，横向切面增强(日志/事务/权限)。JDK代理 ≈ MyBatis Mapper接口(动态生成实现)，CGLIB代理 ≈ 继承重写。
Spring Bean的完整生命周期是怎样的？AOP代理在哪一步创建？

实例化(构造器)→属性注入(populateBean)→Aware接口回调(BeanNameAware等)→BeanPostProcessor前置(postProcessBeforeInitialization，@PostConstruct在此)→初始化(afterPropertiesSet/init-method)→BeanPostProcessor后置(postProcessAfterInitialization)→使用→销毁。

AOP代理在BeanPostProcessor后置处理时创建——AbstractAutoProxyCreator在postProcessAfterInitialization中判断Bean是否需要代理，需要则用JDK动态代理或CGLIB把原始Bean包装成代理对象返回，容器里存的是代理对象而非原始对象。

重点强调"后置处理=AOP代理入口"体现IoC和AOP的关联。说"容器里存的是代理对象"展示理解深度。

3.2 SpringBoot自动配置原理

@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan。自动配置的核心是@EnableAutoConfiguration里的@Import(AutoConfigurationImportSelector.class)，它读取所有jar包中META-INF/spring.factories文件里EnableAutoConfiguration对应的类，然后通过@ConditionalOnXxx条件注解判断是否需要装配。

public class App { ... }

// @EnableAutoConfiguration 内部
@Import(AutoConfigurationImportSelector.class)
// selectImports(): 读取 META-INF/spring.factories 中 EnableAutoConfiguration 的所有类
// → 过滤去重 → @ConditionalOnXxx 条件判断 → 满足条件的才装配到容器

// 典型条件注解
@ConditionalOnClass(DataSource.class)        // classpath有该类才装配
@ConditionalOnMissingBean(DataSource.class)  // 容器没有该Bean才装配(用户没自定义就用默认)
@ConditionalOnProperty(prefix="spring.datasource", name="url")  // 配置存在才装配

// SpringBoot 3.x 改用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

3.3 事务传播机制

事务传播解决的是"一个事务方法调用另一个事务方法时，两个事务如何协调"的问题。

传播行为说明场景
REQUIRED(默认)当前有事务就加入，没有就新建绝大多数场景——方法A有事务调方法B，B加入A的事务，一起成功或一起回滚
REQUIRES_NEW无论如何都新建独立事务，挂起当前事务日志记录——即使主事务回滚日志也要保存
NESTED当前有事务就创建保存点(嵌套)，没有就新建部分回滚——子事务可回滚到保存点不影响主事务
SUPPORTS有事务就加入，没有就非事务运行查询方法——有事务环境就用事务读(一致性)，没有也能跑
NOT_SUPPORTED非事务运行，挂起当前事务耗时操作不想占用事务连接——如调外部API
MANDATORY必须在事务中调用，否则抛异常强制要求调用方有事务的方法(如转账核心逻辑)
NEVER不能在事务中调用，否则抛异常不允许有事务的操作(如初始化)
@Transactional失效的6种场景：①非public方法(AOP代理只拦截public)；②自调用this.xxx()(不走代理，代理对象没参与)；③异常被catch吞掉(代理看不到异常就不回滚)；④rollbackFor默认只回滚RuntimeException/Error(Checked异常不回滚，需rollbackFor=Exception.class)；⑤传播行为NOT_SUPPORTED/NEVER；⑥数据库引擎不支持事务(MyISAM)。

四、数据库核心 ⭐⭐⭐ 必考

4.1 MySQL索引（B+树）

B+树是多路平衡搜索树，MySQL InnoDB索引的底层数据结构。关键特性：非叶子节点只存索引键(不存数据)，单节点能存更多键，树更矮(3-4层存千万数据，每次查询3-4次磁盘IO)；叶子节点存数据+双向链表，范围查询(如BETWEEN)只需找到起点然后顺着链表走。

聚簇索引vs非聚簇索引：聚簇索引(InnoDB主键)的叶子节点存完整数据行，查主键直接拿到数据；非聚簇索引(二级索引)的叶子节点存主键值，需要"回表"(用主键再查一次聚簇索引)。如果查询的列全在二级索引里(如SELECT id,name WHERE name=...)，不需要回表，这叫覆盖索引。

索引失效场景：①违反最左前缀(联合索引(a,b,c)没a不走索引)；②索引列做运算/函数(WHERE YEAR(time)=2026)；③隐式类型转换(varchar列用int查)；④LIKE左模糊('%abc')；⑤OR一侧无索引；⑥NOT IN。

为什么MySQL索引用B+树而不是B树或Hash？

vs B树：B+树非叶子节点不存数据，同尺寸磁盘页能存更多索引键，树更矮，磁盘IO更少。叶子双向链表，范围查询高效(B树需中序遍历回溯)。

vs Hash：Hash等值查询O(1)快，但不支持范围查询(BETWEEN/>/<)、排序(ORDER BY)、最左前缀匹配。数据库大量场景是范围+排序，B+树更通用。

vs 红黑树：二叉树每节点2个子节点，树太高。B+树多路(扇出大)，3-4层存千万数据。

提"16KB页大小"、"扇出(fanout)"、"3-4层存千万"这些具体数字。提InnoDB页大小16KB展示存储层理解。

4.2 事务隔离级别与MVCC

四种隔离级别：READ UNCOMMITTED(脏读)→READ COMMITTED(不可重复读)→REPEATABLE READ(幻读)→SERIALIZABLE。MySQL默认RR，通过MVCC+间隙锁解决幻读。

MVCC(多版本并发控制)：通过undo log版本链+ReadView实现快照读(读写不阻塞)。每行隐藏字段：trx_id(最后修改事务ID)、roll_ptr(指向undo log的指针)。每次修改生成undo log，形成历史版本链表。ReadView包含当前活跃事务列表，判断版本可见性：trx_id < min(已提交)可见，trx_id > max(未来的)不可见，在活跃列表中(未提交)不可见。RC每次SELECT生成新ReadView(能看到最新已提交)，RR事务开始时生成复用(快照一致)。

4.3 分库分表

什么时候分：单表数据量超过千万级、查询性能明显下降、单库无法支撑并发量时。先加索引→读写分离→最后才分库分表(不要一上来就分)。

怎么分：垂直分库(按业务拆)、垂直分表(热列冷列分离)、水平分库(按user_id取模分到不同库)、水平分表(按规则拆成多表)。分片键选查询最频繁+分布均匀的字段。分后的难题：跨库JOIN(应用层组装/冗余字段)、分布式事务(Seata)、全局唯一ID(Snowflake)、跨库分页(查所有库合并)。

5.1 Kafka vs RabbitMQ

维度KafkaRabbitMQ
定位分布式流处理平台(日志/事件)消息代理(AMQP协议)
吞吐量百万级/秒万级/秒

Kafka高吞吐原因：①顺序写磁盘(磁盘顺序写接近内存写)；②零拷贝sendfile(页缓存直接到网卡，不经用户态)；③批量(生产者批量发送+压缩)；④Partition分区并行(多分区分散到多Broker)。

消息不丢三端保障：生产端(acks=all+retries+幂等)、Broker端(副本+ISR+min.insync.replicas≥2)、消费端(关闭自动提交offset，处理完手动提交)。

5.2 幂等消费

消息队列通常是At-Least-Once(至少一次)，可能重复投递。消费端必须幂等(重复消费和一次消费效果一样)。

Java 
// 1. 唯一消息ID + Redis去重(推荐)
if (redis.setIfAbsent("msg:" + msgId, "1", 24, HOURS)) {
    processMessage(msg);  // 首次消费才处理
}

// 2. 数据库唯一约束(兜底)
// INSERT IGNORE INTO consume_record(msg_id) VALUES(?)

// 3. 状态机校验(业务幂等)
if (order.getStatus() == OrderStatus.UNPAID) {
    order.pay();  // 只有未支付状态才执行
}

实际项目通常组合用：Redis去重(快速过滤)+DB唯一约束(兜底保障)。At-Least-Once + 幂等 = Exactly-Once。

  • 线程池7参数+流程：core/max/keepAlive/unit/queue/factory/handler。流程：核心满→入队列→队列满→非核心→max满→拒绝。禁用Executors
  • 锁升级：无锁→偏向锁(单线程CAS记ID)→轻量级锁(多线程自旋)→重量级锁(OS互斥量park)，升级不可逆
  • synchronized vs ReentrantLock：JVM自动释放vs API手动释放，公平/可中断/tryLock/多Condition用ReentrantLock
  • volatile：保证可见性+禁止重排，不保证原子性(i++三步)。CAS无锁原子但有ABA/自旋开销/单变量问题
  • AQS：volatile state + CLH双向队列，park阻塞/unpark唤醒。ReentrantLock/Semaphore/CountDownLatch基础
  • ThreadLocal：ThreadLocalMap(key弱引用value强引用)，用完必须remove()防泄漏+防线程池串数据
  • JVM内存：堆(GC主战场)/栈(SOF)/元空间(本地内存)/本地方法栈/PC(不OOM)。JDK8永久代→元空间
  • GC：GC Roots可达性分析。新生代复制算法(Eden:S0:S1=8:1:1)，老年代标记整理。G1(Region+Garbage First+可预测停顿) / ZGC(染色指针<10ms)
  • 双亲委派：先委派父加载器，保证安全+唯一。Tomcat/SPI/热部署打破
  • Bean生命周期：实例化→注入→Aware→BPP前(@PostConstruct)→初始化→BPP后(AOP代理创建)→使用→销毁
  • SpringBoot自动配置：spring.factories + @ConditionalOnXxx条件装配，约定大于配置
  • 事务传播：REQUIRED(默认)/REQUIRES_NEW(独立)/NESTED(保存点)。失效：非public/自调用/吞异常/rollbackFor
  • MySQL B+树：非叶子只存索引(省空间)，叶子存数据+双向链表(范围查询快)，3-4层存千万数据
  • MVCC：undo log版本链 + ReadView，RC每次新ReadView，RR事务开始时生成复用
  • 消息幂等：Redis唯一ID去重+DB唯一约束+状态机校验，At-Least-Once + 幂等 = Exactly-Once
