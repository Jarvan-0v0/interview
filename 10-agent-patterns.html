CHAPTER 08

Agent 设计模式与工程化

🎯 学习目标：掌握单Agent与多Agent协作的三种核心模式（Supervisor-Worker/Pipeline/Router），理解Agent状态管理与检查点持久化，能从Java工程视角类比错误处理（Spring Retry+Circuit Breaker）、可观测性（链路追踪）、安全边界（Human-in-the-loop）和成本控制，讲清"Java工程经验如何迁移到Agent开发"。

Agent工程化 = 把"能跑的Demo"变成"可上线的产品"——这恰恰是Java后端工程师的主场：状态管理、错误重试、链路追踪、成本控制，全是老朋友换了个场景。

1. 单Agent模式 ★★★★☆

最简单的Agent架构：一个LLM + 一组Tools，LLM自主决定调哪个工具、调几次、何时停止。

单Agent = 一个大脑 + 多只手

  • 大脑：一个LLM实例，负责理解意图、规划步骤、决策调哪个Tool
  • 手：多个Tool（搜索/数据库/API/计算器…），LLM按需调用
  • 循环：LLM思考→选Tool→执行→看结果→再思考→…→输出最终答案

适用场景

  • 任务单一明确（如"客服问答""文档总结"）
  • 工具数量不多（5-10个），LLM能管过来
  • 不需要并行处理多个子任务
单Agent的局限：①工具太多时LLM选错工具概率上升（"选择困难症"）；②一个Agent干所有事，Prompt越来越臃肿；③无法并行——一个任务卡住全卡住；④上下文窗口有限，长对话会丢失前文。复杂任务就该拆成多Agent。
单Agent ≈ 一个Controller调多个Service。Controller（LLM）决定调哪个Service（Tool），所有逻辑在一个类里。简单CRUD够用，但业务复杂了就得拆——这就是多Agent的动机，和Java"大类拆小类"同理。

2. 多Agent协作模式 ★★★★★ 必考

复杂任务拆给多个Agent各司其职，三种经典协作模式，面试必问。

图8-1 三种多Agent协作模式：Supervisor-Worker(分发汇总) / Pipeline(串行流水线) / Router(意图路由)
模式Java类比结构适用场景
Supervisor-Worker Master-Worker / Fork-Join 一个Supervisor分发任务给多个Worker并行执行，汇总结果 可拆分并行子任务（如多文档同时总结、多源搜索）
Pipeline 责任链模式 / Filter Chain 数据依次流过多个Agent，每个处理一步，串行传递 有明确步骤的流程（如：检索→分析→总结→格式化）
Router 策略模式 + 路由表 Router Agent判断意图，只路由给一个最合适的Agent处理 多场景入口（如：客服/分析/闲聊按意图分流）
这三种模式Java里全有对应：Supervisor-Worker = ForkJoinPool分叉合并；Pipeline = Servlet的Filter Chain / Spring的HandlerInterceptor链；Router = Spring MVC的HandlerMapping按URL路由到不同Controller。Agent的多Agent协作不是新概念，是设计模式在LLM场景的重用。

2.1 Supervisor-Worker模式详解

工作原理：Supervisor Agent接收完整任务后，先做任务分解——把大任务拆成多个独立子任务，每个子任务分给一个Worker Agent。Worker各自独立执行（可并行），完成后把结果回报给Supervisor，Supervisor做结果汇总——合并、去重、综合判断，输出最终答案。关键点：Supervisor不执行具体工作，只负责"拆任务+收结果"；Worker不需要知道全局，只处理分到的子任务。这和ForkJoinPool的fork()分叉→compute()并行→join()合并结构完全一致。

适用场景：任务能并行拆分且子任务间无强依赖。例如"总结10篇文档"——Supervisor拆成10个子任务分给10个Worker各总结一篇，再汇总；"多源搜索"——Worker A搜知识库、Worker B搜外部API、Worker C搜历史对话，Supervisor合并三路结果。不适用：子任务有严格顺序依赖的（那应该用Pipeline）。

Java类比：ForkJoinPool + RecursiveTask。Supervisor=父任务fork出子任务，Worker=子任务compute()，汇总=join()。或者类比Master-Worker模式（Hadoop MapReduce也是这个结构：Master分发Map任务给多个Worker，再汇总Reduce）。坑点也类似——Supervisor是单点瓶颈（一个LLM挂了全挂），Worker太多时Supervisor的汇总Prompt会超长（要压缩每个Worker的结果再喂给Supervisor）。

2.2 Pipeline模式详解

工作原理：数据像流水线一样依次流过多个Agent，每个Agent只处理一个步骤，上一步的输出是下一步的输入。例如"研报生成"Pipeline：Agent 1（检索资料）→Agent 2（数据分析）→Agent 3（撰写报告）→Agent 4（格式化输出）。每个Agent的Prompt只关注自己的步骤，职责单一、Prompt精简。数据是串行流动的，前一步完成才能进下一步。

适用场景：任务有明确且固定的步骤，步骤间有顺序依赖。例如RAG本身就是个迷你Pipeline（检索→重排→生成）；客服工单处理（意图识别→信息抽取→知识库查询→回复生成）。不适用：步骤可并行或需要动态选择路径的（那应该用Router或Supervisor-Worker）。

Java类比：Servlet Filter Chain / Spring HandlerInterceptor链 / 责任链模式。每个Filter处理一道工序再传给下一个。坑点：①延迟累加——4个Agent串行总延迟=各步延迟之和，比并行慢；②一步错全链断——中间任何一步出错，后续步骤要么拿到错误输入要么直接中断，需要每步做错误处理和中间结果校验。好处是每步可独立测试和替换——换掉Agent 2不影响其他步，和换一个Filter一样。

2.3 Router模式详解

工作原理：Router Agent只做一件事——判断用户意图，然后路由给最合适的一个专项Agent。它不执行具体任务，相当于"前台调度员"。例如用户说"帮我查下订单"→Router判断是"订单查询"意图→路由给订单Agent；用户说"你们产品怎么用"→Router判断是"产品咨询"→路由给产品Agent。被路由到的Agent独立完成整个对话，各Agent之间互不干扰、互不通信。

适用场景：系统要服务多个不同场景，每个场景需要不同的Prompt/Tool/知识库。例如智能客服平台——退款、物流、产品咨询、闲聊各用一个专项Agent，Router按意图分流。不适用：单一场景（单Agent够用）或需要多Agent协作完成一个任务的（用Supervisor-Worker或Pipeline）。

Java类比：Spring MVC的HandlerMapping——根据URL路由到不同Controller；或策略模式——根据条件选一个Strategy执行。Router就是HandlerMapping，各专项Agent就是各Controller。坑点：Router的意图判断准确率是整条链路的上限——Router判断错了，分给错误的Agent，后面再怎么优化也没用。所以Router通常要用最强的模型（如GPT-4），而各专项Agent可以用便宜模型——这就是后面要讲的"贵模型决策+便宜模型执行"策略的典型应用场景。

选型提示：任务能并行拆→Supervisor-Worker；有固定步骤→Pipeline；多场景分流→Router。复杂系统常组合使用：外层Router分流，内层某条路由用Pipeline或Supervisor-Worker。

3. 状态管理 ★★★★☆

Agent不是"调一次就结束"的无状态函数——它要维护对话历史、中间结果、当前执行步骤等状态。状态管理是Agent能"连续对话"和"中断恢复"的基础。

Agent需要维护哪些状态

  • 对话历史：Message列表，多轮对话的上下文
  • 工具调用记录：调了哪些Tool、参数、返回值——用于调试和审计
  • 中间变量：Pipeline各步的中间结果，Supervisor分发的子任务状态
  • 执行进度：当前在第几步、是否在等待用户输入、是否出错

检查点（Checkpoint）持久化

Agent执行到关键节点时把当前状态序列化存盘（如存Redis/DB），这样：①进程崩了能从检查点恢复，不用从头跑；②长流程可以中断（如等用户确认）后续继续；③可以"时光倒流"回到某个状态重新执行（调试用）。

Agent状态管理 ≈ State模式 + 持久化到Redis。对话状态像HttpSession，存在服务端用sessionId关联；检查点≈分布式事务的Saga日志——每完成一步记一笔，崩了从最后成功步恢复。LangGraph的checkpoint机制和Saga补偿恢复本质一样。

4. 错误处理与重试 ★★★★★ 必考

Agent调用链长（LLM→Tool→外部API→LLM…），任何一环都可能出错。没有错误处理的Agent = "Demo级"，上不了生产。三类错误要分别处理：

错误类型原因处理策略
Tool调用失败 外部API超时/限流/参数错误 重试（指数退避）→ 降级（返回缓存/默认值）→ 熔断（暂停调用该Tool）→ 告知LLM换方案
LLM输出格式错误 LLM没按约定格式输出JSON/工具调用参数 解析重试（把错误信息喂回LLM让它修正）→ 结构化输出约束（JSON Schema/Outlines）→ 兜底正则提取
整体超时 Agent循环太久、LLM响应慢、死循环 设置maxSteps上限 → 超时返回当前最佳结果 → 异步转同步（先返回"处理中"再回调）
Java · Agent错误处理伪代码 
// Tool调用：重试 + 降级 + 熔断（和Spring Retry + Resilience4j一模一样）
@Retryable(maxAttempts = 3, backoff = @Backoff(delay = 1000, multiplier = 2))
@CircuitBreaker(failureRateThreshold = 0.5, waitDurationInOpenState = "30s")
public String callTool(String toolName, Map<String,Object> args) {
    try {
        return toolRegistry.execute(toolName, args);
    } catch (TimeoutException e) {
        return "工具调用超时，请尝试其他方式";  // 降级：返回提示
    }
}

// LLM输出格式修复：把解析错误喂回去让LLM自己改
for (int i = 0; i < 3; i++) {
    String raw = llm.generate(prompt);
    try {
        return jsonParser.parse(raw);  // 尝试解析
    } catch (ParseException e) {
        prompt += "\n你上次的输出格式有误：" + e.getMessage()
                + "\n请严格按JSON格式重新输出";  // 喂回错误让LLM修
    }
}
throw new AgentException("LLM输出格式修复3次仍失败");
Agent错误处理 ≈ Spring Retry + Resilience4j/Circuit Breaker。重试退避、熔断降级、超时兜底——Java工程师在微服务场景练了多年的手艺，直接平移到Agent的Tool调用上。LLM格式修复是新增的，但思路也是"异常→反馈→重试"，和"校验失败→返回错误信息→用户修正"同理。

4.1 Tool调用失败的降级策略详解

Tool调用失败在Agent中比传统微服务更常见——因为LLM生成的参数可能不规范（如日期格式错、必填字段缺失）、外部API本身限流、网络抖动。降级策略要分四级递进：①重试——指数退避重试2-3次，应对瞬时故障（限流/超时），和@Retryable一模一样；②参数修正重试——如果是参数错误，把错误信息（如"date格式应为yyyy-MM-dd"）喂回给LLM让它修正参数再调，这是Agent特有的、传统微服务没有的；③降级返回——重试仍失败则返回缓存结果或默认提示（如"该服务暂不可用，请稍后再试"），不让整条链路崩掉；④熔断+告知LLM换方案——连续失败触发熔断暂停该Tool，同时把"工具不可用"信息喂给LLM，让它改用其他Tool或换思路完成任务。

第④级是Agent降级最精妙的地方——LLM是自适应的。传统微服务熔断后调用方只能干等或走固定兜底逻辑；Agent熔断后把"工具不可用"告诉LLM，LLM能理解这个信息并主动调整策略。例如退款Tool熔断了，LLM收到"退款服务暂不可用"后，可能改为引导用户走人工退款流程，而不是直接报错。这相当于把"降级逻辑"从硬编码变成了"LLM动态决策"——更灵活，但也更不可控，所以高风险操作仍要人工兜底。

4.2 LLM输出格式错误的自动修复

LLM输出JSON格式错误是Agent开发的高频痛点——你要求输出{"action":"query","params":{"order_id":"123"}}，LLM可能输出带Markdown包裹的```json ... ```、多了个尾逗号、甚至直接输出自然语言。修复策略三层递进：①宽容解析——先用正则提取JSON片段（去掉Markdown包裹、截取第一个{到最后一个}），再用宽松JSON解析器（如容忍尾逗号、单引号）；②错误反馈重试——解析失败时把ParseException信息拼进Prompt（"你上次的输出：xxx，错误：缺少右括号，请严格按JSON重新输出"），让LLM自己改，重试2-3次；③结构化约束从源头防——用JSON Schema约束（如langchain4j的@AiService结构化输出、Outlines/grammar约束解码），让LLM物理上无法输出错误格式，比事后修复更可靠。

原则：预防优于治疗。能从源头用结构化输出约束的，就别事后解析修复。只有模型不支持结构化输出、或输出格式太复杂无法用Schema表达时，才退而求其次用"解析+反馈重试"。生产中推荐组合：结构化输出约束（预防90%的格式问题）+ 宽松解析（兜底剩余10%）+ 错误反馈重试（最后一道防线）。Java类比：这就像Bean Validation——能用@NotNull/@Pattern在入口校验的，就别等运行时异常再处理。

Agent错误处理决策流程图：按错误类型分流——Tool失败走重试→修正→降级→熔断四级，格式错误走解析→反馈→兜底三级，整体超时走maxSteps/异步兜底

5. 可观测性 ★★★★☆

Agent是"黑盒"——LLM内部决策不可解释、Tool调用链长、多轮循环。没有可观测性，出了问题只能瞎猜。四个维度必须监控：

维度监控什么Java类比
Token消耗 每次调用的input/output token数、累计消耗、按用户/任务统计 ≈ 接口调用量监控
延迟追踪 LLM响应时间、Tool执行时间、端到端延迟、P50/P99 ≈ 接口RT监控
决策链路 LLM每步选了哪个Tool、为什么选、参数是什么、返回什么 ≈ SkyWalking/Zipkin分布式链路追踪
成本控制 按模型计费（GPT-4贵、GPT-3.5便宜）、按用户限额、预算告警 ≈ 按调用方限流+计费

Agent决策链路追踪

像分布式链路追踪一样，给每次Agent执行打一个TraceId，记录每个Span：①LLM调用（输入Prompt→输出决策→耗时→token）；②Tool调用（工具名→参数→返回→耗时→是否成功）。这样出问题时能看到完整决策链："第2步LLM选了搜索Tool→搜了XX→返回空→第3步LLM决定换数据库Tool→…"，快速定位哪一步出了问题。

Agent可观测性 ≈ SkyWalking + Prometheus + Grafana。链路追踪（TraceId+Span）监控每次Agent的完整决策路径；Token消耗≈接口调用量；延迟P99≈RT监控；成本告警≈按调用方限流计费。Java工程师做APM的经验直接迁移，这是转Agent的核心优势——很多搞AI的不懂可观测性，你懂。

6. 安全边界 ★★★☆☆

Agent能调Tool就能执行真实操作（发邮件、改数据库、调支付API…），一旦失控后果严重。三道安全边界：

① Human-in-the-loop 人工确认

高风险操作（发邮件、退款、删除数据）不自动执行，先暂停等人工审批后再继续。Agent生成操作意图→推给人工确认→确认通过才执行Tool。这是Agent安全最核心的机制。

② 工具权限控制

不同用户/场景下Agent可用的Tool不同。如普通客服Agent不能调退款Tool，只有授权的Agent+人工确认才能。类似RBAC——给Agent也做工具级别的权限管控。

③ 输出过滤

LLM输出可能含敏感信息、越权内容、Prompt注入攻击。对最终输出做过滤：敏感词检测、PII脱敏、内容安全审核。防止Agent被"骗"执行恶意操作或泄露不该泄露的信息。

安全边界 ≈ Spring Security + 审批流。工具权限=RBAC的@PreAuthorize；Human-in-the-loop=OA审批流（提交→审批→执行）；输出过滤=Filter做敏感词/脱敏。全是Java安全工程的老套路，换到Agent场景一样适用。

7. Agent工程化最佳实践 ★★★★☆

① 模型选型：贵的做决策，便宜的做执行

不是所有步骤都需要GPT-4。Router/Supervisor等"决策"角色用贵的大模型（判断准），Worker/执行类Agent用便宜的小模型（够用就行）。如：Router用GPT-4判断意图→路由给客服Agent用GPT-3.5回答。成本能降一个数量级。

7.1 模型选型策略详解

核心原则是"按角色配模型"——不同Agent角色对模型能力要求不同，用最贵的模型干所有事是浪费。具体策略分四档：①决策类角色（Router/Supervisor/Planner）用顶级模型（GPT-4/Claude-3.5-Sonnet）——这类角色需要强推理、少幻觉、判断准，一次判断错了全链路就错了，值得花钱；②执行类角色（Worker/专项Agent）用中端模型（GPT-3.5/GLM-4/DeepSeek）——执行类任务通常是"按已定好的流程做"，对推理要求低，中端模型够用；③简单格式化/摘要用小模型（GPT-3.5/开源7B模型）——这类任务几乎不需要推理，小模型又快又便宜；④兜底/离线批处理用自部署开源模型（Qwen2/Llama3）——不调API零成本，适合离线大批量任务（如批量摘要历史文档）。

怎么落地：在langchain4j里给不同Agent注入不同的ChatLanguageModel实现——Router注入OpenAI的gpt-4，Worker注入gpt-3.5-turbo，兜底注入本地Ollama跑的Qwen2。成本对比实例：纯GPT-4方案每千次对话约$20，"GPT-4决策+GPT-3.5执行"方案约$3（GPT-4只在Router那一步用，占比10%），降了85%。但要注意能力匹配——执行类Agent如果任务复杂（需要多步推理/复杂Tool选择），用太弱的模型反而出错率高，省了模型钱赔了质量。所以选型后必须跑Golden Set验证：换便宜模型后通过率不能掉超过2-3个百分点，否则说明这个角色需要更强的模型。

Java类比：这就像不同接口用不同规格的机器——核心交易接口上高配CPU+大内存的服务器，边缘查询接口上廉价机器。不是所有接口都配顶配，按"这个接口对准确性的要求有多高"来配。Agent的模型选型同理：按"这个Agent角色对推理能力的要求有多高"来配模型。

模型选型策略图：决策类用顶级模型($$$)、执行类用中端($$)、格式化用小模型($)、兜底用自部署(免费)，组合降成本85%+

② 缓存策略

相同/相似问题的回答缓存复用。①精确缓存：相同问题直接返回历史答案（像HTTP缓存）；②语义缓存：用Embedding算问题相似度，超过阈值就返回历史答案（比精确缓存召回更多）。能大幅降低LLM调用次数和成本。

③ 并发控制

LLM API有QPS/并发限制，高并发下要：①限流（令牌桶/信号量控制并发数）；②排队（超限的请求进队列等）；③多模型/多Key负载均衡。和Java高并发三板斧——限流、降级、排队——完全一致。

模型选型≈不同接口用不同规格的机器（核心接口上好机器、边缘接口上廉价机器）；缓存≈Redis缓存热点数据；并发控制≈Sentinel限流+令牌桶。Agent工程化的每个最佳实践，Java后端都有现成经验对应。

面试场景演练

Q1：多Agent协作有哪些模式？

三种经典模式：①Supervisor-Worker——一个Supervisor分发任务给多个Worker并行执行再汇总，类似Java的Fork-Join，适合可拆分的并行子任务；②Pipeline——数据依次流过多个Agent，每个处理一步，类似责任链模式，适合有明确步骤的流程；③Router——Router Agent判断意图后只路由给一个最合适的Agent处理，类似策略模式+路由表，适合多场景分流。

复杂系统常组合使用：外层Router分流，内层某条路由用Pipeline或Supervisor-Worker。选型看任务特征：能并行→Supervisor-Worker，有固定步骤→Pipeline，多场景→Router。

能说出Java类比（Fork-Join/责任链/策略模式）是加分项——证明你不是背概念而是真理解。画三个结构图更佳。
Q2：Agent出错怎么处理？

分三类错误分别处理：①Tool调用失败（外部API超时/限流）——重试（指数退避）→降级（返回缓存/默认值）→熔断（暂停该Tool）→告知LLM换方案，和Spring Retry+Resilience4j一样；②LLM输出格式错误——把解析错误信息喂回给LLM让它修正，重试2-3次，或用JSON Schema/Outlines做结构化约束从源头防；③整体超时——设maxSteps上限防死循环，超时返回当前最佳结果或转异步处理。

核心思想：Agent的每个环节都要有try-catch+重试+降级+超时兜底，和微服务容错一个套路。

关键词："重试退避""熔断降级""格式修复喂回去""maxSteps防死循环"。类比Spring Retry+Circuit Breaker，面试官一听就知道你有工程底子。
Q3：怎么监控Agent的运行？

四个维度：①Token消耗——每次调用的input/output token、按用户/任务统计累计，做成本核算；②延迟——LLM响应时间、Tool执行时间、端到端P50/P99；③决策链路追踪——像SkyWalking一样给每次执行打TraceId，记录每个Span（LLM选了哪个Tool、参数、返回、耗时），出问题能看完整决策链定位；④成本告警——按用户限额、预算阈值告警。

工具上可以用LangSmith/LangFuse做Agent可观测性，也可以自己埋点接现有的Prometheus+Grafana+链路追踪体系。

重点讲"决策链路追踪"——这是Agent特有的、也是最难做的。类比SkyWalking分布式追踪，说明你懂"黑盒系统怎么变白盒"。
Q4：Agent系统怎么做成本控制？

三个层面：①模型选型——贵的模型（GPT-4）做决策/路由，便宜的（GPT-3.5/开源模型）做执行/生成，成本能降一个数量级；②缓存——精确缓存（相同问题直接返回历史答案）+语义缓存（用Embedding算问题相似度超阈值就复用），大幅减少LLM调用；③并发控制+限额——令牌桶限流防超QPS、按用户设token预算上限、超额告警/拒绝。

还可以加：短问题用小模型、长文档先摘要再处理（减少input token）、Tool结果截断只留关键字段（减少喂回LLM的token）。

"贵模型决策+便宜模型执行"是最高性价比的优化，一定要提。再补"语义缓存"和"按用户限额"就是实战级答法。
Q5：你的Java工程经验对Agent开发有什么帮助？

这是我的核心优势，几乎一一对应：①设计模式——多Agent协作的Supervisor-Worker/Pipeline/Router就是Fork-Join/责任链/策略模式，我做了4年Java一眼就能做架构映射；②错误处理——Spring Retry+Resilience4j的重试退避、熔断降级、超时兜底，直接平移到Agent的Tool调用；③可观测性——SkyWalking链路追踪、Prometheus监控的经验，用来做Agent决策链路追踪和Token/延迟监控，很多搞AI的不懂这块；④安全工程——Spring Security的RBAC权限、OA审批流、Filter脱敏，对应Agent的工具权限、Human-in-the-loop、输出过滤；⑤高并发——限流排队、多Key负载均衡、缓存策略，Agent面对LLM API限流时一样要用。
