第 05 章

LangChain4j框架详解 面试重点

🎯 学习目标：掌握LangChain4j整体架构、同步与流式模型、@AiService声明式接口、Tools工具调用机制、ChatMemory对话记忆、RAG支持及高级特性，能在面试中清晰阐述框架设计原理与底层机制。

1. LangChain4j整体架构 ★★★★☆

LangChain4j是Java生态的LLM应用开发框架，对标Python的LangChain。它采用经典的三层架构设计，借鉴了Spring的分层思想，让Java开发者能用熟悉的注解和接口方式构建AI应用。

三层架构的职责划分：最上层是应用层，开发者通过@AiService注解或AiServices Builder声明Agent接口，框架生成实现类，这一层屏蔽了所有底层细节。中间是核心层（langchain4j-core），它定义了所有能力的接口契约——ChatLanguageModel、EmbeddingModel、ChatMemory、EmbeddingStore、ContentRetriever、DocumentLoader等，核心层本身不依赖任何具体模型厂商。最底层是集成层，各种独立的模块（langchain4j-open-ai、langchain4j-ollama、langchain4j-milvus等）实现核心层接口，对接具体的模型、向量库和文档解析器。

这种分层带来两个工程价值：一是可替换性——换模型只换集成层的依赖和Builder，业务代码完全不动；二是可测试性——核心层是纯接口，可以用Mock实现做单测，不依赖真实LLM API。

LangChain4j = Spring Boot风格的LLM开发框架——核心层提供能力契约，集成层对接各种模型和存储，应用层用@AiService像写Bean一样开发Agent。

2. ChatLanguageModel vs StreamingChatLanguageModel ★★★☆☆

核心层提供两种调用LLM的接口：ChatLanguageModel（同步）和StreamingChatLanguageModel（流式）。它们对应同一套能力（生成对话），但返回机制完全不同。

同步模式：ChatLanguageModel.generate()是阻塞调用——发起HTTP请求后线程挂起，等待LLM把整个回答生成完毕，再一次性返回完整的Response<AiMessage>。这就像调用普通REST API，简单直接，但首字延迟高（3-10秒），用户体验差——用户盯着空白页面等待。

流式模式：StreamingChatLanguageModel.generate()是非阻塞回调——发起请求后立即返回，LLM每生成一个Token就通过StreamingResponseHandler回调推送。三个回调方法：onPartialResponse(String token)每来一个Token触发一次，onComplete(Response<AiMessage>)全部生成完触发，onError(Throwable)异常时触发。底层用的是HTTP的SSE（Server-Sent Events）或chunked transfer，连接保持打开，服务端持续推送。

为什么需要流式：人眼对延迟敏感，3秒空白会觉得"卡住了"，但3秒内逐字出现会觉得"正在思考"。所有主流ChatBot（ChatGPT、Claude、通义千问）都用流式输出，这是用户体验的刚需。

同步等全部生成再返回，流式逐Token回调——前者像REST API，后者像Server-Sent Events。
图5-2 同步阻塞返回 vs 流式逐Token回调对比
Java / langchain4j 
// 1. 同步模式——阻塞等待完整回复
ChatLanguageModel model = OpenAiChatModel.builder()
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .build();

String answer = model.generate("什么是Spring Boot？");
// 等待3-10秒后，一次性拿到完整回答

// 2. 流式模式——逐Token回调，实时显示
StreamingChatLanguageModel streamingModel = OpenAiStreamingChatModel.builder()
        .apiKey(System.getenv("OPENAI_API_KEY"))
        .build();

streamingModel.generate("什么是Spring Boot？", new StreamingResponseHandler() {
    @Override
    public void onPartialResponse(String token) {
        System.out.print(token);  // 逐Token输出
    }
    @Override
    public void onComplete(Response<AiMessage> response) {
        System.out.println("\n--- 完成 ---");
    }
    @Override
    public void onError(Throwable error) {
        error.printStackTrace();
    }
});

2.5 SSE流式输出：Agent的打字机效果 ⭐⭐⭐ 必考

大模型生成一个完整回答通常需要2-10秒，如果等全部生成再返回，用户体验极差。当前主流Agent/ChatBot全部采用SSE(Server-Sent Events)流式输出——LLM每生成一个token就立即推送到前端，用户看到"打字机效果"。

SSE = HTTP长连接 + 服务端逐条推送，比WebSocket简单(单向)，比轮询高效(不断开)，是LLM流式输出的标准方案。

SSE vs WebSocket vs 轮询

对比HTTP轮询SSEWebSocket
方向客户端拉服务端->客户端(单向)双向
协议HTTP(反复请求)HTTP(长连接)WS(升级协议)
实现复杂度低低(最简)高(握手/心跳/重连)
断线重连天然(每次新请求)浏览器自动重连需手动实现
代理友好✓✓(标准HTTP)✗(部分Nginx/CDN不支持)
适合LLM✗(延迟高)⭐ 最佳过重(LLM只需单向推送)
为什么Agent用SSE不用WebSocket：LLM流式输出是服务端->客户端的单向推送，用户不需要在生成过程中给LLM发消息。SSE用标准HTTP协议，Nginx/CDN/防火墙全兼容，实现最简单。WebSocket的双向能力在这里是浪费。

SSE协议原理

HTTP响应头 
HTTP/1.1 200 OK
Content-Type: text/event-stream    # SSE的核心：这个MIME类型
Cache-Control: no-cache                # 禁止缓存
Connection: keep-alive                 # 长连接
Access-Control-Allow-Origin: *        # 跨域(如果前后端不同域)

# 响应体格式：每条消息以 data: 开头，两个\n结尾
data: {"token": "你"}\n\n
data: {"token": "好"}\n\n
data: {"token": "，"}\n\n
data: {"token": "有什么"}\n\n
data: [DONE]\n\n    # 结束标记
SSE ≈ Java Servlet的AsyncContext + PrintWriter逐步flush()，但浏览器原生支持自动解析和重连。比WebSocket简单得多——不需要握手协议、不需要心跳维持、不需要处理帧(frame)。

Spring Boot实现SSE的两种方式

Java (Spring Boot SseEmitter) 
// 方式1：SseEmitter（Spring原生，推荐）
@GetMapping(value = "/chat/stream", produces = "text/event-stream")
public SseEmitter chatStream(@RequestParam String message) {
    // 超时设长一点，LLM生成可能要10秒+
    SseEmitter emitter = new SseEmitter(60_000L);
    
    // 异步调用流式模型
    CompletableFuture.runAsync(() -> {
        streamingModel.generate(message, new StreamingResponseHandler() {
            @Override
            public void onPartialResponse(String token) {
                try {
                    // 每生成一个token就推送到前端
                    emitter.send(SseEmitter.event()
                        .data(Map.of("token", token)));
                } catch (IOException e) {
                    emitter.completeWithError(e);
                }
            }
            
            @Override
            public void onComplete(Response<AiMessage> response) {
                emitter.send(SseEmitter.event().data("[DONE]"));
                emitter.complete();
            }
        });
    });
    
    return emitter;
}

// 方式2：Flux<ServerSentEvent>（WebFlux响应式，更优雅）
@GetMapping(value = "/chat/stream", produces = "text/event-stream")
public Flux<ServerSentEvent<String>> chatStream(@RequestParam String message) {
    return Flux.create(sink -> {
        streamingModel.generate(message, new StreamingResponseHandler() {
            @Override
            public void onPartialResponse(String token) {
                sink.next(ServerSentEvent.builder(token).build());
            }
            @Override
            public void onComplete(Response<AiMessage> response) {
                sink.next(ServerSentEvent.builder("[DONE]").build());
                sink.complete();
            }
        });
    });
}

Nginx配置SSE（必须！）

Nginx配置 
location /chat/stream/ {
    proxy_pass http://backend;
    
    # 关键1：关闭缓冲！否则Nginx会等全部生成再转发
    proxy_buffering off;
    proxy_cache off;
    
    # 关键2：支持HTTP/1.1长连接
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    
    # 关键3：超时设长（LLM生成可能10秒+）
    proxy_read_timeout 60s;
    
    # 关键4：禁用gzip（压缩会导致缓冲）
    gzip off;
}
最坑的问题：Nginx默认proxy_buffering on，会把SSE流缓冲到完整响应才转发——前端看到的是等10秒后一次性出现全部文字，完全失去流式效果。proxy_buffering off 是SSE必须的配置。

你的Agent流式输出是怎么做的？为什么用SSE不用WebSocket？

用SSE(Server-Sent Events)实现。后端Spring Boot用SseEmitter(或WebFlux的Flux<ServerSentEvent>)，langchain4j用StreamingChatLanguageModel逐token回调，每个token通过SseEmitter.send()推到前端。前端用浏览器原生EventSource API消费，逐token追加实现打字机效果。

用SSE不用WebSocket的原因：LLM流式输出是服务端->客户端的单向推送，SSE用标准HTTP协议，Nginx/CDN全兼容，浏览器原生支持自动重连，实现最简单。WebSocket的双向能力在这里是浪费，而且握手协议更复杂、部分代理不兼容。

关键配置是Nginx必须proxy_buffering off，否则流被缓冲成一次性返回。

能说出"SSE是单向推送所以够用"和"Nginx buffering off"这两个关键点就够了。再提一句EventSource只支持GET、POST要用fetch+ReadableStream说明你真做过。
SSE的EventSource不支持POST请求怎么办？

EventSource API原生只支持GET。如果用户消息很长(超出URL限制)或需要POST，有两个方案：1）用fetch + ReadableStream手动解析——fetch发起POST请求，拿到response.body.getReader()，逐chunk读取并用TextDecoder解析text/event-stream格式；2）先用POST创建会话拿到session_id，再用EventSource GET流式获取结果。

实际项目里我用的方案2——POST发消息存数据库，返回session_id，前端用EventSource GET /chat/stream/{sessionId} 接收流式回复。这样既支持长消息，又复用EventSource的自动重连能力。

"POST创建会话+GET流式接收"是生产环境最常用的方案，能说这个说明你有实战经验。
SSE流式输出在Nginx层有什么坑？

最大的坑是proxy_buffering。Nginx默认proxy_buffering on，会把后端响应缓冲到完整再转发给客户端——SSE流被缓冲后，前端等10秒看到一次性出现全部文字，完全失去流式效果。必须配置proxy_buffering off + proxy_cache off。

第二个坑是超时。LLM生成可能要10秒+，Nginx默认proxy_read_timeout 60秒通常够，但如果有网关层(WAF/SLB)也要调超时。第三是gzip必须关，压缩也会导致缓冲。

能说出"proxy_buffering off"和"gzip off"说明你真配过。提"网关层也要调超时"说明考虑了全链路。

3. @AiService 注解：声明式Agent接口 ★★★★★ 必考

这是LangChain4j最核心、也最有Java味道的特性。你只需定义一个Java接口，标注几个注解，框架就用动态代理生成实现类——把"调用LLM"这件事变成"调用本地方法"，业务代码完全感知不到LLM的存在。

声明式开发的意义：传统做法是手动拼Prompt、手动调model.generate()、手动解析返回——LLM调用逻辑散落在业务代码里，难维护。@AiService把这些都收进框架：你在接口上声明@SystemMessage（角色设定）、@UserMessage（用户输入）、@V（模板变量），框架在方法被调用时自动拼装Prompt、调用模型、解析结果。业务代码只看到analyzer.analyze("评论")这样一个普通方法调用。

结构化输出是关键能力：当方法返回类型是POJO（如SentimentResult）而非String时，框架会在Prompt里追加"请输出符合此JSON Schema的JSON"，LLM返回JSON文本后，框架用Jackson反序列化为目标类型。解析失败会自动重试（带修复提示）。这让LLM的输出能直接进入业务流程——查询结果、入库、传给下游Service，全链路类型安全。

@AiService就是"LLM版的@FeignClient"——你只写接口，框架生成实现，把Prompt调用变成方法调用。
@AiService 类似 Spring Cloud 的 @FeignClient——你定义一个Java接口，标注注解，框架用动态代理生成实现类。@FeignClient把HTTP调用变成方法调用，@AiService把LLM调用变成方法调用。底层是JDK动态代理 + Prompt模板拼装 + 结果解析。也类似MyBatis的@Mapper——接口即契约，实现由框架生成。
图5-4 @AiService底层原理：动态代理拦截方法 -> Prompt拼装 -> 调LLM -> (工具循环) -> 结果解析 -> 返回
Java / langchain4j @AiService 
// 1. 定义返回POJO（结构化输出）
public record SentimentResult(
    String sentiment,   // 正面/负面/中性

public interface SentimentAnalyzer {

@AiService 核心注解详解

注解作用类比
@SystemMessage定义System Prompt（可带{{变量}}），设定角色/规则类上的全局配置/拦截器预设
@UserMessage标记哪个参数是用户输入（方法参数）@RequestParam 参数绑定
@VPrompt模板变量插值，把方法参数填入{{变量}}位置SpEL表达式 / @PathVariable
@MemoryId标记会话ID参数，用于多用户Memory隔离HttpSession的sessionId

结构化输出原理：当返回类型是POJO时，AiService在Prompt中追加"请输出符合此JSON Schema的JSON"，调用LLM后将返回的JSON文本用Jackson反序列化为目标类型。解析失败时自动重试（带修复提示）。这是@AiService最有价值的能力——让LLM输出直接成为类型安全的业务对象。

4. Tools（工具调用） ★★★★★ 必考

Tools是Agent的核心能力——让LLM能调用外部函数（查数据库、调API、发邮件），突破LLM"只会说话"的限制。没有Tools，Agent就退化成Chatbot。

Tool执行机制（核心原理）：LLM本身不能执行任何代码，它只能输出文本。所谓"工具调用"是一个协议约定——你在Java方法上加@Tool注解写好描述，框架把方法名、描述、参数Schema转成JSON发给LLM；LLM分析用户问题后，如果决定用工具，就返回一个ToolExecutionRequest（包含工具名+参数JSON）；框架收到后用反射调用对应的Java方法，拿到返回值；把返回值作为ToolExecutionResultMessage加入对话历史，再次调用LLM；LLM基于工具结果生成最终自然语言回答。整个过程可能循环多次（LLM连续调用多个工具）。

description是LLM选工具的唯一依据。LLM看不到你的Java代码，它只读每个工具的@Tool描述字符串和@P参数描述，根据用户问题的语义匹配最合适的工具。描述写得模糊，LLM就会选错或漏选——这是Tool调用不准的头号原因。好的description要写清功能 + 输入参数含义 + 触发场景。

Tools就是给LLM"长手"——LLM决定调什么工具、传什么参数，你的Java代码执行后把结果还给它。
Tools机制 ≈ Spring MVC的@RequestMapping路由 + 反射调用。LLM输出的ToolExecutionRequest就像一个HTTP请求（工具名=URL，参数=RequestBody），框架像DispatcherServlet一样根据工具名找到对应的@Tool方法，反射调用执行，把返回值作为响应回传。区别：传统路由是字符串匹配，Tool路由是LLM语义匹配。
图5-5 Tool调用全流程：提问 -> LLM决策 -> 反射执行 -> 结果回传 -> (循环) -> 生成回答

// 1. 用 @Tool 定义工具方法
public class WeatherTools {

    @Tool("查询指定城市的天气信息")  // 工具描述，LLM靠它理解用途
    public String getWeather(
        @P("城市名称，如北京、上海") String city   // 参数描述
    ) {
        // 实际调用天气API
        return weatherApi.query(city);
    }

    @Tool("查询指定城市的空气质量指数")
    public String getAirQuality(@P("城市名称") String city) {
        return airApi.queryAQI(city);
    }
}

好的 description vs 差的 description

// ❌ 差的description——LLM容易选错或漏选
@Tool("查询订单")
public String queryOrder(String orderId) { ... }

// ✅ 好的description——功能+输入+输出+触发场景都讲清楚

差描述只说"查询订单"，LLM无法区分这是查状态、查物流还是查详情；好描述说清了"输入什么、输出什么、什么场景该用"，LLM选工具准确率大幅提升。

ToolExecutionRequest机制：LLM不是直接执行Java方法。流程是：①LLM返回一个JSON（ToolName + 参数）-> ②框架解析为ToolExecutionRequest -> ③反射调用对应Java方法 -> ④结果转成ToolExecutionResult -> ⑤作为新消息加入对话 -> ⑥LLM再生成最终回答。整个过程对业务代码透明——你只调service.chat()，工具循环在框架内部完成。

5. Memory（对话记忆） ★★★★☆

LLM本身是无状态的——每次API调用都是全新的，模型不记得上一轮说了什么。ChatMemory的作用就是在应用层维护对话历史，每次调用LLM时把历史消息一起带上，让多轮对话成为可能。

为什么需要Memory：用户说"我叫张三"，下一句"我叫什么"，LLM单独看第二句根本无法回答。ChatMemory把第一轮的"我叫张三"存下来，第二轮调用时把[用户:我叫张三, AI:好的] + [用户:我叫什么]一起发给LLM，LLM才能回答"张三"。本质上Memory就是在每次请求里拼接历史上下文。

Token预算是核心约束。历史消息会占用模型的上下文窗口（如GPT-4是128K，但实际可用要留给System Prompt和当前问题）。如果对话很长，历史消息可能把窗口占满，导致LLM"忘记"当前任务。所以ChatMemory必须有裁剪策略——LangChain4j提供两种：按消息条数裁剪和按Token预算裁剪。

ChatMemory就是"LLM的短期记忆"——保存最近几轮对话，让LLM能"接着上次说"。
ChatMemory 类似 Java Web 的 HttpSession——按会话ID隔离，存储对话上下文。但有关键区别：HttpSession无大小限制（存服务端内存），ChatMemory有Token预算限制——历史消息太长会超出模型上下文窗口，必须裁剪。可以理解为"有容量上限的HttpSession"。

两种ChatMemory策略

类型裁剪策略原理优点缺点
MessageWindowChatMemory按消息条数（保留最近N条）FIFO队列，超过N条丢最早的简单可控，无需Tokenizer可能Token超限（一条长消息就占满）
TokenWindowChatMemory按Token数（不超预算）用Tokenizer算每条消息Token，累计不超maxTokensToken精确，不超窗口需要模型对应Tokenizer

6. RAG支持 ★★★★☆

LangChain4j内置完整的RAG（检索增强生成）链路——从文档加载到向量检索到注入Prompt，开发者只需配置几个组件即可实现"开卷考试"式问答。

朴素RAG的原理：LLM的知识有截止日期，也不知道你的私有数据。RAG的思路是——先从知识库检索与问题相关的内容，把检索到的内容拼进Prompt，让LLM基于这些内容回答，避免幻觉。完整流程是：离线阶段加载文档→切片→用EmbeddingModel向量化→存入EmbeddingStore；在线阶段用户提问→问题向量化→在EmbeddingStore做相似度检索取Top-K→把检索片段拼入Prompt→LLM基于片段回答。

LangChain4j的RAG抽象：核心是ContentRetriever接口——它定义了"给定用户消息，返回相关内容片段"的契约。EmbeddingStoreContentRetriever是其默认实现，封装了"问题向量化→向量检索→过滤"的完整流程。把它注入AiService后，每次用户提问框架会自动先检索、再把结果注入Prompt，业务代码完全无感。

RAG就是"开卷考试"——先从知识库检索相关内容，再让LLM基于检索结果回答，避免幻觉。

7. 高级特性 ★★★☆☆

除了基础能力，LangChain4j的AiServices Builder还提供一系列高级配置，覆盖生产环境的常见需求。

AiServices Builder链式构建：所有能力（模型、记忆、工具、检索器）都通过Builder链式注入，组合即用。这种设计让"一个Agent同时具备记忆+工具+RAG"变得简单——四行Builder代码搞定。Builder本身是不可变配置，build()后生成的Agent实例是线程安全的，可以作为Spring单例Bean注入。

多模型切换：同一个接口（如CustomerService）可以绑不同模型——生产用GPT-4保质量，测试用GPT-3.5省钱，本地用Ollama保隐私。因为核心层是接口，切换只需换Builder的.chatLanguageModel()参数，业务代码零改动。这是三层架构带来的直接红利。

动态SystemMessage：默认@SystemMessage是静态的（编译期写死）。但有些场景需要运行时切换角色——比如客服系统根据用户VIP等级给不同人设。这时用systemMessageProvider，传入一个Function<Object, SystemMessage>，每次调用时根据sessionId动态生成SystemMessage。类比Spring的RequestScope Bean——同一个接口，不同请求上下文返回不同实例。

面试场景演练

"LangChain4j和Python LangChain有什么区别？"

核心区别在于设计哲学和语言生态：

1. 设计风格：LangChain4j更贴合Java/Spring习惯——强类型、接口驱动、注解声明式。Python LangChain更灵活、链式调用、动态类型。

2. @AiService：LangChain4j独有，类似@FeignClient的声明式Agent接口，把LLM调用变成方法调用，返回POJO。Python版本没有这么自然的接口抽象。

3. 类型安全：LangChain4j的结构化输出利用Java泛型和record，编译期就能发现类型错误。

4. 并发模型：Java无GIL，多线程真正并行；Python受GIL限制，IO并行靠asyncio。在多用户并发Agent场景下Java有优势。

5. 生态：Python LangChain起步早、社区大、组件多；LangChain4j起步晚但跟Spring Boot集成更自然，有官方starter。

强调"Java生态友好"+"声明式接口"+"无GIL并发优势"是核心。结合项目说"在客服助手中用@AiService把LLM调用写得像写Service层一样"。
"@AiService的底层原理是什么？"

本质是JDK动态代理 + Prompt模板拼装 + 结果解析三步：

1. 动态代理：AiServices.builder()用Proxy.newProxyInstance生成接口的实现类，拦截所有方法调用。

2. Prompt拼装：拦截到方法调用后，读取@SystemMessage/@UserMessage/@V注解，用模板引擎填充变量，组装成完整的消息列表（System + Memory历史 + User）。

3. 结果解析：调用ChatLanguageModel.generate()，拿到返回文本后，根据返回类型决定解析方式——String直接返回，POJO则解析JSON并反序列化，Result<T>还会带上Token用量等元数据。

4. 工具循环：如果配置了Tools且LLM返回了ToolExecutionRequest，会先执行工具、把结果加入对话、再次调用LLM，直到LLM不再请求工具。

提"动态代理"立刻和Spring联系起来。补充"Tool调用是个循环"体现你理解了Agent的ReAct模式。
"Tools是怎么工作的？LLM怎么知道该调哪个工具？"

Tools依赖LLM的Function Calling能力，整个流程是一个循环：

1. 注册：Builder注册工具时，框架把@Tool方法的名称、description、参数Schema转成JSON，作为tools参数传给LLM。

2. 决策：LLM分析用户问题，靠description语义匹配决定是否需要调用工具、调哪个、传什么参数，返回一个ToolExecutionRequest（含工具名+参数JSON）。

3. 执行：框架用反射调用对应的Java方法，拿到返回值。

4. 回传：结果作为ToolExecutionResultMessage加入对话历史，再次调用LLM。

5. 循环：LLM可能连续调用多个工具（如先查天气再查空气质量），直到不再请求工具，生成最终自然语言回答。

关键：description是LLM选工具的唯一依据，写不好就选错。要写清功能+输入+触发场景。

强调"@Tool的描述是给LLM看的"——LLM靠描述决定用不用这个工具。说"多工具可循环调用"展示你理解ReAct/Agent循环。
"ChatMemory怎么管理Token？两种策略怎么选？"

核心是在上下文窗口预算内做裁剪，两种策略：

1. MessageWindowChatMemory：按消息条数裁剪。比如maxMessages=20，超过20条就丢弃最早的。简单但不够精确——一条长消息可能就占满Token。

2. TokenWindowChatMemory：按Token数裁剪。用Tokenizer计算每条消息的Token数，保留不超过maxTokens的最新消息。更精确，但需要模型对应的Tokenizer。

关键原则：System Prompt + Memory + 当前问题 + 输出空间 ≤ 模型上下文窗口。Memory占用越多，留给当前任务的空间越少。生产中要动态平衡——通常Memory占总窗口的30-50%。

进阶：长对话可以用摘要压缩——把早期对话用LLM总结成一段摘要存入Memory，释放Token空间。

提"Token预算分配公式"和"摘要压缩"非常加分，说明你做过生产环境的长对话优化。
"你的Agent流式输出是怎么做的？为什么用SSE不用WebSocket？"

用SSE(Server-Sent Events)实现。后端Spring Boot用SseEmitter(或WebFlux的Flux<ServerSentEvent>)，langchain4j用StreamingChatLanguageModel逐token回调，每个token通过SseEmitter.send()推到前端。前端用浏览器原生EventSource API消费，逐token追加实现打字机效果。

用SSE不用WebSocket的原因：LLM流式输出是服务端->客户端的单向推送，SSE用标准HTTP协议，Nginx/CDN全兼容，浏览器原生支持自动重连，实现最简单。WebSocket的双向能力在这里是浪费，而且握手协议更复杂、部分代理不兼容。

关键配置是Nginx必须proxy_buffering off，否则流被缓冲成一次性返回。

能说出"SSE是单向推送所以够用"和"Nginx buffering off"这两个关键点就够了。再提一句EventSource只支持GET、POST要用fetch+ReadableStream说明你真做过。
"LangChain4j的RAG是怎么实现的？ContentRetriever起什么作用？"

LangChain4j的RAG分两阶段：离线用EmbeddingStoreIngestor加载文档→切片→EmbeddingModel向量化→存入EmbeddingStore；在线用ContentRetriever检索。

ContentRetriever是核心接口，定义"给定用户消息返回相关内容片段"的契约。默认实现EmbeddingStoreContentRetriever封装了"问题向量化→向量检索Top-K→minScore过滤"。把它注入AiService后，每次用户提问框架自动先检索、把结果作为context拼入Prompt，业务代码只调assistant.chat(question)，完全无感。

调参重点：切片大小（300字+50重叠常用）、maxResults（Top-K，通常3-5）、minScore（相似度阈值，0.7左右）。

能说出"ContentRetriever是接口契约，注入后框架自动检索+拼接"体现你理解了框架设计。提调参三件套说明有实战。
  • LangChain4j三层架构：应用层（@AiService）-> 核心层（接口契约，无厂商依赖）-> 集成层（模型/存储/加载器）。换模型只换集成层，业务代码不动
  • 和Python LangChain区别：Java强类型+注解声明式+无GIL并发优势+Spring集成；@AiService是独有声明式Agent抽象
  • 同步ChatLanguageModel阻塞返回（首字延迟高），流式StreamingChatLanguageModel逐Token回调（onPartialResponse/onComplete/onError）
  • SSE流式输出：SseEmitter/WebFlux Flux推送，前端EventSource消费。Nginx必须proxy_buffering off！EventSource只支持GET，POST用fetch+ReadableStream
  • @AiService = LLM版@FeignClient：JDK动态代理+Prompt模板拼装+结果解析。返回POJO=结构化输出（框架追加JSON Schema要求+Jackson反序列化）
  • Tools机制：@Tool描述→LLM输出ToolExecutionRequest→框架反射执行Java方法→结果回传→LLM整合回答（可循环）。description是选工具唯一依据，要写清功能+输入+触发场景
  • ChatMemory：MessageWindow按条数裁剪（简单），TokenWindow按Token预算裁剪（精确）。Token预算公式：System+Memory+问题+输出 ≤ 窗口，Memory占30-50%
  • RAG链路：离线（加载→切片→向量化→存储）+ 在线（ContentRetriever检索→拼Prompt→LLM回答）。注入AiService后业务无感
  • 高级特性：Builder链式构建（组合模型+记忆+工具+RAG）、多模型切换（换Builder参数）、systemMessageProvider动态角色（按sessionId切换Prompt）
