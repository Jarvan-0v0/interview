SSE流式输出 必考

🎯 学习目标：掌握SSE协议原理、Spring SseEmitter/WebFlux实现、EventSource前端API、Nginx代理配置（proxy_buffering off）、SSE vs WebSocket选型、断线重连与错误处理，能在面试中清晰阐述Agent流式输出的完整链路和踩过的坑。

SSE是Agent回答"打字机效果"的底层协议——没有它，用户要等Agent全部思考完才能看到结果，体验极差。面试官问"流式输出怎么实现的"，考察的是你对HTTP长连接+事件流的完整理解。

1. 为什么Agent必须用流式输出 ★★★★★ 必考

Agent和传统API最大的区别是响应时间不确定。传统API调用数据库+业务逻辑，100ms内返回；Agent要做LLM推理+工具调用+再推理，5-30秒很正常。如果等全部完成再返回，用户盯着白屏十几秒——体验灾难。

流式输出解决三个问题：

流式输出的三大价值

  1. 感知速度：用户看到第一个token只需0.5-1秒（TTFT, Time To First Token），而不是等30秒看完整答案。心理学上，看到内容在"打字"比等空白屏幕焦虑感低得多。
  2. 中途取消：用户看到Agent推理方向错了，可以中途打断（Stop按钮），避免浪费Token。非流式只能等全部返回才知道结果。
  3. 增量处理：前端可以边接收边渲染Markdown/代码高亮，不需要等完整响应再一次性渲染。对于长回答（如代码生成），增量渲染体验更好。
流式输出 ≈ Java InputStream的分块读取而非一次性readAllBytes()。传统API是"把整个byte[]一次性返回"，流式是"每读到一个chunk就返回给调用方"。WebFlux的Flux<String>就是这个模式——不是等待所有数据就绪，而是来一个推送一个。

2. SSE协议原理 ★★★★☆

SSE（Server-Sent Events）是HTTP协议上的单向推送标准。核心思想：客户端发起一个普通HTTP GET请求，服务端保持连接不关闭，持续向客户端推送文本事件流。这不是WebSocket那种全双工协议，而是HTTP长连接上的单向数据流。

SSE协议格式非常简单——纯文本，每行一个字段，事件之间用空行分隔：

SSE协议原始格式 
// 服务端推送的原始TCP数据
data: 你

data: 好，我

data: 来帮您

data: 查一下

event: done
data: {"status":"completed"}

// 每个字段的含义：
// data: 事件数据（必需）
// event: 事件类型（可选，默认message）
// id: 事件ID，用于断线重连时的Last-Event-ID
// retry: 重连间隔（毫秒）
// 空行: 事件结束标志

SSE协议的关键特性

  • Content-Type: text/event-stream——服务端必须设置此响应头，浏览器才识别为SSE
  • Connection: keep-alive——保持TCP连接不关闭
  • Cache-Control: no-cache——禁止代理缓存，确保实时性
  • Last-Event-ID——断线重连时客户端自动发送此请求头，服务端可以从中断处继续推送
  • 单向推送——客户端只能接收，不能通过SSE连接发送数据（需要发数据用另一个HTTP请求）
SSE本质：HTTP长连接上的单向文本事件流

3. Spring实现：SseEmitter vs WebFlux ★★★★★ 必考

Spring生态中有两种SSE实现方式，面试官经常问它们的区别。核心差异在于底层线程模型——一个阻塞一个非阻塞。

3.1 Spring MVC SseEmitter（Servlet阻塞模型）

SseEmitter是Spring MVC 4.2+提供的SSE支持，底层依赖Servlet 3.0+异步。每个SSE连接占用一个Tomcat线程（虽然可以异步释放），大并发场景下线程资源是瓶颈。

Java (SseEmitter标准写法) 
@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream() {
    // timeout: 30分钟无活动超时
    SseEmitter emitter = new SseEmitter(30 * 60 * 1000L);

    // 异步发送事件（通常用线程池）
    executor.execute(() -> {
        try {
            for (int i = 0; i < 10; i++) {
                emitter.send(SseEmitter.event()
                    .name("message")      // 事件类型
                    .data("chunk " + i)       // 事件数据
                    .id(String.valueOf(i)));  // 事件ID（断线重连用）
                Thread.sleep(1000);
            }
            emitter.send(SseEmitter.event()
                .name("done")
                .data("{\"status\":\"completed\"}"));
            emitter.complete();
        } catch (Exception e) {
            emitter.completeWithError(e);
        }
    });

    return emitter;
}

SseEmitter的坑：默认timeout是30秒，长连接场景必须显式设大。onCompletion和onTimeout回调必须注册，否则连接断开时send()会抛异常。send()是阻塞调用，如果客户端断开连接（网络断开），send()会抛IOException，必须捕获处理。

3.2 Spring WebFlux ServerSentEvent（响应式非阻塞）

WebFlux基于Reactor，使用少量线程+NIO事件循环处理大量并发连接。一个SSE连接不占用线程，只占用一个文件描述符。对于Agent这种需要同时处理大量并发流式连接的场景，WebFlux是更好的选择。

Java (WebFlux + LangChain4j流式) 
@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> chatStream(@RequestParam String query) {
    return Flux.create(sink -> {
        // LangChain4j流式回调
        StreamingChatLanguageModel model = /* ... */;
        model.generate(query, new StreamingResponseHandler<AiMessage>() {
            @Override
            public void onNext(String token) {
                // 每个token推送给前端
                sink.next(ServerSentEvent.builder(token).build());
            }
            @Override
            public void onComplete() {
                sink.next(ServerSentEvent.builder("[DONE]").event("done").build());
                sink.complete();
            }
            @Override
            public void onError(Throwable e) {
                sink.error(e);
            }
        });
    });
}
对比维度SseEmitter (MVC)ServerSentEvent (WebFlux)
线程模型每个连接一个Servlet线程（可异步释放）Event Loop + 少量线程
并发能力受Tomcat线程池限制（默认200）理论数千并发，受文件描述符限制
背压支持无（send()阻塞）有（Reactor背压机制）
使用场景简单SSE推送，并发量不大高并发流式场景，Agent/LLM流式响应
学习成本低，传统Servlet开发模式中，需要理解Reactor响应式编程
mall-agent选择—✅ WebFlux，高并发Agent场景

4. 前端EventSource API ★★★☆☆

浏览器原生支持SSE，通过EventSource对象接收事件流。它比WebSocket API更简单——不需要握手，自动重连，自动解析事件格式。

JavaScript (EventSource标准用法) 
const eventSource = new EventSource('/api/chat/stream?query=你好');

// 默认事件类型 "message"
eventSource.onmessage = (event) => {
    const token = event.data;
    appendToChat(token);  // 逐字追加到聊天界面
};

// 自定义事件类型
eventSource.addEventListener('done', (event) => {
    const data = JSON.parse(event.data);
    console.log('流式完成', data);
    eventSource.close();  // 主动关闭连接
});

// 错误处理
eventSource.onerror = (event) => {
    if (eventSource.readyState === EventSource.CLOSED) {
        console.log('连接已关闭（可能是服务端断开）');
    } else {
        console.log('连接错误，EventSource会自动重连');
    }
};

// 主动取消
function stopStreaming() {
    eventSource.close();  // 关闭连接，停止接收
}

EventSource的自动重连机制

EventSource有一个内置的重连机制：连接断开后，浏览器会自动重新发起GET请求。重连间隔由服务端通过retry:字段控制（毫秒）。如果服务端没设置，浏览器默认等几秒后重试。重连时浏览器会自动带上Last-Event-ID请求头，服务端可以根据这个ID从中断处继续推送。

这个机制对Agent场景很重要：网络抖动导致连接断开时，EventSource会自动重连，前端不需要写重连逻辑。但有一个限制：EventSource的GET请求不支持自定义请求头，如果需要传Token认证，只能用URL参数或Cookie。

5. Nginx代理配置：proxy_buffering off ★★★★★ 必考

这是SSE在实际部署中踩坑率最高的配置。Nginx默认会对上游响应做代理缓冲（proxy_buffering on）——等上游响应全部到达后再一次性发给客户端。这个行为对SSE是致命的：流式推送变成了批量推送，用户看不到打字机效果。

Nginx代理缓冲对SSE的破坏

Nginx默认proxy_buffering=on时，会把上游（Spring应用）的响应先缓存到内存/磁盘，等收集完整个响应体再发送给客户端。对于SSE——服务端每10ms推送一个token，Nginx却把它们攒起来，等连接关闭或超时才一次性发出。结果：用户等了30秒，然后"刷"一下看到完整答案——流式推送完全失效。

关闭缓冲后，Nginx变成透传模式——上游推送一个字节，Nginx就转发一个字节给客户端。SSE的逐字推送行为得以保留。

Nginx配置 (关键三段) 
location /api/chat/stream {
    # ① 关闭代理缓冲——SSE最关键的配置
    proxy_buffering off;

    # ② 关闭Nginx自己的响应缓存
    proxy_cache off;

    # ③ 延长连接超时（默认60s对Agent不够）
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;

    # ④ 禁用gzip压缩（流式内容不适合压缩）
    gzip off;

    # ⑤ 设置HTTP版本（SSE需要HTTP/1.1长连接）
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_pass http://backend:8080;
}

proxy_buffering off 是SSE的"保命配置"——面试必说。不关这个，所有流式推送变成批量推送，前端EventSource的逐字渲染完全失效。另外，proxy_read_timeout默认60秒，Agent的LLM推理+工具调用经常超过60秒，必须设大到300秒以上。如果用了K8s Ingress（Nginx Ingress Controller），也要在Ingress annotation里设置：nginx.ingress.kubernetes.io/proxy-buffering: "off" 和 nginx.ingress.kubernetes.io/proxy-read-timeout: "300"。

除了proxy_buffering，另一个常见坑是中间代理的缓冲——CDN、API Gateway、负载均衡器都可能自带缓冲。排查方法：先绕过所有代理直连Spring应用测试SSE是否正常，如果正常说明代理层有问题，逐层排查。

6. SSE vs WebSocket vs 长轮询 ★★★★☆

面试官经常问"为什么用SSE不用WebSocket"，考察的是对协议选型的理解。三者的核心区别在于通信方向、协议层和复杂度。

对比维度SSEWebSocketHTTP长轮询
通信方向单向（服务端→客户端）全双工（双向）单向（客户端→服务端→客户端）
协议HTTP/1.1 长连接WebSocket协议（ws://）HTTP/1.1 多次请求
浏览器支持所有现代浏览器所有现代浏览器所有浏览器
自动重连✅ EventSource内置❌ 需手动实现❌ 需手动实现
二进制数据❌ 仅文本✅ 支持二进制❌ 仅文本
Nginx代理简单（HTTP代理）需额外配置Upgrade简单
防火墙友好✅ 标准HTTP端口⚠ 部分防火墙拦截✅ 标准HTTP
Agent场景适用✅ 流式回答（单向推送）⚠ 过度设计（双向不必要）❌ 低效（重复建连）
SSE ≈ 服务端给客户端发短信（单向推送），WebSocket ≈ 双方打电话（双向实时）。Agent场景中，用户把问题发给Agent是一个普通HTTP POST请求，Agent把答案流式推回用SSE——不需要WebSocket的全双工能力。用WebSocket就像给一个只收短信的场景配了双向通话，过度设计。

为什么Agent场景SSE优于WebSocket：

  • 简单：SSE就是一个HTTP GET，不需要协议升级握手，不需要心跳保活，不需要处理帧格式
  • 自动重连：EventSource内置重连，WebSocket断线需要手动写重连逻辑（还要处理消息去重）
  • Nginx友好：SSE走标准HTTP代理，WebSocket需要Nginx配置Upgrade头
  • 单向够用：用户发消息走普通POST，Agent流式回答走SSE——两个方向分开，职责清晰

7. 断线重连与错误处理 ★★★★☆

SSE连接不是永远稳定的——网络抖动、服务端重启、Nginx超时都会导致连接断开。生产环境必须处理断线重连。

7.1 客户端重连策略

JavaScript (增强版EventSource，带手动重连控制) 
class RobustEventSource {
    constructor(url, options = {}) {
        this.url = url;
        this.maxRetries = options.maxRetries || 3;
        this.retryDelay = options.retryDelay || 2000;
        this.retryCount = 0;
        this.lastEventId = null;
        this.connect();
    }

    connect() {
        const urlWithId = this.lastEventId
            ? `${this.url}?lastEventId=${this.lastEventId}`
            : this.url;

        this.es = new EventSource(urlWithId);

        this.es.onmessage = (event) => {
            this.lastEventId = event.lastEventId;
            this.onMessage(event.data);
        };

        this.es.onerror = () => {
            if (this.es.readyState === EventSource.CLOSED) {
                this.retryCount++;
                if (this.retryCount <= this.maxRetries) {
                    console.log(`重连 ${this.retryCount}/${this.maxRetries}`);
                    setTimeout(() => this.connect(), this.retryDelay);
                } else {
                    this.onFail('重连次数耗尽');
                }
            }
        };
    }

    close() { this.es.close(); this.retryCount = this.maxRetries + 1; }
}

7.2 服务端处理客户端断开

服务端需要感知客户端断开（关闭浏览器/网络断开），释放资源停止推送。否则服务端会一直向一个已断开的连接推送数据，浪费LLM Token。

Java (WebFlux检测客户端断开) 
@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> chatStream(@RequestParam String query) {
    return Flux.create(sink -> {
        model.generate(query, new StreamingResponseHandler<>() {
            @Override public void onNext(String token) {
                // sink.isCancelled()检测客户端是否已断开
                if (!sink.isCancelled()) {
                    sink.next(ServerSentEvent.builder(token).build());
                } else {
                    // 客户端断开，停止LLM生成
                    model.cancel();  // 取消LLM调用，节省Token
                }
            }
            @Override public void onComplete() {
                if (!sink.isCancelled()) sink.complete();
            }
        });
    }).doOnCancel(() -> {
        log.info("客户端断开连接，取消LLM调用");
        // 清理资源：取消LLM请求、释放上下文
    });
}

8. mall-agent中的SSE实战 ★★★★★ 必考

mall-agent的SSE实现有几个设计决策，面试时可以展开讲。

设计决策1：为什么用WebFlux不用MVC SseEmitter

矿池官网高峰期同时在线用户数可能上千，每个用户都在等Agent流式回答。MVC SseEmitter每个连接占用一个Tomcat线程（即使异步释放也有限制），WebFlux基于Netty NIO，少量线程处理数千并发连接。另外WebFlux的Flux可以和LangChain4j的StreamingResponseHandler天然对接——每个token到达时通过sink.next()推送，不需要自己管理线程池。

设计决策2：缓冲解析 vs 流式推送的权衡

mall-agent的ReAct循环有一个特殊处理：流式输出先全部缓冲，等完整响应拿到后确认没有Action（工具调用）才推送Final Answer给用户。这是因为LLM在流式输出时可能编造Observation——在Action还没执行时就先输出虚构的Observation。代价是失去了打字机效果，但保证了正确性。

面试时可以这样回答：这是正确性优先于体验的工程权衡。如果以后模型支持原生function calling（如DeepSeek），可以回归流式推送——模型在返回tool_calls时不会编造Observation。

设计决策3：SSE事件类型设计

mall-agent用了多种事件类型来区分不同阶段的消息：

  • thinking：Agent正在思考（显示"思考中..."动画）
  • action：Agent正在调用工具（显示"正在查询..."）
  • token：流式回答的文本片段（逐字渲染）
  • error：错误信息（红色提示框）
  • done：回答完成（停止加载动画，显示完整回答）
  • transfer：转人工（显示人工客服接入提示）

前端根据事件类型做不同的UI渲染，比只用一种事件类型+状态码更清晰。

mall-agent SSE完整链路：浏览器→Nginx→WebFlux→LangChain4j→ReAct→SSE事件流→浏览器渲染

9. 面试Q&A ★★★★★ 高频

Q1：你的Agent流式输出是怎么实现的？完整链路说一下。

完整链路：浏览器EventSource发起GET /api/chat/stream → Nginx（proxy_buffering off，透传）→ Spring WebFlux AiController → Flux.create异步推送 → LangChain4j StreamingChatModel的onNext回调 → 每个token通过sink.next()推送SSE事件 → 经Nginx透明转发 → 浏览器EventSource.onmessage逐字渲染。

关键点：WebFlux用Netty NIO少量线程处理高并发，Nginx必须关proxy_buffering否则流式变成批量，LLM生成token到前端渲染的延迟控制在50ms内。

画链路图加分。提proxy_buffering off展示你有部署经验。说出"WebFlux NIO"和"Event Loop"展示深入理解。
Q2：Nginx代理SSE需要哪些配置？为什么？

核心三段：

1）proxy_buffering off——最重要。Nginx默认会缓存上游响应，攒够再发给客户端。SSE需要逐字推送，必须关缓冲让Nginx变成透传模式。

2）proxy_read_timeout 300s——默认60秒，Agent的LLM推理+工具调用经常超过60秒，不设大Nginx会主动断开连接。

3）gzip off——流式内容不适合压缩（gzip需要攒够数据才能压缩，和proxy_buffering一样会破坏流式效果）。

K8s Ingress还要加annotation：nginx.ingress.kubernetes.io/proxy-buffering: "off"。

三条都说清楚，尤其第一条必须强调。提K8s Ingress annotation展示你有容器化部署经验。
Q3：SSE和WebSocket怎么选？Agent场景为什么用SSE？

Agent场景用SSE的原因：

1）通信模式匹配：用户发消息（POST）→ Agent流式回答（SSE推送），Server→Client单向推送，不需要WebSocket的双向通道。

2）简单：SSE就是HTTP GET，不需要协议升级握手、心跳保活、帧格式处理。WebSocket要处理连接管理、心跳、断线重连——额外复杂度。

3）自动重连：EventSource内置重连+Last-Event-ID续传，WebSocket需要手动实现。

4）基础设施友好：SSE走标准HTTP，Nginx/CDN/防火墙都不需要额外配置。WebSocket需要Upgrade头，部分代理/防火墙会拦截。

WebSocket适合的场景：实时双向通信（在线协作、游戏、聊天室）。Agent是典型的单向推送场景，用WebSocket过度设计。

不要只说"SSE简单"，要说"为什么Agent场景不需要双向"。提"过度设计"表明你有架构判断力。
Q4：SseEmitter和WebFlux的ServerSentEvent有什么区别？

核心区别在线程模型：

SseEmitter（Spring MVC）：每个SSE连接占用一个Tomcat线程（即使异步释放，线程池大小也有限制，默认200）。send()是阻塞调用。适合低并发场景。

ServerSentEvent（WebFlux）：基于Reactor，Event Loop + 少量线程处理数千并发连接。Flux支持背压——下游消费慢时上游减速。doOnCancel可以检测客户端断开并释放资源。适合高并发Agent场景。

mall-agent选WebFlux的原因：矿池高峰期上千用户同时等待Agent流式回答，MVC的线程池撑不住。WebFlux的Netty NIO用少量线程处理所有连接，和LangChain4j的StreamingResponseHandler天然对接。

核心是线程模型差别。说"Event Loop + 少量线程"比说"WebFlux好"有深度。提背压和doOnCancel展示实际使用经验。
Q5：流式输出时用户关闭网页会怎样？怎么处理？

三件事：

1）检测断开：WebFlux Flux.create的sink.isCancelled()检测客户端断开。EventSource连接关闭时，Flux的订阅自动取消。

2）停止LLM：检测到断开后调用model.cancel()终止LLM推理，避免浪费Token。如果已经在工具调用中，等当前工具返回后不再继续下一轮ReAct。

3）清理资源：doOnCancel中释放上下文（ReActTraceStore、对话记忆），避免内存泄漏。

如果不处理，服务端会继续向已断开的TCP连接写数据（触发IOException），LLM继续生成完整回答浪费Token，内存中的上下文对象也不会被GC。

分三层说（检测→停止→清理），展示系统性思维。提"节省Token"说明你有成本意识。
Q6：EventSource的GET请求怎么传Token认证？

三种方式：

1）URL参数：/api/chat/stream?token=xxx——最简单，但Token暴露在URL中（浏览器历史、服务器日志）。

2）Cookie：登录时设置HttpOnly Cookie，EventSource自动携带——安全，但跨域需要withCredentials配置。

3）先POST再SSE：用户先POST /api/chat发起对话（带Authorization头），返回streamId，然后EventSource连GET /api/chat/stream/{streamId}——最安全，Token不暴露在URL中，streamId一次性使用。

mall-agent用的是方案3：POST发起对话返回streamId，SSE通过streamId关联会话，认证在POST阶段完成。

三种方案都说出来，展示你知道EventSource的局限性。提"方案3最安全"展示你有安全意识。
  • SSE协议：HTTP长连接上的单向文本事件流，Content-Type: text/event-stream，data/event/id/retry四字段
  • Spring实现：SseEmitter（MVC，阻塞，低并发）vs ServerSentEvent（WebFlux，NIO，高并发）
  • 前端EventSource：原生API，自动重连+Last-Event-ID，不支持自定义请求头
  • Nginx关键配置：proxy_buffering off（必开）、proxy_read_timeout 300s、gzip off、K8s Ingress annotation
  • SSE vs WebSocket：Agent是单向推送场景，SSE够用；WebSocket双向+复杂，过度设计
  • 断线重连：EventSource内置重连，服务端sink.isCancelled()检测断开，model.cancel()省Token
  • mall-agent设计：WebFlux+NIO、缓冲解析防编造Observation、多种事件类型区分状态、POST+streamId认证
  • 面试核心数字：proxy_read_timeout 300s、Tomcat线程池默认200、TTFT 0.5-1s、NIO少量线程处理数千连接
