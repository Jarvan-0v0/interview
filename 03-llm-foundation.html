第03章

LLM大模型基础

学习目标：理解LLM底层原理——Transformer架构、Token与Embedding、关键参数调优、幻觉成因、Function Calling机制。这是转行Agent开发必须补的知识地基，面试会问"LLM是怎么工作的"。

1. Transformer架构 ⭐⭐⭐

Transformer是当前所有主流大模型（GPT/Claude/Gemini/Llama）的基础架构，2017年Google在《Attention Is All You Need》中提出。理解Transformer是理解LLM一切行为的基础。

Transformer的核心是自注意力：让句子中每个词都能"看到"所有其他词，根据相关性分配注意力，用矩阵乘法并行计算。

1.1 自注意力机制 (Self-Attention)

传统RNN处理文本时逐词串行处理，前面的词要等后面处理完。自注意力让每个词同时和所有词计算关联度，根据关联度加权融合信息。这解决了两个问题：一是并行化（GPU友好），二是长距离依赖（任意两个词直接相连，不像RNN距离远了就"遗忘"）。

具体实现用三个矩阵：Q(Query)表示"我在找什么信息"，K(Key)表示"我能提供什么信息"，V(Value)表示"我的实际内容是什么"。计算时，用Q和所有K做点积算相似度，softmax归一化后作为权重，对V加权求和。公式：Attention(Q,K,V) = softmax(QKT/√dk)V。√dk是缩放因子，防止点积过大导致softmax梯度消失。

Self-Attention ≈ Java里的双重for循环：对集合中每个元素，和其他所有元素做一次对比算关联度。但Transformer用矩阵乘法把这个O(n²)操作高度并行化了，跑在GPU上非常快。类比：你开会有10个人，每个人同时和所有人交流（自注意力），比一个人一个人轮流发言（RNN）效率高得多。
自注意力机制：每个词与所有词计算关联度，线越粗注意力越高

1.2 Multi-Head Attention（多头注意力）

一个注意力头只能学到一种关联模式。多头注意力就是同时用多组Q/K/V（如GPT-4有96个头），每组学到不同模式——有的关注语法关系，有的关注语义关系，有的关注位置关系。最后把所有头的输出拼接起来。类比：同一篇文章，用语法、语义、逻辑三个视角各读一遍，综合理解。

1.3 Encoder-Decoder vs Decoder-only

原始Transformer有Encoder(理解输入)和Decoder(生成输出)两部分。但不同模型选择不同：

  • GPT系列：只用Decoder(Decoder-only)，擅长生成文本。你给它前文，它预测下一个token。
  • BERT：只用Encoder(Encoder-only)，擅长理解文本。适合分类、情感分析等理解任务。
  • T5/BART：Encoder+Decoder都用，Encoder编码输入，Decoder生成输出。

当前主流聊天/Agent模型（GPT/Claude/Llama）都是Decoder-only，因为聊天本质是"根据上下文生成下一个token"。

1.4 为什么不用RNN/LSTM

O(n²)复杂度意味着：上下文从4K→128K，计算量增加了1024倍！这就是为什么超长上下文模型贵且慢——不是线性增长，是平方增长。

2. Token与Tokenizer ⭐⭐⭐

LLM不直接处理文本，它处理的是token——文本被切分后的最小单元。理解token对成本估算和上下文管理至关重要。

Token是LLM的"原子"：文本→切成token→查表变成向量→送入模型计算。Token数量直接影响成本和上下文窗口。

2.1 什么是Token

Token不等于单词，也不等于字符。它介于字符和词之间：英文"hello"是1个token，"unbelievable"可能被切成"un"+"bel"+"ievable"3个token。中文"你好"通常是2个token（每个汉字1个），但也可能因为词表里收录了"你好"这个词而只算1个。

2.2 BPE分词算法

Byte Pair Encoding (BPE)是最常用的分词算法，原理是"高频子串合并"：

  1. 初始：把所有文本拆成单个字符
  2. 统计：找出出现频率最高的字符对（如"t"+"h"出现了100万次）
  3. 合并：把它们合并成新token"th"，加入词表
  4. 重复：不断合并高频对，直到达到预设词表大小（如GPT-4的cl100k词表约10万token）
BPE ≈ Java的字符串压缩算法：先统计高频子串，再合并，最终建一个"词表"。Tokenizer就是这个词表的查找表，类似于HashMap<String, Integer>。文本→Tokenizer→token ID序列。

2.3 中英文Token差异（影响成本！）

语言示例Token数说明
英文"Hello world"2基本1词=1token
中文"你好世界"4-61字≈1-2token，中文更费token
代码public static void3-4关键字+空格各为token

中文场景的token成本是英文的2-3倍！做中文Agent时，上下文窗口和成本预算要特别注意。这也是为什么国产模型（Qwen/GLM）在中文token效率上做了优化——它们的词表收录了更多中文高频词。

2.4 Token到向量(Embedding)

每个token ID通过查表得到一个高维向量（通常768/1024/4096维）。这个向量是模型在训练中学到的——语义相近的token向量距离也近。如"猫"和"狗"的向量距离近，"猫"和"汽车"的向量距离远。这个"向量空间"是所有语义理解的基础。

文本处理流水线：原文→Tokenizer→Token IDs→Embedding查表→高维向量

3. 关键参数详解 ⭐⭐⭐

调参是Agent开发的核心技能。理解每个参数的数学原理才能精准调优。

3.1 Temperature（温度）

温度控制LLM生成的随机性。模型在每个位置输出一个概率分布，温度决定如何从这个分布中采样。数学上：adjusted_prob = softmax(logits / T)。温度小(T→0)放大logits差异，概率分布更尖锐（几乎总选最高概率token）；温度大(T→∞)抹平差异，概率分布更均匀（选token接近随机）。

场景推荐温度原因
客服问答/知识检索0.3-0.7要准确稳定，不能乱编
代码生成0.2-0.5代码要精确，不能"创造性"乱写
创意写作/头脑风暴0.8-1.2需要多样性和创造力
数据提取/分类0-0.3要确定性输出，同一输入同一输出
Temperature ≈ Java的Random(seed)中的分布参数。温度=0相当于直接取max（贪心解码，确定性），温度高相当于从均匀分布随机取。客服场景我用0.5——既不呆板也不乱说。

3.2 Top-K / Top-P采样

除了温度，还有两种控制采样的方法，常和温度配合使用：

  • Top-K：只从概率最高的K个token中采样，直接截断长尾。如Top-K=40，只考虑前40个最可能的token。简单粗暴。
  • Top-P (nucleus sampling)：从概率累加达到P的最小token集合中采样。如Top-P=0.9，选最少的token使概率和≥0.9。比Top-K更自适应——当模型很确定时（一个token概率0.95），Top-P只选1个；当模型不确定时（多个token概率相近），Top-P会选更多。

3.3 Context Window（上下文窗口）

上下文窗口是模型能"看到"的最大token数，包括输入+输出的总和。GPT-4是128K，Claude 3.5是200K。但这不意味着200K以内效果都一样——存在"Lost in the Middle"问题：模型对上下文开头和结尾的信息记忆最好，中间的信息容易被忽略。

Context Window ≈ Java的BufferedReader缓冲区大小。缓冲区装不下的内容被丢弃。LLM上下文满了后，最早的消息被"遗忘"——类似于固定大小的环形缓冲区。所以RAG检索结果放在prompt开头或结尾效果更好。
"Lost in the Middle"对RAG的启示：检索到的相关文档放在prompt的开头或结尾，不要放在中间。System Prompt放最前面，用户问题放最后面，RAG结果放中间偏后。

5. 幻觉 (Hallucination) ⭐⭐⭐

幻觉是LLM生成看似合理但实际错误的内容。这是LLM最被诟病的问题，也是面试必问。

LLM不是知识库，是概率模型——它"生成"最可能的内容，而非"检索"正确的内容。所以会一本正经地胡说八道。

5.1 为什么会产生幻觉

本质原因：LLM是next-token predictor（预测下一个token），它预测的是"统计上最可能的"而非"事实正确的"。当遇到训练数据中没见过的知识时，它会根据概率分布生成一个"看起来合理"的答案，而非承认不知道。这和搜索引擎完全不同——搜索引擎是"检索"已有信息，LLM是"生成"新文本。

产生幻觉的具体场景：①知识盲区（模型没学过的知识）；②模糊提问（问题不明确，模型"猜"你要什么）；③prompt引导错误（prompt里的错误信息会引导模型输出错误内容）；④温度过高（增加随机性，更容易选到不靠谱的token）。

5.2 如何缓解幻觉

方法原理效果
RAG（检索增强）给模型参考资料，让它"看着资料回答"⭐⭐⭐ 最有效
降低温度减少随机性，更倾向选高概率token⭐⭐ 有效但牺牲多样性
结构化输出强制输出JSON，限制格式减少"发挥空间"⭐⭐ 特定场景有效
System Prompt约束"如果不确定就说不知道"⭐ 有一定效果但不可靠
多模型交叉验证多个模型回答同一问题，对比结果⭐⭐⭐ 但成本高
人工审核关键场景人工确认⭐⭐⭐ 最可靠但无法规模化
LLM ≈ 一个读过很多书但可能记错的人。RAG ≈ 给他一本参考手册，让他"看着手册回答，不要靠自己记"。结构化输出 ≈ 让他填表而不是自由发挥，减少编造空间。我在客服助手项目里用RAG+温度0.5+结构化输出三管齐下控制幻觉。

6. 上下文长度与成本 ⭐⭐

大模型按token计费，输入token和输出token分别计价，输出通常比输入贵2-5倍。

模型输入价格输出价格说明
GPT-4o$2.5/1M$10/1M输出是输入的4倍
Claude 3.5$3/1M$15/1M输出是输入的5倍
DeepSeek-V3$0.27/1M$1.1/1M性价比极高

长上下文 vs RAG权衡：如果知识量小于20K token且不常更新，直接塞进上下文窗口（简单、信息完整）。但超过50K token或频繁更新，用RAG更划算——RAG只检索相关片段(几K token)，成本远低于全塞进上下文。

实际经验法则：文档<20K token且不更新→直接塞上下文；>50K token或频繁更新→用RAG。客服助手场景几乎都需要RAG——产品文档、FAQ太多了，全塞进去既贵又影响效果。

7. Function Calling原理 ⭐⭐⭐

Function Calling是LLM调用外部工具的核心机制，也是Agent能"做事"的关键能力。

Function Calling = LLM看了工具说明书后，输出一段结构化JSON告诉你要调哪个函数、传什么参数，你的代码执行后把结果喂回LLM。

7.1 完整流程

Function Calling不是魔法，它是模型训练出来的能力。模型在训练时见过大量"工具描述+用户问题→工具调用JSON"的样本，学会了根据工具描述和用户意图输出结构化调用请求。推理时，API把工具描述拼接到prompt中，模型"学会"了输出特定格式的JSON。你的代码解析JSON执行函数，把结果作为新消息送回模型，模型再生成最终自然语言回答。

Function Calling完整流程：用户提问→LLM选工具→输出JSON→执行→结果回传→LLM整合回答
Function Calling ≈ Java的动态代理+反射调用：工具描述≈接口文档/Javadoc，告诉"代理"有哪些方法可调；LLM≈动态代理层，根据输入决定调哪个方法、传什么参数；执行函数≈Method.invoke()反射执行；结果回传≈把方法返回值序列化后给代理处理。
关键：工具的description写得越好，LLM选择工具越准确。好的description应该说明：这个工具做什么、什么时候该用、什么时候不该用、参数含义。这和写好的Javadoc是一个道理。

🎤 面试实战

Transformer的自注意力机制是什么？为什么比RNN好？

自注意力让序列中每个位置都能直接和所有其他位置计算关联度，用QKV三个矩阵实现：Q是查询("我在找什么")，K是键("我能提供什么")，V是值("我的内容")，attention=softmax(QKT/√d)V。每个词的新表示是所有词的V按注意力权重加权求和。

比RNN好三个原因：1）并行化——所有位置同时计算，RNN必须串行；2）长距离依赖——任意两个位置直接相连，RNN距离远了就遗忘；3）梯度稳定——残差连接+LayerNorm缓解梯度消失。代价是O(n²)复杂度。

画QKV计算流程图加分。提一句Multi-Head是多个注意力头并行学不同模式。再提O(n²)复杂度说明你知道代价。
为什么LLM会产生幻觉？如何缓解？

本质原因是LLM是概率模型不是知识库。它预测"最可能的下一个token"，而非"正确的下一个token"。遇到知识盲区时，它生成一个"看起来合理"的答案而非承认不知道。

缓解方法：RAG最有效(给参考资料看着回答)；降低温度减少随机性；结构化输出限制格式；System Prompt加约束"不确定就说不知道"；关键场景人工审核。我在客服助手用RAG+温度0.5+结构化输出三管齐下。

必须结合项目说"三管齐下"展示工程化思维。能说出"LLM是概率模型不是知识库"这句本质话说明理解到位。
Temperature参数怎么调？数学原理是什么？

温度控制采样随机性。数学原理：adjusted_prob = softmax(logits / T)。T小放大logits差异，分布更尖锐(更确定)；T大抹平差异，分布更均匀(更随机)。

调参经验：客服用0.3-0.7要准确稳定；代码生成0.2-0.5要精确；创意写作0.8-1.2要多样性；数据提取0-0.3要确定性。我的客服助手实际用0.5。

能说出softmax(logits/T)数学公式是加分项。说"客服场景用0.5"结合项目更有说服力。
中英文token有什么差异？对成本有什么影响？

英文基本1词≈1-2个token，中文1字≈1-2个token。同样含义的文本，中文token数量是英文的2-3倍。这意味着中文场景API成本更高，上下文窗口消耗更快。

影响：1）成本预算要按中文token量估算；2）上下文窗口更容易满，需要更激进的Memory管理；3）选模型时优先考虑中文token效率优化的国产模型(Qwen2/GLM-4)。

"中文token是英文2-3倍"这个具体数字说明你真的踩过坑。提国产模型中文优化说明你有选型经验。
Function Calling的底层原理是什么？

Function Calling是模型训练出来的能力，不是魔法。模型在训练时见过大量"工具描述+用户问题→工具调用JSON"的样本，学会了根据工具描述和用户意图输出结构化调用请求。

推理时流程：1）API把工具描述拼进prompt；2）模型输出JSON指定要调的函数和参数；3）你的代码解析JSON并执行函数；4）把执行结果作为新消息送回模型；5）模型根据结果生成最终自然语言回答。类比Java就是动态代理+反射。

用Java类比解释是转行面试最佳策略——展示你能把新知识和存量经验关联。提"工具description越准确选择越准"说明你有实战经验。
长上下文和RAG什么时候用哪个？

经验法则：知识量<20K token且不常更新→直接塞上下文，简单有效；>50K token或频繁更新→用RAG，便宜且可控。

长上下文优点是简单、信息完整，但贵(O(n²)计算量)且有"Lost in the Middle"问题——中间内容容易被忽略。RAG需要向量库基建但可扩展到海量数据，且只检索相关片段成本低。生产环境推荐混合方案：System Prompt+少量RAG结果放入上下文。

提"Lost in the Middle"说明你对LLM局限性有深入理解。提"混合方案"展示工程判断力。
  • Transformer核心：自注意力让每个词看到所有词，QKV矩阵并行计算，O(n²)复杂度是上下文窗口贵的原因
  • Multi-Head：多组QKV并行学不同模式(语法/语义/位置)，最后拼接
  • Decoder-only：GPT/Claude/Llama都是Decoder-only，擅长生成；BERT是Encoder-only擅长理解
  • vs RNN：并行化+长距离依赖+梯度稳定，代价是O(n²)复杂度
  • Token是LLM原子：中文token是英文2-3倍，直接影响成本和上下文窗口
  • BPE分词：高频子串合并建词表，tokenizer≈HashMap查找表
  • Temperature：softmax(logits/T)，客服0.3-0.7、代码0.2-0.5、创作0.8-1.2
  • Top-K/Top-P：Top-K截断长尾，Top-P更自适应(概率累加达P的最小集合)
