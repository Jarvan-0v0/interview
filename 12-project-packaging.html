项目经验：mall-agent智能客服

学习目标：基于实际项目 mall-agent 源码，掌握矿池智能客服系统的完整架构、核心亮点、技术难点和面试Q&A。内容100%来自源码，不是文档纸上谈兵。

一、项目介绍（面试开场用）

面试官说"介绍一下你这个项目"时，用以下版本。控制在2分钟左右，有结构、有亮点、有深度。

矿池智能客服系统：统一ReAct Agent架构，缓存快速通道+关键词拦截+LLM自主路由，32个工具+MCP远程工具+RAG知识库预检索+质检门禁。

30秒版（快速介绍）

我做的是一个矿池智能客服系统，核心是统一ReAct Agent架构。用户提问后，系统先查缓存和转人工关键词做零成本快速拦截，然后统一进入ReAct循环——LLM自主推理决定调用哪些工具（32个本地工具+MCP远程工具），或者调用searchKnowledgeBase工具检索知识库。

项目有几个做得比较深的点：一是手写ReAct循环（Qwen兼容端点tool calling不稳定，通过Prompt约定格式+字符串解析实现）；二是RAG全链路评估（每小时自动跑Hit Rate/MRR/NDCG/忠实度/相关性五项评估）；三是质检门禁（5维度评分，低于0.6分自动重答最多3次）；四是MCP协议集成（Java实现SSE客户端，远程工具和本地工具统一注册调度）。

技术栈是Spring WebFlux + LangChain4j + Milvus + Redis + MySQL，响应式架构，用户级限流10次/分钟，全局并发100。

2分钟版（详细展开）

我做的是一个矿池智能客服系统，解决矿池运营中用户咨询量大、人工客服响应慢的问题。核心架构是统一ReAct Agent + RAG知识库 + MCP工具调用。

整体流程是这样的——没有前置意图分类器，由LLM在ReAct推理过程中自主决定路由：

  1. 缓存快速通道：SimpleQaCache命中且未过期→直接返回缓存答案（~5ms）
  2. 转人工关键词拦截：用户明确说"转人工/人工客服"→零成本立即返回转接事件
  3. 统一ReAct：问题规范化→加载历史→工具分类（关键词+LLM混合多分类）→KB预检索上下文注入→ReAct循环。LLM自主选择调用searchKnowledgeBase工具检索知识库、transferToHuman工具转人工、或32个业务工具（订单/财务/物流/商品/用户/营销等）

ReAct循环：Thought→Action→Observation→Final Answer，最多3轮，单轮90秒超时。支持并行工具调用（CompletableFuture），工具调用重试限制（MAX_TOOL_CALLS_PER_TOOL=3）。

后置处理：答案→Redis对话记忆→QualityGate质检（5维度评分，<0.6重答3次）→异步写MySQL。质检通过的答案自动缓存。

这个项目我觉得有几个做得比较深的地方：第一是手写ReAct循环，第二是RAG全链路评估，第三是质检门禁，第四是MCP协议集成，第五是从"意图分类三路路由"演进到"统一ReAct"的架构升级——这个演进本身就是亮点。

统一ReAct架构：缓存/关键词零成本拦截→统一ReAct由LLM自主路由，无前置意图分类器

二、项目六大亮点（面试时的"杀手锏"）

亮点1：手写ReAct循环（不依赖AiServices）

背景：Qwen的OpenAI兼容端点对原生tool calling支持不稳定，放弃LangChain4j AiServices的自动调用。

实现：自己实现Thought→Action→Observation循环。通过系统提示词约定格式（Action:/Final Answer:），用字符串解析提取工具名和JSON参数。流式输出时模型会编造Observation，做了StreamState状态机跟踪已发送位置，等完整响应拿到后确认没有Action才推送Final Answer给用户。

控制：最多3轮循环，单轮90秒超时（CompletableFuture+Mono.fromFuture异步等待，不阻塞WebFlux线程池），工具调用重试限制（MAX_TOOL_CALLS_PER_TOOL=3），兜底策略（Final Answer为空但有工具结果时用Observation组装）。

亮点2：RAG全链路评估（四阶段自动化）

Phase 1 检索层：算Hit Rate/MRR/NDCG，判断黄金数据对应的chunk是否在top-K中

Phase 2 Rerank层：对比Rerank前后NDCG变化，量化Rerank提升效果

Phase 3 忠实度：LLM-as-Judge评判回答是否忠实于检索内容（有无幻觉）

Phase 4 相关性：LLM-as-Judge评判回答是否切题

机制：每小时@Scheduled执行，基于人工审核的黄金数据（rag_golden_data），指标持久化到MySQL可追溯。

亮点3：质检门禁+自动重答（QualityGate）

每次回答后异步调用QualityJudge（LLM-as-Judge, Qwen）做5维度评分：准确性(30%)+完整性(25%)+有用性(20%)+简洁性(15%)+安全性(10%)。

≥0.8通过，0.6-0.8警告，<0.6自动重答最多3次。重答时传递扣分理由让模型针对性改进（如"准确性不足：回答中订单号错误"）。质检超时或不可用时跳过，直接返回原始答案。质检通过的答案自动缓存。

亮点4：MCP协议集成（Java实现客户端）

用Java实现MCP客户端，通过SSE长连接+JSON-RPC连接mall-mcp-server。启动时自动发现远程工具（tools/list），McpToolAdapter包装为HardWorkflowTool接口，与本地32个工具统一注册到HardWorkflowToolRegistry。MCP不可用时返回disabled()占位实例，本地工具不受影响。

亮点5：工具分类选择性注入（Token降60-80%）

ToolRouter做关键词+LLM混合多分类，返回Set<ToolCategory>（如"订单+物流"）。8个分类：ORDER(订单)/FINANCE(财务)/LOGISTICS(物流)/PRODUCT(商品)/USER(用户)/SERVICE(客服政策)/MARKETING(营销)/GENERAL(通用)。根据分类只注入相关工具到系统提示词，Token消耗降低60-80%，工具选择准确率显著提升。

亮点6：架构演进——从意图分类到统一ReAct

项目经历了一次重要架构演进：早期版本用IntentClassifier做意图分类，分知识库/通用/转人工三路。后来发现三路路由维护复杂、KB路径和General路径代码重复、LLM分类3s超时影响响应速度。

演进后：移除IntentClassifier，改为统一ReAct模式——缓存和关键词做零成本快速拦截，其他统一进ReAct。LLM在推理过程中自主决定是否调用searchKnowledgeBase工具（知识库）、transferToHuman工具（转人工）、或业务工具。好处是：代码更简洁、路由更灵活（LLM能处理意图分类无法覆盖的复杂场景）、维护成本更低。

这个演进本身就是面试亮点——展示你不仅能写代码，还能判断架构什么时候该重构、怎么重构。

K8s配置要点

  • replicas: 3——三副本保证高可用，maxUnavailable: 0保证滚动更新时不中断服务

  • 资源限制——requests保证最低资源，limits防止OOM影响同节点其他Pod
  • ConfigMap管理配置——数据库连接、模型端点等环境差异配置通过ConfigMap注入，不硬编码

四、核心代码实现解析

面试中如果被问到"能看看你写的代码吗"，这一节就是准备好的"代码展示"。精选三个最核心的模块：ReAct循环流式解析、MCP客户端、QualityGate质检门禁。

4.1 ReAct循环流式解析（StreamState状态机）

Java (StreamState状态机核心逻辑) 
// StreamState枚举：跟踪LLM流式输出的当前状态
enum StreamState {
    THOUGHT,       // 正在输出Thought
    ACTION_NAME,   // 正在输出Action: 工具名
    ACTION_JSON,   // 正在输出Action的JSON参数
    FINAL_ANSWER,  // 正在输出Final Answer
    DONE           // 输出完成
}

// 核心逻辑：逐token解析，状态机跟踪
for (String token : streamTokens) {
    buffer.append(token);
    switch (state) {
        case THOUGHT:
            if (buffer.contains("Action:")) {
                state = StreamState.ACTION_NAME;
                // 不推送Thought内容给用户
            }
            break;
        case ACTION_NAME:
            if (buffer.contains("```json")) {
                extractActionName();
                state = StreamState.ACTION_JSON;
            }
            break;
        case ACTION_JSON:
            if (buffer.contains("```")) {
                extractActionParams();
                // 执行工具调用，进入下一轮ReAct
                executeTool(actionName, actionParams);
                state = StreamState.THOUGHT;  // 重置
            }
            break;
        case FINAL_ANSWER:
            // 确认没有Action后才推送Final Answer给用户
            pushToUser(token);
            break;
    }
}

StreamState的核心价值：防止LLM在流式输出时编造Observation。LLM可能在Action还没执行时就输出虚构的Observation结果——"流量: 100TH/s"看起来像真的，但实际没调工具。StreamState状态机跟踪已发送位置，等完整响应拿到后确认没有Action才推送Final Answer给用户。代价是牺牲打字机效果，但保证了正确性。

4.2 MCP客户端实现

Java (MCP SSE客户端) 
public class McpSseClient {
    private final WebClient webClient;

    // 建立SSE连接
    public Flux<String> connect() {
        return webClient.get().uri("/sse")
            .accept(MediaType.TEXT_EVENT_STREAM)
            .retrieve().bodyToFlux(String.class);
    }

    // JSON-RPC请求
    public Mono<JsonNode> send(String method, JsonNode params) {
        return webClient.post().uri("/mcp/message")
            .bodyValue(Map.of("jsonrpc","2.0", "method",method))
            .retrieve().bodyToMono(JsonNode.class);
    }

    // 工具发现
    public List<ToolDef> listTools() {
        return send("tools/list", null).map(this::parseTools).block();
    }
}

// McpToolAdapter：将MCP工具包装为HardWorkflowTool接口
public class McpToolAdapter implements HardWorkflowTool {
    private final McpSseClient client;
    private final ToolDef toolDef;

    @Override
    public ToolResult execute(Map<String,Object> args) {
        String json = client.callTool(toolDef.name(), args).block();
        return ToolResult.success(json);
    }

    public static McpToolAdapter disabled() {
        return new McpToolAdapter(null, null) {
            public ToolResult execute(Map args) {
                return ToolResult.error("MCP服务不可用");
            }
        };
    }
}

六、项目五大难点踩坑（面试官最爱问）

难点1：Qwen兼容端点tool calling不稳定 → 被迫手写ReAct

问题：Qwen的OpenAI兼容端点不支持原生tool calling，LangChain4j AiServices自动调用工具不可靠。

解决：放弃AiServices，自己实现ReAct循环。系统提示词约定Action:/Final Answer:格式，字符串解析提取工具名和参数。兼容所有模型，精细控制流式推送时机。

难点2：流式输出时模型编造Observation/Final Answer

问题：LLM流式输出时，模型可能在Observation位置直接编造工具结果，或在Final Answer还没到时就推送。

解决：StreamState状态机跟踪已发送位置——流式输出先通过状态机判断，等完整响应拿到后确认没有Action才推送Final Answer给用户。如果有Action，先执行工具再进下一轮。代价是牺牲打字机效果，但保证了正确性。

难点3：Rerank超时降级vs用户体验权衡

问题：DashScope gte-rerank有时超时，降级为向量检索原始顺序会影响精度。

解决：10秒超时，超时返回null，调用方降级为向量检索原始顺序。onErrorResume确保降级不影响主流程。权衡：Rerank提升精度但增加延迟，生产环境根据P95延迟决定是否启用。

难点4：多模型降级时Token消耗累积

问题：模型降级时，前一个模型已消耗了token（可能已部分输出），切换下一个模型需要重新发送完整prompt，token消耗翻倍。

解决：降级只在模型调用失败时触发（网络错误/超时），不在"回答质量差"时触发。质检门禁的重答是异步的，不阻塞用户已收到的流式回答。

难点5：MCP SSE长连接断线

问题：mall-mcp-server重启或网络抖动时，SSE连接断开，MCP远程工具不可用。

解决：启动时连接失败返回disabled()占位实例，本地工具不受影响。运行中断开时工具调用返回错误JSON，ReAct感知失败后尝试其他工具。欠缺：没有自动重连，生产环境应加指数退避重试。

七、面试Q&A（项目深挖）

Q1：你的项目整体架构是什么？

核心架构是统一ReAct Agent——缓存快速通道（SimpleQaCache命中直接返回，~5ms）+ 转人工关键词拦截（"转人工"等零成本）+ 统一ReAct循环。

没有前置意图分类器。所有非缓存、非关键词拦截的问题统一进入ReAct循环。LLM在ReAct推理中自主决定：调用searchKnowledgeBase工具检索知识库、调用transferToHuman工具转人工、或调用32个业务工具（订单/财务/物流/商品/用户/营销等）。

ReAct循环：Thought→Action→Observation→Final Answer，最多3轮，单轮90秒超时。支持并行工具调用，工具分类选择性注入（Token降60-80%）。后置：Redis记忆→QualityGate质检→MySQL持久化。

提"统一ReAct，无前置意图分类器"展示架构演进。提"缓存~5ms"和"关键词零成本"展示快速通道设计。数字要记准：32工具/3轮/90s。
Q2：你的项目为什么选择手写ReAct而不是用LangChain4j的AiServices？

项目实际原因：Qwen的OpenAI兼容端点不支持原生tool calling，AiServices的动态代理依赖模型返回tool_calls格式，Qwen不稳定。

手写ReAct的优势：1）兼容所有模型（Prompt约定格式+字符串解析，不依赖原生function calling）；2）完全控制流式推送时机（StreamState状态机，防止模型编造Observation）；3）精细控制超时（单轮90s）和最大轮次（3轮）；4）完整兜底策略。

同时我也理解AiServices的原理：底层是JDK动态代理(InvocationHandler)，自动将@Tool方法注册为ToolSpecification，LLM返回tool_calls时自动反序列化参数并调用。但Qwen兼容端点不稳定所以放弃。

先说"为什么"（Qwen不支持），再展示"我理解AiServices原理但选择不用"的工程判断力。提"StreamState状态机防编造Observation"是亮点。
Q3：项目最大的技术挑战是什么？怎么解决的？

最大挑战是Qwen兼容端点tool calling不稳定导致LangChain4j AiServices不可用。

解决：放弃AiServices自动调用，自己实现完整ReAct循环。系统提示词约定Action:/Final Answer:格式，用字符串解析提取工具名和JSON参数。支持多工具并行调用（CompletableFuture执行），工具调用重试限制（MAX_TOOL_CALLS_PER_TOOL=3），兜底策略（Final Answer为空时用Observation组装）。

落地效果：兼容所有模型不依赖原生function calling，Token消耗降低70-80%（工具分类选择性注入），响应速度提升2-3倍（并行工具调用+记忆管理优化）。

讲"挑战→解决→效果"三段式。提"Token降70-80%"和"速度提升2-3倍"这些量化数据说明有实际收益。
Q4：你的项目架构演进过吗？

是的，项目经历了一次核心架构演进。早期版本用IntentClassifier做意图分类，分知识库/通用/转人工三路。后来发现三个问题：1）三路路由维护复杂，KB路径和General路径代码重复；2）LLM意图分类3s超时影响响应速度；3）意图分类是硬编码的，无法处理跨类别的复杂问题。

演进后：移除IntentClassifier，改为统一ReAct模式——缓存和关键词做零成本快速拦截，其他统一进ReAct。LLM在推理中自主决定路由。好处是：代码更简洁、路由更灵活（LLM能处理意图分类无法覆盖的复杂场景）、维护成本更低。

这个演进验证了一个设计原则：让LLM做路由决策比硬编码分类更灵活，但前提是你得通过工具分类选择性注入控制Token消耗。

这是最大的加分项——展示架构迭代能力。讲"为什么改"和"改后好处"三段式。提"让LLM做路由比硬编码更灵活"是设计哲学。
Q5：你的知识库检索流程是怎样的？

知识库检索有两层：1）KB预检索——ChatService在进入ReAct前，对匹配KB关键词的问题做预检索（KnowledgeBaseService.retrieveContext），将检索结果注入ReAct上下文。2）LLM自主调用——ReAct循环中LLM也可以自主调用searchKnowledgeBase工具检索。

预检索流程：问题→QuestionFormatService规范化（LLM改写口语化问题，temp=0.3）→Qwen Embedding生成向量→Milvus向量检索（minScore=0.7过滤）→DashScope gte-rerank重排→取topK条。预检索结果高于0.65相似度才注入上下文。

分块策略：DocumentSplitters.recursive(500, 50)，每片500字重叠50字。

提"两层检索"（预检索+LLM自主）是亮点，展示不是只靠LLM记得调工具。数字要准：500字/50重叠/0.7过滤/0.65注入阈值。
Q6：为什么向量检索后还要Rerank？

向量检索用Bi-Encoder（问题和文档各自编码再算余弦相似度），速度快但精度有限——query和doc没有深度交互。Rerank用Cross-Encoder（将query-document拼一起送入模型联合编码），能捕捉细粒度语义交互，精度更高但计算量大。

两阶段策略：向量检索粗排（快，召回16条）→Rerank精排（准，取top4条）。项目用DashScope gte-rerank，10秒超时，失败降级为向量检索原始顺序。

Bi-Encoder vs Cross-Encoder是核心知识点。提"10秒超时降级"展示容错。能说出"粗排快+精排准"的两阶段思路。
Q7：你的ReAct循环是怎么控制死循环的？

三层控制：1）最大轮次：maxRounds=3，超过3轮强制结束；2）单轮超时：单轮90秒超时（CompletableFuture+Mono.fromFuture异步等待），防止LLM卡住，不阻塞WebFlux线程池；3）单工具调用限制：MAX_TOOL_CALLS_PER_TOOL=3，同一工具最多调用3次。

兜底策略：3轮后Final Answer为空但有工具结果时，用最近一次Observation组装兜底回答（buildFallbackFromObservations），不会给用户返回空。

三层控制（轮次/超时/工具次数）展示防御性编程。提"CompletableFuture不阻塞WebFlux"说明你理解响应式编程。
Q8：MCP协议是什么？你的项目怎么集成的？

MCP（Model Context Protocol）是Anthropic提出的标准化AI工具调用协议，解决"每个框架自己定义工具接口格式，工具无法跨框架复用"的问题。

项目实现：Java实现MCP客户端，通过SSE长连接+JSON-RPC连接mall-mcp-server。启动时连接→tools/list发现远程工具→McpToolAdapter包装为HardWorkflowTool接口→与本地32个工具统一注册。客户端GET /sse建立连接，POST /mcp/message发送JSON-RPC请求。MCP不可用时返回disabled()占位实例。

说"Java实现MCP客户端"是加分项。提"SSE长连接+JSON-RPC"展示实现细节。提"disabled占位实例"展示容错。
Q9：你的评测链路是怎么做的？

两层评测：1）质检门禁(QualityGate)——每次回答后LLM-as-Judge做5维度评分(准确性/完整性/有用性/简洁性/安全性)，≥0.8通过，<0.6自动重答3次。2）RAG批量评估(RagEvaluator)——每小时@Scheduled执行四阶段：检索层(Hit Rate/MRR/NDCG)→Rerank层(前后NDCG对比)→忠实度(LLM-Judge)→相关性(LLM-Judge)。基于人工审核的黄金数据。

说"四阶段+每小时+黄金数据"展示系统性。提"5维度加权评分"和"重答传递扣分理由"展示工程化。
Q10：你的系统怎么应对高并发？

已有的：用户级10次/分钟（滑动窗口算法）+ 全局并发100（AtomicInteger计数）+ WebFlux背压（响应式流天然支持）。

欠缺的：没有Token级别限流（只限请求次数没限token消耗量）。面试回答策略：先说已有的，再说欠缺的，最后说方案——Token限流用Redis+滑动窗口记录每用户token消耗，超阈值拒绝。LLM调用加Resilience4j RateLimiter按租户限流。

先说已有再承认欠缺是好的策略。提"Token级限流"和"Resilience4j"展示你知道怎么补。
Q11：为什么选langchain4j不选Python LangChain？

四个维度：1）技术栈统一——团队是Java后端，复用Spring Boot运维体系(监控/部署/CI/CD/日志)；2）学习成本低——Java工程师学langchain4j比学Python快；3）部署运维一致——Java jar部署到现有K8s，不需要Python运行环境；4）权衡——承认Python生态更成熟，但对Java团队TCO(总拥有成本)更低。

四维度+承认权衡是标准答法。提"TCO更低"体现工程思维。
Q12：如果重新做你会怎么改进？

1）引入Hybrid Search（向量+BM25），当前只有纯向量检索+Rerank，专有名词/订单号精确匹配弱；2）MCP加自动重连（指数退避重试），当前断线只有disabled降级；3）Token级限流，当前只限请求次数；4）流式输出优化，当前StreamState缓冲牺牲了打字机效果，可以探索更精细的流式推送；5）如果模型支持原生function calling（如换DeepSeek），可以回归AiServices方式减少手写维护成本。

每条改进都要说"当前是什么→缺什么→怎么改"。提"换模型可以回归AiServices"展示你不是为了手写而手写。
Q13：你的系统部署架构是怎样的？

Docker多阶段构建 → 推送Docker Hub（jarvan616/mall-agent:vX）→ K8s Deployment（3副本，RollingUpdate，maxUnavailable: 0保证不中断）→ Rancher管理。镜像用版本Tag不用:latest，确保精确回滚。

说"版本Tag不用:latest"和"maxUnavailable: 0"展示K8s实战经验。提ConfigMap展示配置管理。
Q14：Tool调用是怎么注册和调度的？

HardWorkflowToolRegistry管理所有工具，分为两类：本地工具（32个，直接实现HardWorkflowTool接口，Spring Bean注册）和MCP远程工具（启动时通过McpSseClient连接mall-mcp-server→tools/list发现→McpToolAdapter包装→注册）。

调度流程：ToolRouter先做关键词+LLM混合多分类（8个分类：ORDER/FINANCE/LOGISTICS/PRODUCT/USER/SERVICE/MARKETING/GENERAL），根据分类结果选择性注入相关工具到系统提示词。LLM在ReAct中输出Action: tool_name → 字符串解析提取工具名和JSON参数 → Registry查找工具 → 执行。MCP不可用时返回disabled()占位实例。

提"8个分类"和"选择性注入"展示工具管理。说"本地+MCP统一注册"展示架构设计。
Q15：Token成本怎么控制的？

五层成本控制：1）工具分类选择性注入——不是32个工具全部注入，而是根据关键词+LLM分类只注入4-5个相关工具，系统提示词从2000降到400-800 tokens（降60-80%）；2）记忆管理——简化历史格式（user: xxx | assistant: xxx），动态消息限制，Token降33%；3）工具调用重试限制——MAX_TOOL_CALLS_PER_TOOL=3，Token降30-50%；4）并行工具调用——一次Action多工具并行，减少轮次，Token降67%；5）多模型梯度——dev用Qwen 7b（最便宜），staging用32b，生产用72b，按场景分配模型容量。

五层成本控制层层递进。记住核心数字：工具注入降60-80%、记忆降33%、并行降67%。

十一、项目复盘与经验总结

面试官问"如果重新做你会怎么改进"时，不要只说"会做得更好"，要有具体的反思和可操作的改进点。

做对了什么

  1. 从实际约束出发做技术决策：Qwen tool_calling不稳定→手写ReAct，不是硬上AiServices碰运气
  2. 敢于架构演进：从IntentClassifier三路路由→统一ReAct，代码更简洁、路由更灵活
  3. 质量保障前置：质检门禁+RAG评估在项目中期就做了，不是上线后被骂才加
  4. 成本意识贯穿始终：工具分类注入、多模型梯度、记忆管理——Agent最大的隐性成本就是Token
  5. 拥抱MCP标准：Java实现MCP客户端，提前卡位行业趋势

踩过的坑

坑1：LLM编造Observation——流式输出时Action还没执行就输出虚构结果。解决：StreamState状态机+缓冲解析。教训：Agent场景正确性优先于体验。

坑2：Nginx proxy_buffering破坏流式——本地SSE正常，部署后变批量。解决：proxy_buffering off + K8s Ingress annotation。教训：本地跑通≠部署环境跑通。

坑3：工具描述太技术化——"查询算力贡献记录及收益分配明细"→LLM理解为"修改收益分配"。解决：用户视角+只读标注。教训：LLM用自然语言理解工具。

坑4：IntentClassifier维护成本高——三路路由代码重复，LLM分类3s超时。解决：演进为统一ReAct。教训：硬编码分类不如让LLM自主路由。

坑5：CountDownLatch阻塞WebFlux线程——ReAct超时等待用CountDownLatch.await()，阻塞了事件循环线程。解决：改为CompletableFuture+Mono.fromFuture异步等待。教训：响应式编程中任何阻塞调用都是定时炸弹。

架构反思：如果重来

  1. 模型层抽象：Qwen/DeepSeek切换逻辑散落各处，应抽象ModelRouter统一管理选择、降级、Token计费
  2. 工具插件化注册：HardWorkflowToolRegistry硬编码，应改为类似Spring @Bean自动发现
  3. 混合检索：纯向量检索对专有名词不友好，应引入BM25全文检索做RRF融合排序
  4. MCP做成Server：当前是MCP客户端调用远程服务，更合理的架构是mall-agent本身作为MCP Server暴露工具给其他系统复用
  5. 流式双模式：支持原生tool_calls的模型走流式推送，不支持的走缓冲解析，根据模型能力自动选择
