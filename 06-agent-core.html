CHAPTER 06

Agent核心概念

🎯 学习目标：理解Agent的本质（感知->决策->行动->观察的自主系统），掌握ReAct、Planning、Tool Use、Multi-Agent协作等核心机制，能用Java工程师熟悉的概念类比讲清楚Agent与传统chatbot/workflow的区别，从容应对转行面试的核心问题。

Agent不是"会聊天的机器人"，而是"会自己决定做什么、调用什么工具、并根据结果调整下一步"的自主系统——它的核心是决策循环，而不是对话能力。

1. 什么是Agent ★★★★★ 必考

很多人把Agent和Chatbot混为一谈，这是面试中最常见的认知误区。面试官问"什么是Agent"，本质是在考察你对自主决策这一核心特征的理解。

Agent的本质定义：Agent是一个以LLM为大脑、通过感知->决策->行动->观察循环自主完成任务的系统。它不只是回答问题，而是主动决定做什么。具体来说，Agent接收用户输入或环境状态（感知），LLM推理出该做什么、用什么工具（决策），调用工具/API执行具体操作（行动），获取执行结果并判断是否继续循环（观察）。这个循环会持续进行，直到LLM判断任务完成。

Agent vs Chatbot vs Workflow的核心区别在于决策由谁做。Chatbot无决策能力——用户问什么，LLM直接用自身知识回答，遇到不知道的就开始"编"（幻觉），因为它没有获取外部真实信息的手段。Workflow的决策由开发者预先编排——A->B->C->D的执行路径在代码里写死，LLM只在每个节点"填空"（比如A节点让LLM做摘要，B节点让LLM做分类），路径不会因中间结果改变。Agent的决策由LLM动态完成——它根据当前上下文和上一步结果，自主决定下一步调什么工具、是否继续循环、何时结束。这带来灵活性，但也带来不可控性。

Agent的核心能力：感知-决策-行动-观察循环

  • 感知（Perceive）：接收用户输入或环境状态（如工具返回结果）
  • 决策（Reason）：LLM推理该做什么、用什么工具、传什么参数
  • 行动（Act）：调用工具/API执行具体操作（查库、调接口、发邮件）
  • 观察（Observe）：获取执行结果，判断是否完成任务、是否继续循环

这四步循环是所有Agent的执行骨架，ReAct、Plan-and-Execute等模式都是在这个骨架上的变体。

Agent ≈ Spring MVC Controller + Service层自动编排 + 外部API调用。Controller接收请求，但不像传统Controller那样写死调用链，而是把"该调哪个Service"这个决策权交给LLM；Service层也不再是固定方法栈，而是LLM根据上下文动态选择工具组合。可以把Agent理解为一个"方法调用栈由LLM实时决定"的Service编排器——传统Controller的方法调用链是编译期确定的，Agent的方法调用链是运行时由LLM决定的。

2. ReAct模式 (Reasoning + Acting) ★★★★★ 必考

ReAct是Agent最核心的执行范式，几乎所有的Agent框架都基于它。"ReAct" = Reasoning（推理）+ Acting（行动），由Yao等人2022年提出，核心思想是让LLM边想边做边看。

ReAct为什么有效：如果直接让LLM调用工具（不先推理），LLM经常盲目调用——用户问"帮我查下北京天气顺便推荐穿什么"，不推理的LLM可能直接调getWeather，拿到天气后再调getClothingRecommendation，但它没有先想"这个问题需要两步：先查天气，再根据天气推荐穿搭"。ReAct强制LLM在每次行动前先输出一段自然语言推理（Thought），这段推理帮助LLM理清思路、避免盲目调工具、也方便人类调试时看到LLM的"思考过程"。

循环机制：Think->Act->Observe->Think->Act->Observe...直到LLM在Think阶段判断"任务已完成，可以输出最终答案"，循环终止。框架通常设置maxIterations（如10次）防止死循环——如果LLM一直调工具但始终无法完成任务，到上限就强制终止并返回当前结果。这个参数是Agent工程化的必配项。

ReAct = "我想想该做什么 -> 我去做 -> 我看看结果 -> 我再想想"——一个不断循环的决策过程，直到任务完成。
图6-2 ReAct循环：Think -> Act -> Observe -> Think（继续或结束）。强制先推理再行动，避免盲目调工具。

这个循环会一直进行，直到LLM判断任务已完成（输出Finish）或达到最大迭代次数上限。这就是为什么Agent需要设置maxIterations参数——防止它陷入死循环。

Java · langchain4j ReAct Agent 
// langchain4j 对ReAct的封装：AiServices + Tools
interface CustomerServiceAgent {
    @SystemMessage("你是一个智能客服助手，可以查询订单、物流、退换货。"
            + "请先想清楚需要调用哪些工具，再执行。")
    String chat(@UserMessage String userMessage);
}

// 定义Agent可用的工具——LLM会根据description自主决定是否调用
class OrderTools {
    @Tool("根据订单号查询订单状态，返回订单当前所在环节和预计送达时间")
    public String queryOrder(@P("订单号") String orderId) {
        return orderService.getStatus(orderId);  // 实际查库
    }

    @Tool("根据订单号查询物流轨迹，返回最近3条物流信息")
    public String queryLogistics(@P("订单号") String orderId) {
        return logisticsService.getTrack(orderId);
    }
}

// 组装Agent——框架底层就是ReAct循环
CustomerServiceAgent agent = AiServices.builder(CustomerServiceAgent.class)
    .chatLanguageModel(model)
    .tools(new OrderTools())
    .build();

// 用户问"我的订单20230801到哪了"——Agent会自己想：
// Think 1: 需要先查订单状态
// Act 1:   调用 queryOrder("20230801")
// Observe 1: 拿到订单状态=已发货
// Think 2: 已发货，那就查物流
// Act 2:   调用 queryLogistics("20230801")
// Observe 2: 物流轨迹...
// Think 3: 信息齐全，可以回答用户了 -> 输出最终答案
String answer = agent.chat("我的订单20230801到哪了");
很多面试者只会背概念，但说不清"Think具体在想什么"。Think阶段LLM输出的是一段自然语言推理（"我需要先查订单状态..."），框架解析这段推理后决定调用哪个工具。description写不好，LLM就会在Think阶段选错工具。

3. Planning（任务规划） ★★★★☆

复杂任务单步ReAct可能走偏——LLM边走边想，容易在某个分支钻牛角尖，或者走了十步才发现方向错了。Planning让Agent先拆解再执行，像项目经理一样先排期再干活。

Agent如何分解复杂任务：用户说"帮我分析竞品并出一份报告"，单步ReAct的LLM可能上来就调搜索工具，搜一个竞品就开始写报告，写到一半发现信息不全又回去搜——效率低且容易遗漏。有Planning能力的Agent会先输出一个任务分解：1.搜索竞品名单获取3家主要竞品 -> 2.对每家竞品分别搜索产品特性、定价 -> 3.汇总对比生成报告大纲 -> 4.按大纲撰写报告输出。然后逐个执行子任务，每个子任务内部仍是ReAct循环，Planning只是把"大目标"切成"小目标序列"。

两种范式的本质区别：ReAct是边走边想——每一步都根据上一步结果现场决定，灵活但容易跑偏、token消耗大（每步都要推理）。Plan-and-Execute是先规划后执行——Planner角色一次性生成完整计划，Executor角色逐个执行，结构清晰、可并行子任务，但规划固化、难应对突发情况（计划生成时没预料到的信息）。实际工程中常混合使用：先Plan出骨架，每个子任务内部用ReAct灵活执行。

Plan-and-Execute vs ReAct 两种范式

维度ReActPlan-and-Execute
规划时机边走边想，不预先规划先一次性规划，再逐个执行
结构单循环：Think-Act-ObservePlanner + Executor 双角色
优点灵活、能根据中间结果调整结构清晰、可并行子任务、token省
缺点容易跑偏、token消耗大规划固化、难应对突发情况

Planning ≈ 工作流引擎（Camunda/Activiti）的BPMN任务分解。Camunda里你画一张流程图，引擎按节点推进；Plan-and-Execute就是让LLM动态画出这张流程图再执行——Planner生成计划相当于生成BPMN定义，Executor按节点推进。ReAct则更像事件驱动——没有预定义流程，每一步都根据上一步结果现场决定，类似复杂事件处理（CEP）。

4. Tool Use（工具使用） ★★★★★ 必考

Tool Use是Agent区别于Chatbot的根本能力。没有工具，Agent就退化成Chatbot。Function Calling是Tool Use在OpenAI API层的实现方式，现已成为各家模型的标准能力。

Function Calling完整流程：①开发者用@Tool注解定义工具方法，框架把方法名、description、参数Schema转成JSON Schema发给LLM；②用户提问，LLM分析问题语义，根据每个工具的description决定是否调用工具、调哪个、传什么参数；③LLM输出一个结构化的ToolExecutionRequest（包含工具名+参数JSON），而不是直接输出自然语言；④框架解析请求，用反射调用对应的Java方法；⑤方法执行结果作为ToolExecutionResult回传给LLM；⑥LLM基于工具结果生成最终自然语言回答，或继续调用下一个工具（循环）。

LLM如何选择正确的工具：核心靠工具的description。LLM看不到你的Java代码，它只读每个工具的描述字符串和参数描述，根据用户问题的语义匹配最合适的工具。这就像用户在API网关上看每个微服务的接口文档来决定调哪个API——description就是工具的"接口文档"。描述写得模糊或不全，LLM就会选错或漏选。

图6-3 Function Calling完整流程：用户提问 -> LLM分析(读description) -> 选Tool -> 执行 -> 返回 -> LLM整合 -> 回答（可循环）

好的 description vs 差的 description

description是LLM选工具的唯一依据。LLM没有"调用代码"的能力，它只是读了每个工具的description，根据用户问题语义匹配最合适的工具。

description写得模糊或不全，LLM就会选错工具或不调用。比如"查询订单"和"查询订单状态"是两个不同的工具——如果description都只写"查询订单"，LLM根本分不清。建议：description要写清输入什么、输出什么、什么场景该用。
Java · 工具描述的最佳实践 
// ❌ 差的description——LLM容易选错
@Tool("查询订单")
public String queryOrder(String orderId) { ... }

// ✅ 好的description——输入、输出、场景都讲清楚
@Tool("根据订单号查询订单状态，返回订单当前环节（待付款/已发货/已签收）"
    + "和预计送达时间。当用户询问'我的订单到哪了'、'订单状态'时使用。")
public String queryOrder(@P("订单号，纯数字，如20230801") String orderId) { ... }

多工具编排

实际项目会有5-20个工具。LLM通过ReAct循环自主编排多个工具的调用顺序。比如"帮我查订单20230801的状态，顺便看看能不能退"：

  • Think 1：需要先查订单状态 -> 调 queryOrder
  • Observe 1：已签收
  • Think 2：已签收的要看退换货政策 -> 调 queryReturnPolicy
  • Observe 2：7天无理由
  • Think 3：综合回答用户

这种"按需串联"就是多工具编排的本质——没有硬编码调用顺序，全靠LLM根据上下文决定。这也是Agent比固定Workflow灵活的根本原因。

5. Multi-Agent协作 ★★★☆☆

单个Agent能力有限——工具太多description会互相干扰，上下文太长LLM容易"忘记"前面的任务。复杂任务常拆给多个Agent协作，每个Agent专注一个领域，工具集小、上下文聚焦、准确率更高。这是当下Agent工程化的热门方向。

三种主流协作模式各有适用场景：Supervisor-Worker（主管-工人）有一个中心Supervisor Agent负责任务拆解和分发，多个Worker Agent各司其职执行子任务，结果汇总回Supervisor整合。这是工程中最常用的模式——职责清晰、可控性强、好调试。Pipeline（流水线）是Agent串联——A的输出是B的输入，B的输出是C的输入，像工厂流水线。适合步骤固定但每步都需要LLM智能的任务。Router（路由器）是一个Router Agent根据输入分类，路由到对应的专家Agent——类似API网关的请求分发。

图6-4 三种Multi-Agent协作模式对比：Supervisor-Worker / Pipeline / Router
Multi-Agent ≈ 微服务架构中的服务编排。Supervisor-Worker就是API网关 + 后端微服务模式——网关（Supervisor）做路由分发，各微服务（Worker）独立处理。Pipeline像消息驱动的事件链——Kafka里topic A的消费者处理完发到topic B。Router就是纯粹的API网关路由——根据请求路径分发到不同后端。区别在于：微服务用代码做路由，Multi-Agent用LLM做路由决策。
工程经验：Supervisor-Worker最常用因为可控——Supervisor能看到所有Worker的状态，可以兜底。Pipeline适合步骤明确的分析类任务。Router适合意图分类明确的客服场景。Peer-to-Peer（无中心节点，Agent互调）灵活但难调试，实际工程中很少用。

6. Agent vs Chain vs Workflow ★★★★☆

面试官最爱问的"选择题"：什么场景该用Agent，什么场景该用固定Workflow？答错会显得你对工程化没有判断力。

判断标准是"流程能否穷举"。如果业务流程是确定的、步骤可以枚举（比如"用户提交订单->校验库存->扣款->生成发货单"），用Workflow——路径写死、可控性强、好调试、成本低、出问题能精确定位是哪个节点。如果任务开放性强、路径无法预先知道（比如"帮我研究一下竞品并给建议"），用Agent——靠LLM动态决策，灵活但路径不固定、调试难、成本高（每次都调LLM做决策）。

实际工程的最佳实践是混合用：90%的企业场景用Workflow + 少量Agent节点就够了——主干用Workflow保证可控，少数需要灵活决策的节点嵌一个Agent。比如客服流程：识别意图（Workflow固定节点）-> 分发到对应处理逻辑（Router）-> 处理逻辑中用Agent综合多工具结果（Agent节点）-> 格式化输出（Workflow固定节点）。不要为了"看起来高级"而滥用纯Agent方案——成本高、不稳定、难维护。

维度AgentChain（链）Workflow（工作流）

Agent ≈ 动态代理（Dynamic Proxy），运行时才决定调用哪个方法；Workflow ≈ Template Method模式，父类定好骨架、子类填空；Chain ≈ 责任链模式（Chain of Responsibility），一个节点处理完传给下一个。选哪个？业务流程能枚举完就用Workflow，流程无法穷举就上Agent。这不是技术优劣，是适用场景不同。
工程经验之谈：90%的企业场景其实用Workflow + 少量Agent节点就够了——固定流程部分用Workflow保可控，少数需要灵活决策的节点嵌一个Agent。纯Agent方案成本高、不稳定，不要为了"看起来高级"而滥用。面试时强调这个观点，立刻显得你做过真实项目、知道成本和稳定性取舍。

面试场景演练

Q1：什么是Agent，和普通chatbot有什么区别？

Agent是一个以LLM为大脑、能通过感知->决策->行动->观察循环自主完成任务的系统。它和Chatbot的核心区别在于决策能力：Chatbot只能用模型自身知识回答，遇到不知道的就会"编"（幻觉）；Agent能在推理后主动调用外部工具（查库、调API）来获取真实信息，再基于结果回答。

举个客服例子：用户问"订单20230801到哪了"，Chatbot只能猜，Agent会调用queryOrder工具查真实状态再回答。本质上Agent多了一个"行动层"——能跟外部世界交互。

用Java类比打高分会：Agent ≈ Controller + LLM动态编排的Service + 外部API，决策权从硬编码转移到了LLM。
Q2：ReAct模式是什么，画一下流程？为什么有效？

ReAct = Reasoning + Acting，核心是Think -> Act -> Observe的循环。LLM先推理该做什么（Think），再调用工具执行（Act），拿到结果观察（Observe），然后再次Think判断是否完成——循环直到输出最终答案。

为什么有效：强制LLM在行动前先输出自然语言推理，帮助理清思路、避免盲目调工具。比如"查天气顺便推荐穿搭"，不推理的LLM可能直接调getWeather但忘了后续要推荐穿搭；ReAct的Think阶段会输出"需要两步：先查天气，再根据天气推荐穿搭"，思路清晰。

比如"查订单状态"：Think 1（要查订单）-> Act（调queryOrder）-> Observe（已发货）-> Think 2（要查物流）-> Act（调queryLogistics）-> Observe（轨迹）-> Think 3（信息齐全，回答用户）。

能在白板/纸上现场画出Think-Act-Observe循环图是加分项；提到maxIterations防死循环更体现工程意识。说"先推理再行动避免盲目调工具"展示你理解Why。
Q3：Agent怎么决定调用哪个工具？

靠工具的description。LLM读每个工具的描述（"这个工具做什么、输入什么、什么场景用"），把用户问题的语义和description做匹配，选最合适的工具。所以description写得好坏直接决定Agent准不准——描述模糊，LLM就会选错或漏选。

实践上：description要包含功能 + 输入参数含义 + 触发场景，参数也要用@P注明含义。不能只写"查询订单"，要写"根据订单号查状态，返回环节和预计送达，当用户问订单到哪了时使用"。

差的description："查询订单"——LLM无法区分是查状态、查物流还是查详情。好的description：写清功能+输入+输出+触发场景。

举一个"差description vs 好description"的对比例子，立刻显得有实战经验。
Q4：多Agent协作有哪些模式？你的项目用的哪种？

主要有三种：Supervisor-Worker（主管-工人），一个Supervisor负责任务拆解和分发，多个Worker各司其职执行，结果汇总回Supervisor整合；Pipeline（流水线），Agent串联执行，A输出是B输入；Router（路由），按意图分类路由到专家Agent。

工程上Supervisor-Worker最常用，因为可控——Supervisor能看到所有Worker状态，可以兜底。Pipeline适合步骤固定的分析类任务。Router适合意图分类明确的客服场景。

我做的客服系统就是Supervisor-Worker——Supervisor识别意图后分发给订单Agent、物流Agent、退款Agent，结果汇总后整合回答。

类比微服务：Supervisor-Worker = API网关+微服务；Pipeline = 消息事件链；Router = API网关路由。类比一出来工程理解力立显。
Q5：Agent和固定Workflow什么时候用哪个？

看流程能否穷举。业务流程确定、步骤可枚举——用Workflow，可控性强、好调试、成本低；任务开放性强、路径无法预先知道——用Agent，靠LLM动态决策。类比Java：Agent像动态代理运行时决定调谁，Workflow像Template Method骨架预先定好。

实际工程里最佳实践是混合用：主干用Workflow保证可控，少数需要灵活的节点嵌Agent。比如客服流程主干是固定的（识别意图->分发->回答），但"回答"这步可以用Agent综合多工具结果。

强调"不要为了高级而滥用Agent"——这体现你做过真实项目、知道成本和稳定性取舍。说"90%场景用Workflow+Agent节点就够了"非常加分。
Q6：Planning和ReAct有什么区别？什么场景用Planning？

ReAct是边走边想——每步都根据上一步结果现场决定，灵活但容易跑偏、token消耗大。Planning（Plan-and-Execute）是先规划后执行——Planner角色一次性生成完整计划，Executor角色逐个执行子任务，结构清晰、可并行，但规划固化、难应对突发情况。

类比：ReAct像事件驱动（CEP），每步现场决策；Planning像工作流引擎（Camunda），先画流程图再执行。

Planning适合流程相对固定的复杂任务——比如"分析竞品出报告"，步骤可以预先拆解（搜竞品->搜特性->对比->写报告）。ReAct适合探索性、步骤不确定的任务——比如"帮我查这个问题怎么解决"，走一步看一步。

能说出"先规划后执行 vs 边走边想"和各自适用场景，说明你理解了两种范式的本质。提"实际常混合用：Plan出骨架，每步内部ReAct"更显示工程判断。
  • Agent = 感知->决策->行动->观察的自主系统，核心是LLM动态决策，不是"会聊天"。能调用工具获取真实信息，避免幻觉
  • Chatbot无工具（只会说）、Agent有工具且自主调用（会做事）、Workflow路径预先编排（可控但不灵活）——三者区别在决策权归谁
  • ReAct = Think->Act->Observe循环，强制先推理再行动避免盲目调工具。需配maxIterations（通常10）防死循环
  • Planning：ReAct边走边想（灵活但易跑偏）vs Plan-and-Execute先规划后执行（结构清晰但固化）。类比Camunda工作流引擎
  • Tool Use靠description选工具——描述要含功能+输入+输出+触发场景，写不好就选错。多工具编排靠ReAct循环，无硬编码调用顺序
  • Function Calling流程：注册工具Schema->LLM输出ToolExecutionRequest->框架反射执行->结果回传->LLM整合（可循环）
  • Multi-Agent三种模式：Supervisor-Worker（工程常用，可控）、Pipeline（流水线串联）、Router（意图分类路由）。类比微服务编排
  • 选型原则：流程能穷举用Workflow，开放任务用Agent，最佳实践是主干Workflow+节点Agent混合（90%场景够用）
